# Enter starts a new line, and the chord sends

The composer's plain Enter has sent the message since it was written, with Shift+Enter making the line. That is the chat-app convention and not what the field is: the composer is a `<textarea>`, and a multiline field's own behaviour is a carriage return — the HTML spec's implicit-submission list covers single-line `input` types and never `textarea`, and Android's IME offers a carriage return for a multiline field unless the app asks for a send action. Gots is a phone app first, where the return key is the only key there is and Shift does not exist. So Enter starts a new line, and the switch under Appearance — **Send on Enter**, off by default — hands the key back to the send for anyone who wants the convention. Ctrl+Enter sends either way, and Cmd+Enter with it: that is the pair Slack, Microsoft Teams, GitHub's comment box, Gmail and Linear all bind wherever Enter is a line break. Shift always starts a line, so a paragraph never depends on the switch.

Two consequences that are decisions rather than details. The switch stays on this device (`Settings.sendOnEnter`, written by `saveSettings`), unlike its neighbours in that section, which follow the account: a phone's soft keyboard and a laptop's hardware keyboard are different keyboards, so one account-wide value would send on the laptop and then send on the phone's return key — the very thing the default prevents. It also keeps a new field out of the synced appearance record, which is one value with one clock (`mergeDocs` last-write-wins), so a build that predates the field would erase it from the record on its next write. Microsoft scopes its version of this preference to desktop and web for the same reason. And the cheatsheet has to say what the key now does: `cheatsheetGroups` takes the switches that gate it, drawing Enter as the line and Ctrl+Enter as the send while this one is off, and keeping the chord's row when the switch is on because it sends either way, since ADR 0042 requires the sheet to be edited wherever a handler changes and never to advertise a binding that does nothing.

The chord is not a new path: `Enter && !shiftKey` was the old condition, so Ctrl+Enter already sent, and the slash-menu branch — which took any Enter as a pick — now asks `isSendChord` before it picks, so the chord can never be swallowed by a menu that happens to be open under the field. One predicate answers "is this the chord" for both the rule and the menu.

## Considered options

- **Enter sends, with a switch to keep it** — the shape Slack and Teams ship, and the default every messaging product kept when it added the preference. Rejected because it makes the chat convention the default rather than the field's own behaviour: on a phone it puts the send on the only key there is, and a paragraph then needs Shift, which a soft keyboard does not have.
- **Enter lines, with nothing else sending** — rejected: a hardware keyboard could then only send by leaving the field for the Send button, and the harness's own send is a key press. Every product that keeps Enter for a line break binds the chord.
- **Enter lines, Shift+Enter sends** — rejected: it inverts the strongest modifier habit there is ("Shift = the line"), and Slack, Teams and GitHub all keep Shift on the line even in their newline mode.
- **A synced appearance switch, in `APPEARANCE_FIELDS`** — rejected on both counts above: one account-wide value cannot be right for a phone and a laptop, and the record's one-clock last-write-wins merge lets an older build drop the field.

## Consequences

- The composer's keyboard hint follows the switch (`enterKeyHint` is `enter` while it is off, `send` while it is on), so a phone's return key stops claiming to send.
- The test tiers send with the chord: `scripts/e2e/lib.mjs`'s `send` presses `SEND_CHORD` and the three scripts that pressed Enter themselves follow, while the component kit's `pickPress` keeps meaning "pick" where a menu is open and `sendPress` means send. No new flow: the switch's effect is a rendered rule over a seeded database, so the component tier owns it — and `chat-message` gained the one step jsdom cannot perform, that a bare Enter in a real browser leaves the words in the field and starts no run.
- Ctrl+C still stops, a double Escape still clears, and the slash menu still takes the bare Enter and Tab as its pick: only what Enter does to the message moves.
- `docs/specs/cheatsheet-in-the-composer.md`'s second decision is amended in the build that lands this: the composer's rows are the switch's, not a constant, and its third names the switches rather than the one flag.
- A later removal is the section's first retirement of a local switch: `RETIRED_SETTINGS_KEYS` plus a `db.version` upgrade, with no appearance record to clean.
