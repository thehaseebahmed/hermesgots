# Plan: Fix phone bottom-sheet peek geometry and scroll-to-expand

## Overview

Two issues with the expandable phone bottom sheet, both root-caused against Base UI's drawer source. (1) The stack peek behind a child sheet is wrong: Base UI's lift aligns the parent against the *child's bottom-aligned rest position*, ignoring the child's own collapsed snap offset, and nothing accounts for the parent being expanded — so a full-screen parent peeks its square top corners behind the child (and keeps its expanded state, which looked stuck). Per the user's rule, the parent's state is preserved behind a child: full screen → flush behind the child, no peek; not full screen → the usual 28px peek with rounded corners. (2) Scrolling the content up past its end never expands the sheet: Base UI's native touch arbitration only claims gestures moving toward dismiss (down) from the scroll top, and its mouse path ignores presses inside `Drawer.Content` — so only handle drags expand. The fix keeps Base UI's snap points and adds one focused touch-chaining handler for the single gesture Base UI's architecture cannot express. Confirmed with the user: the parent stays where it was after a child closes.

## Approach

- **Peek geometry (replaces the collapse-on-child-open idea):** pure CSS in the sheet's transform. Behind a child, the parent's position is dictated by the child's geometry, not its own snap offset: the parent's top lands exactly at the child's actual top, minus 28px when the parent is collapsed (rounded peek) and flush when expanded (hidden). This required two corrections to the current lift: compensating for the child's own collapsed offset (`max(0, childHeight − 85dvh)` — today a short parent behind a tall child shows a 155px strip with its rounded corner cut off the screen top), and dropping the parent's own snap offset while a child is open (today a collapsed tall parent hides completely behind a short child). Both terms gate on `min(1, --nested-drawers)` so a sheet with no child is untouched, and the peek's existing unwind with the child's swipe is preserved. Verified arithmetically for all eight parent×child height/state combinations.
- **Scroll-to-expand chaining:** a capture-phase `touchmove` listener on the phone sheet's popup. Base UI's native listener (on `document`, capture) runs first and declines upward drags without stopping propagation, so ours sees them next: when the gesture is upward, vertically dominant, and the sheet's scroll container sits at `scrollTop <= 0`, we claim it — `preventDefault` + `stopPropagation` — and move the sheet through the same CSS vars Base UI uses (`--drawer-swipe-movement-y` with the same square-root damping past the top edge; `data-swiping` for a transition-free drag), settling on release: expand if dragged past half the snap offset or flicked, else spring back to collapsed. Upward drags with content still to scroll pass through (the content scrolls natively), which also suppresses a Base UI quirk where an up-drag at the content's *bottom* starts the expand swipe in parallel with the native scroll.
- Rejected: collapsing the parent when a child opens (the user's rule preserves its state); patching node_modules; a full custom gesture engine (the shim covers exactly one missing gesture — Base UI still owns handle drags, collapse, dismissal and snapping).

## Risks and assumptions

- Decision (confirmed with the user): the parent keeps its state behind a child and after it closes — a full-screen parent stays full screen; only the peek follows the rule.
- The peek's child-offset term uses `85dvh` to approximate Base UI's measured viewport height for the child's collapsed offset; on mobile browsers with collapsing UI these can differ by the URL-bar height, bounded to when a child is taller than 85% of the viewport (peek shifts slightly or the parent hides a hair early). Accepted.
- The chaining shim is custom touch handling — a deliberate deviation from the earlier "Base UI native only" decision, forced by Base UI's architecture (its native arbitration only claims toward-dismiss gestures from the scroll top; its React path only claims at the content's end edge). Scoped to one gesture; Base UI owns everything else.
- Event-ordering correctness rests on Base UI's native listener being on `document` in the capture phase (runs before ours at the popup, re-arbitrates every move) — code-verified, to be re-verified live in checkpoint 2.
- Verification limits: synthetic touches don't arm Base UI's React path, so handle/backdrop gestures are verified with mouse drags; the chaining gesture is verified synthetically against our own listener; real-touch arbitration remains Base UI's production path.
- A grandchild sheet (child on child) makes the parent position against the grandchild's height rather than the child's — harmless since a flush parent shows nothing and the peek is a fixed strip.
