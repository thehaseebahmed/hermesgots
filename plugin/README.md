# Gots plugin for Hermes

The [Gots](../README.md) app uses this plugin to keep each bot's chat list on its Hermes server, to show how full each chat's context is, to show where each chat's model changed, to show the agent's todo list in each chat, to show routine (cron) history, to list Hermes Projects and create them with their GitHub repos cloned in, to run project sessions in their own git worktrees with a permission mode, to read a project's GitHub tasks as AFK's frontier and what is out of it, to claim the oldest ready one and work it in a session of its own, to give that claim back when the session is closed or its run never started and to say when one stalled, to hold AFK's switch for a project, to set the model a bot's delegated tasks run on, and to label its chats in the Hermes dashboard. It reads Hermes's cron execution ledger (`cron/executions.db`), so every device sees the same runs, including the ones that happened while no device was looking.

It has two parts:

- **API server routes** (`__init__.py`). Gots calls these with the bot's API key, and they follow the API server's `API_SERVER_CORS_ORIGINS`.
  - `GET /api/plugins/memento/info` returns the plugin's name, version and features.
  - `GET /api/plugins/memento/cron/runs?per_job=24[&job_id=…]` returns each job's newest runs from the ledger, newest first.
  - `GET /api/plugins/memento/chats` returns the chat list Gots keeps here: titles, Hermes session ids and deletions, keyed by chat id. `POST` it `{ "chats": { … } }` to merge a device's list in (the newer record wins) and get the merged list back. A chat's value may carry `draftText` (its unsent composer text) and `mode` (the session's picked permission mode); each record is capped at 64 KB, and the `draft_text` feature in `info` marks a plugin that accepts drafts. It's stored in `$HERMES_HOME/memento/memento.db`, outside the plugin's folder, so updates leave it alone.
  - `GET /api/plugins/memento/sessions/{id}/context` returns the prompt tokens of the session's latest model call and the context window Hermes runs it with, recorded by a `post_api_request` hook, and `model_changes`: every model that session's calls ran on, oldest first, so a chat's thread can show where the model changed. It follows compression to the session that continues the chat, and answers the model history under the id the app asked with too.
  - `GET /api/plugins/memento/usage?provider=…` returns the provider's account-usage windows (label, used percent, reset time) by calling Hermes core's own `fetch_account_usage` with the profile's credentials, so the app can show how much of a plan's quota is left. Core is asked with `read_only` only where the Hermes it runs on takes it (a display read never refreshes or rotates a credential there, and an older core is read the plain way instead of failing). Supports the providers Hermes core knows: `anthropic`, `openai-codex`, `openrouter`, `opencode-go`, plus `ollama-cloud`, whose limit windows the plugin reads itself from `GET https://ollama.com/api/balance` with the profile's `OLLAMA_API_KEY` (core has no fetcher for it). An unsupported provider returns an empty windows list.
  - `GET /api/plugins/memento/sessions/{id}/todos` returns `{ revision, todos, progress }`: the list the agent's `todo_list` tool last wrote in the session (or the sessions it was compressed from), read from the transcript, each item with its `depth` under its parents and the list with its own progress. All are null when it has none.
  - `GET /api/plugins/memento/projects` returns the profile's Hermes Projects (`hermes project create`) with their folders, whether each folder is a git repo, its GitHub `user/repo` and the branch a session's worktree starts from, and when a session last ran in one of them. Gots's Code screen lists them.
  - `GET /api/plugins/memento/github` says whether the server has a GitHub account (`GITHUB_TOKEN` or `GH_TOKEN` resolved through Hermes's `get_env_prefer_dotenv`, else the gh CLI's login), and `GET /api/plugins/memento/github/repos` lists its repos. The token stays on the server.
  - `POST /api/plugins/memento/projects` with `{ "name": …, "description": …, "repos": ["owner/name", …] }` creates a project in `$HERMES_HOME/projects/<slug>/` and clones each repo from GitHub into it, so a repo used by two projects has a clone in each. It needs `git` on the server.
  - `POST /api/plugins/memento/projects/{id}` with any of `{ "name", "description", "archived", "pinned" }` edits a project, archives or restores it, or pins it; `GET /api/plugins/memento/projects` lists archived projects too, with `archived` and `pinned_at`. `GET …/projects/{id}/usage` sums the tokens and cost of the sessions that ran in the project's folders, from Hermes's session store. A session that switched models mid-way is split by the model that ran each call (`session_model_usage`), with anything those rows don't account for counted under the session's own model, so the total never changes.
  - `POST /api/plugins/memento/projects/{id}/repos` with `{ "repo": "owner/name" }` clones another repo into the project in the background (202) and adds it to the project once it's in; `POST …/repos/remove` takes one out at once and deletes the plugin's clone of it in the background (a folder the plugin didn't make stays on disk). The projects list shows each such repo with `status: "cloning" | "failed" | "removing"`. While a repo is being added, no new session can start in the project, and a session that worked in a removed repo can't take another turn (the workspace reports why as `blocked`).
  - `POST /api/plugins/memento/sessions/{id}/workspace` with `{ "project_id": …, "task": …, "mode": … }` gives a Gots project session a git worktree in every repo of the project (`<repo>/.worktrees/<task-slug>`, branch `hermes/<task-slug>`, made with Hermes's own worktree code) and points the session's terminal and file tools into the primary repo's. The answer carries the workspace (each repo as `user/repo` from its GitHub `origin`, and `files_dir`, the session's library folder `<project folder>/files/<task-slug>/`) and an `instructions` line that tells the agent where its worktrees are and where its generated files go, which Gots adds to every run. Gots posts it before every run, because that pointer only lives in the gateway's memory; the `pre_tool_call` hook restores it after a restart. `GET` returns the workspace (null without one), `POST …/mode` with `{ "mode": "accept_edits" | "auto" | "plan" }` changes the permission mode, and `POST …/workspace/remove` removes each worktree that has no uncommitted changes and no commits a remote lacks, keeps the others and says which (`kept: [{ name, reason }]`).
  - **The agent files its generated files in the session's library with the `library_add` tool** (`library.py`, registered on the `memento` toolset and added to every API-server agent like `pull_request`). The screenshots, images, charts, reports and markdown a session makes for the user belong under `files_dir` (`<project folder>/files/<task-slug>/`, beside `plans/`, outside the worktrees so nothing lands in the branch's diff), not in the worktree; the run's `instructions` say so, right after the worktree line. The tool takes a `path` (absolute or relative to the session's cwd) and a required `folder`, files the file at `files_dir/<folder>/<name>` — creating the folder if it needs to (a session row from before `files_dir` existed resolves it from the project, the way `save_plan` resolves `plans/`) and keeping `files/` in the project clone's `.git/info/exclude` when the folder is itself a repo — and answers `{ name, path }` with the new absolute path, which the agent can reference with a `MEDIA:<path>` tag for an image. **Folders and file names are kebab-case slugs** (`^[a-z0-9]+(-[a-z0-9]+)*$`; a file name is a slug plus one extension, `dashboard-light.png`), and folders are named after the flow or change the files belong to — `library-tab` for work on the library tab, `library-tab-tree-view` for a follow-up change to it — not the file type, so one project's library reads as a tree of what was done. The tool's description and the `instructions` teach this; a name that isn't a slug is rejected, never rewritten, with the nearest correction and the rule (e.g. `'Library Tab' is not a slug (…); name the folder after the flow … Call again with folder 'library-tab'.`), and a file name that isn't one tells the agent to rename it on disk first. A file of that name already in the folder is an error naming the file and folder: the agent renames it and calls again, and nothing is renamed for it. `workspace/remove` and `close` leave the folder alone: the files are the deliverable.
  - `GET /api/plugins/memento/projects/{id}/tasks` answers `{ repos, ready, claimed, blocked }`: the project's tasks as AFK reads them from its repositories' GitHub issues, for the app's AFK sheet. A repository is read a page at a time, following GitHub's `Link` header, so a project whose ready tasks outnumber one page still has every one of them read. Only an issue that is open and marked `ready-for-agent` is AFK's at all; it is **claimed** — and so out of the frontier — when it carries an assignee or Gots's own `gots-got-it` mark, **blocked** while any of its blockers is still open, and **ready** otherwise, oldest first (ADR 0011, ADR 0012). A blocker is GitHub's native issue dependency; a `Blocked by: #n` line at the top of the body is read only for an issue that has no native edges, a number that names no issue blocks nothing, and one that can't be read counts as open, so a task is never worked ahead of its blockers. The rule is `tasks.groups`, one function over the rows the read has already fetched, so it is tested without GitHub (`tests/test_tasks.py`). A server with no GitHub account answers GitHub's own refusal (409) rather than an empty frontier, so the sheet can say why it can't read the tasks; a project still being cloned answers empty groups. `info` reports the route as the feature `afk`.
  - `GET /api/plugins/memento/projects/{id}/afk` answers `{ on, reason, task, refusal }`: whether the project is left to work its own tasks — AFK's switch, kept in the plugin's store (`project_afk`), so it is the project's own setting rather than the device's — and, when it can't be, why: `"This project has no repository."` when none of its checkouts points at a GitHub repository, `"No GitHub account on the server."` when the host has no token to read or claim a task with, `"This project is archived."` once the project is put away. `task` is the task AFK has claimed and is holding (`{ repo, number, title, url, created_at }`, or null) and `refusal` the last reason GitHub refused its sweep (or null). `POST` the same route with `{ "on": true | false }` turns it on or off and answers the same shape after the write; turning it on is refused (409, the reason as its message) for a project that can't be worked, and nothing is written, while turning it off is always allowed. A project still being cloned answers 409 rather than a switch, where its task read answers empty groups. Archiving a project turns its switch off and deleting one forgets it (`afk.py`, `tests/test_afk.py`); a project archived where the plugin didn't do it — Hermes's own dashboard or CLI — is turned off the first time its switch is read, so restoring it starts off rather than resuming work nobody asked for. `info` reports the route as the feature `afk_switch`, apart from `afk`, so a plugin that can list a project's tasks but never switch AFK on shows the switch off and disabled rather than a control that could only fail.
  - **AFK claims the oldest ready task.** With the switch on, a sweep on the host — every `SWEEP_SECONDS` (three minutes), at once when a project is turned on, and when a project session ends — reads each of the project's repositories' frontiers and takes the oldest ready task: labelled `gots-got-it` and assigned to the host's GitHub user, in that order, and a refused assignment takes the label back off, so a task a failed claim half-touched returns to the frontier. Both go through `github.claim_issue` and the token every other GitHub call uses; the label is created on the repository the first time it's used (`_ensure_label`, colour `#0e8a16`), because a label that doesn't exist can't be applied (ADR 0012). One task per project at a time: a project already holding one is left alone, and the hold is the host's record (`project_afk.task`/`claimed_at`, schema v26), not the app's. The hold lasts as long as the run working the task (ADR 0015): a run that finishes lets go of the hold and leaves the claim on GitHub, since the work is in review; a run that fails or was interrupted keeps both and records why (`project_afk.stalled`/`stalled_at`), and the project's session is then reported as waiting (`runs/live`, `{ kind: "stalled", reason }`); closing the session — discarded, resolved or deleted, read off the chat list so a close from any device counts — gives the claim back (`afk.release`, `github.release_claim`: the label off and Gots's own assignment with it, because a task carrying either is out of the frontier, so the label alone would leave it claimed for good), as does a start that never got its run away, and the next sweep may take the task again — never the one that gave it back, so it isn't handed out the moment the user walks away. A hold naming no session — a row claimed before the column existed — goes back once it is older than `STALL_SECONDS`, since nothing can be working it. A hold is settled whatever the switch says — a project switched off mid-run still gives its task back when the session is closed, and is swept for its hold alone — so the switch only decides whether a new task is taken. A reason the project can't be worked — no repository, no account, archived — is the switch's own (`afk.reason`), not a refusal; a GitHub refusal — no permission to write issues, a rate limit, no connection — leaves the switch on, records its reason (`project_afk.refusal`/`refused_at`) and stops that sweep, so the sheet says why instead of the app retrying; the next sweep is the next attempt. Releasing is best-effort on GitHub: a refusal to take the marks off is recorded for the sheet and the hold goes anyway. `afk.run` is the loop (started beside the other background loops; it sweeps every home the process serves, `link.served_homes`), `afk.wake` asks for a sweep now (from a write that turns the switch on, from a session ending and from a release), and the claim is tested through the plugin's HTTP stub (`tests/test_afk.py`, `ClaimStubTests`).
  - **AFK works the task it claimed in a session of its own.** The sweep answers the task it claimed, and the loop starts each one after that home's sweep: `sessions.ensure` makes the session the way the app's workspace route does — its own worktree and branch in every repo of the project, mode `auto`, an id of `memento-afk-…` the plugin's hooks label — `sessions.apply_cwd` points its tools into that worktree, `POST /v1/runs` starts the run on the profile's own API server — carrying no model, so the host's own runs, and the key that home's `.env` holds, else the one `outbox` knows — and `afk.publish` then writes the chat record that makes it appear and open in the app: its title `#<number> <task title>`, its `hermesSessionId`, the project, `mode: "auto"` and `afk: true`, with an `updatedAt` one millisecond newer than its `createdAt` (the Code list hides a session nothing was sent in by that rule, and the app marks an `afk` row with a chip). A run that started but couldn't be published is logged with its session id rather than left to vanish. The run's input is one line naming the issue and where it is, built by `prompt_builder.afk_input` — `Implement Issue #265 (https://github.com/owner/repo/issues/265)` — and its `instructions` are `prompt_builder.afk_prompt`, the one module every word the agent is told lives in: the session's own prompt (its worktree, where its files go, how to report progress, the `pull_request` tool and the repo's template), then the AFK block, which says the issue was planned before the user left and is implementation rather than design — read it from GitHub (`gh issue view <n> --repo <owner>/<repo> --comments`) instead of being handed its text, plan with the todo list, write the test first, follow the repo's own conventions and commands, run its own gates before shipping, and open one draft pull request whose body says what changed and how it was verified, leaving the `Closes` line to the tool — and that nobody is there to ask, so a decision is made, recorded and, where it matters, given a second opinion with `delegate_task`; a run that can't finish leaves a consistent tree and names its blocker. The issue's own text is deliberately not copied into the prompt, so it can't go stale and the prompt is the same tokens every turn. Auto is the session's own mode, so Hermes's per-session approval bypass is on (ADR 0011). A session that can't be made, or a run that can't start, starts nothing and gives the claim back (`afk.release`, ADR 0015) — a task nothing ever began is handed out again rather than lost. The row names the session as soon as it exists (`project_afk.session_id`, written before the run is posted), so the restarted host adopts that session rather than starting a second one on the same task, and the session's run ending is what settles the hold: a run that finished lets go (`_free`, the claim staying for the review), one that failed or was interrupted records why (`_stall`, `project_afk.stalled`/`stalled_at`) and is reported as waiting by `runs/live` (`afk.stalled`: `{ kind: "stalled", reason }`, the reason the run's own words — "The run failed." / "The run was interrupted." — and a claim nothing has touched for `STALL_SECONDS` (five minutes) after a restart given `DEFAULT_STALL`), never beside a live run. The user's own Discard or Resolve on that session is what gives the claim back (`_settle`, reading `discardedAt`/`resolvedAt`/`deleted` off the chat list, and the close route's `afk.release_session` for the record the session carries), wherever it was closed. Tested for what it publishes — the record's fields and its clock, and the run's request — with Hermes's `sessions.ensure` and `outbox.post` patched (`tests/test_afk.py`, `AfkSessionTests`), because that record is what makes the session visible at all (ADR 0013), and for the hold's whole life — given back when a start fails, freed when a run finishes, stalled when one doesn't, adopted after a restart, released when the user closes the session — against a real store and the plugin's HTTP stub. The session's own record names the task it works (`project_sessions.task`, written as the run is published), and its pull request body carries `Closes #<n>`: `ship` reads the task off that record and adds the line in the task's own repository only — GitHub closes an issue through a pull request in the same repository, so a project's other repos open theirs without it — once, and restores it on a body an `update` replaced. Opening that pull request is AFK's own news: an `afk_pr` push under the `code_afk_pr` category, whose tap lands on the session whose pill opens the pull request (`tests/test_pull_request_tool.py`, `AfkTaskTests`).
  - **The Library tab reads the tree from three routes.** `GET /api/plugins/memento/projects/{id}/library` answers `{ folders: [{ name, files: [{ name, path, size, at, worktree, folder }] }] }` from a walk of the project's `files/` folder: folders alphabetical, files newest first, capped at 500, and a file with no folder (filed before folders existed) grouped under its worktree's name. `GET /api/plugins/memento/sessions/{id}/library` answers the same folders for one worktree (`worktree` names it), with an empty tree — never a 404 — for a session the plugin doesn't know, since the app reads a 404 as a missing plugin. `GET /api/plugins/memento/library/file?path=…` serves any file under a project's `files/` folder (Hermes's own media-path safety check, then the containment check against every project's library root) with its extension's content type: an image, markdown and friends as text, anything else as an octet-stream the browser downloads — capped at `media.MAX_BYTES`, like an image. The library walks the filesystem rather than an index, so files outlive deleted session rows. The app shows it as a tree: each folder (title) with the session that filed it (subtext), its files beneath as icon-and-name rows.
  - In `auto` mode the same hook turns on Hermes's per-run approval bypass (`enable_session_yolo`, keyed by the run id), so dangerous commands run without a prompt and nothing needs the app open; the hardline blocklist still blocks. It switches the bypass off again when the mode isn't `auto`. `POST …/mode` to `auto` also approves, once, anything a run of the session is already waiting on (a guardian's DENY is left for the user).
  - In `plan` mode the plugin's `pre_tool_call` hook blocks `write_file`, `patch`, `execute_code`, `delegate_task` and any `terminal` command that isn't a plain read (`ls`, `cat`, `grep`, read-only `git`, …), so the agent can only investigate and present a plan, and the run's `instructions` carry the plan's shape (overview, approach, changes, checkpoints that each name their commit message, verification, risks and assumptions) and ask the agent to settle every open choice first, with the `clarify` tool where it can, so the plan leaves nothing for the user to decide. A reply that is a plan (it has a `# Plan:` heading) is saved by the `post_llm_call` hook as `plans/<branch slug>-<YYYYMMDD-HHMMSS>.md` under the project's primary folder, with a YAML front matter naming the session, branch, project and time; every iteration gets its own file, and when that folder is itself a git repo `plans/` goes into its `.git/info/exclude`. The workspace reports the newest one as `plan_file`. When such a turn finishes, the workspace also reports `plan_pending`, which Gots shows as a plan waiting for approval, until the user changes the mode or sends the next message.
  - `GET /api/plugins/memento/sessions/{id}/prs` returns every pull request from the session's branch in each of its repos, newest first — the ones it already merged or closed included, so the session has its whole history (`{ repo, number, title, state, checks, url }`, where `state` is `open`, `draft`, `merged` or `closed` and `checks` is `success`, `failure`, `pending` or null from the head commit's check runs and statuses, asked for the open ones only). Looked up with the server's GitHub token when it has one.
  - `POST /api/plugins/memento/sessions/{id}/close` is what the app sends when a session is deleted or discarded: it removes the session's worktrees that hold nothing unpushed or uncommitted (the others are kept and named, as with `workspace/remove`), then closes the open pull request from its branch in each repo and deletes the branch on GitHub when it was pushed. It answers `{ removed, kept, results: [{ name, closed, branch_deleted, error? }] }`; one repo failing doesn't stop the others.
  - The agent gets a `pull_request` tool with a required `action` (`ship`, `push`, `update`, `status`; `title`, `body`, `commit_message?`, `force?`) and is told to call `ship` once the work is done and checked: it commits what's left in each worktree, pushes the branch with the server's GitHub token and opens a **draft** pull request into the branch the session started from, or pushes to the one open. Pull requests are always drafts; there is no draft parameter. `force: true` replaces the branch's remote commits after a rebase or amend, leasing against the commit this session last knew the branch at (`--force-with-lease=<ref>:<sha>`, never a ref it refreshes on the way — that would always match and guard nothing), so a branch that moved since then is refused, not overwritten; with no commit to check against, it refuses rather than overwriting blind. `update` changes the open pull request's title and/or body; `status` reports without writing. `merge` and `close` are listed in the enum but refused with a message telling the agent that merging and closing are the user's decision, to ask the user with `clarify` instead. The old `open_pull_request` name stays as a stub that only redirects to `pull_request`. The session's instructions name each repo's pull request template so the description follows it, else Summary, Changes and How to test; the Gots Code footer is added. They also tell the agent, once the work is done, not to share the pull request url or the commit message in its reply (the tool's result and the session's PR list already surface them) and to update its todo list to its final state — every item completed, or cancelled where it was dropped. A commit without a git identity on the server uses the GitHub account's no-reply address. Plan mode blocks the tool.
  - Every 5 minutes, and whenever the app asks for a session's pull requests, a project session whose pull requests are all settled with at least one merged is marked resolved in the chat list, so it resolves on every device with the app closed. A merged pull request does it once: a session reopened afterwards stays open.
  - `POST /api/plugins/memento/dictation?hint=…&context=…` with a recorded clip as the body (`audio/webm`, `ogg` or `mp4`, up to 9 MB) answers `{ text, ms }`: Hermes's own local faster-whisper path (`_transcribe_local`, with the host's model, language and anti-hallucination settings) transcribes it, whichever provider the host picked for voice notes, and Whisper's stock phantom phrases come back as `""`. `hint` (the bot's name, the chat title, a project's repos) follows the host's `stt.local.initial_prompt` as Whisper's prompt, and `context` (the text of the recording so far, when the app sends it in pieces cut at pauses; its last 400 characters) goes last. One clip runs at a time; the clip is written to a temp file and deleted. `POST …/dictation/warm` loads the model while the user is still talking. `info.dictation` is `{ ready, reason?, model, language }`: ready when `stt.enabled` is on and faster-whisper is importable; it never installs or loads anything (`dictation.py`).
  - `POST /api/plugins/memento/sessions/{id}/attachments?name=…` with a file as the body (up to 9 MB) saves a photo or file the user attached in Gots as `$HERMES_HOME/memento/attachments/<session>/<name>` (a second file of the same name gets `-2`, and so on) and answers `{ name, path, size }`. Gots names the path in the message, so the agent can open the file with its own tools on that turn and later ones; the API server itself only takes images, inline, and keeps them in the transcript as a `[screenshot]` line. The daily cleanup removes the folder with the session.
  - `GET /api/plugins/memento/runs/live` lists the sessions with a run in flight on this API server, each `running` or `waiting_for_approval`, with its run id in `run_ids`, so every device can tell which project sessions are working or waiting, and its `waiting` map carries what a session is waiting for: a `clarify` question (`{ kind: "question", count }`), an approval (`{ kind: "approval", command }`), a project session's pending plan (`{ kind: "plan" }`) or a goal that stopped (`{ kind: "goal", reason }`), each with the project's name — and `{ kind: "stalled", reason }` for an AFK session nothing is working any more, whose run failed or which a restart adopted (ADR 0015).
  - **The agent always has `todo_list`.** Hermes defers it behind `tool_search` by default, and a `platform_toolsets.api_server` list without `todo` hides it entirely, so the plugin adds the tool to every agent the API server builds, whatever the tool config says. `GET /api/plugins/memento/info` reports `todo_tool: true` when the wiring took.
  - **The agent can ask the user questions.** Hermes's `clarify` tool isn't in the API server's toolset and its agents get no way to show a question, so the plugin adds the tool to every agent the API server builds and answers it from Gots: a call puts `clarify.request` on the run's event stream (`{ clarify_id, questions: [{ id, question, choices?, multi_select? }] }`, the first choice being the recommended one) and `clarify` on the run's status while the run waits as `waiting_for_approval`; Gots shows the questions in place of the composer and posts the answers to `POST /api/plugins/memento/runs/{run_id}/clarify` with `{ "clarify_id", "answers": { "q0": "a choice or typed text" | ["several"] | null }, "outcome": "submitted" | "cancelled" }`; the run then carries `clarify.responded` and the agent carries on in the same turn with the answers. An unanswered question times out after Hermes's `agent.clarify_timeout` (an hour by default). `GET /api/plugins/memento/info` reports `clarify: true` when the wiring took on this Hermes version.
  - `POST /api/plugins/memento/model` with `{ "provider": …, "model": … }` makes that the profile's main model in its `config.yaml`, which is what a bot's Default model in Gots sets. It goes through Hermes's own `switch_model` and `persist_model_selection`, as `/model --global` does in a messaging chat, so Hermes checks the pick (a refusal is a 400 with its reason), only the `model.*` keys it changes are written and the file's comments stay. The next turn on every surface of the profile runs it, without a restart.
  - `GET /api/plugins/memento/fallbacks` answers `{ "object": "memento.fallbacks", "fallbacks": [{ "provider": …, "model": … }, …] }`, the profile's fallback models in the order Hermes would try them after the main model, and `POST` it `{ "fallbacks": [ … ] }` to make that list the chain, which is what a bot's Fallback models field in Gots sets (an empty list, or no `fallbacks` key at all, clears it). At most two: a longer list is a 400 `A bot takes at most 2 fallback models`, unless it is shorter than the chain the profile already holds — a chain of three built with `hermes fallback` can be trimmed from Gots, never grown. A new or edited pick is checked by Hermes's own `switch_model` exactly as the main model is, so an unresolvable one is a 400 with Hermes's reason (`GET` and `POST` answer with the picks as stored, provider and model trimmed). **They are Hermes's own failover chain:** the top-level `fallback_providers` key that `hermes fallback` writes, so Hermes tries them, in order, on every surface of the profile after the main model fails, and the legacy single `fallback_model` key is dropped when it is there, so the chain has one source of truth. The write is one key at a time through Hermes's round-trip YAML save, so the rest of the file and its comments stay, and a cleared profile keeps no empty list behind it. A read answers with provider and model only: a credential or endpoint a hand-written entry carries stays in the file and rides along through an edit. Whatever Hermes's own reader can't use (a hand-edited entry, junk) is dropped on read. `info` reports the route as the feature `fallbacks`.
  - `GET /api/plugins/memento/delegation` answers `{ "object": "memento.delegation", "delegation": { "provider": …, "model": … } | null }`, the model the profile's delegated tasks run on, and `POST` it `{ "delegation": { … } }` to make that the pick, which is what a bot's Second opinion field in Gots sets (`null`, or no key at all, clears it). **It is Hermes's own delegation model:** the `delegation` section's `provider` and `model`, which every `delegate_task` child runs on, and nothing set there means a child inherits the bot's own model. A new pick is checked by Hermes's own `switch_model` exactly as the main model is, so an unresolvable one is a 400 with Hermes's reason, while a pick the profile already holds is not checked again. The write moves those two keys one at a time through Hermes's round-trip YAML save, so a budget, a concurrency or a hand-written endpoint in the section stays, and so do the rest of the file and its comments; clearing removes both keys. A read answers with provider and model only: a section that sets just `model` — or `provider: auto` — comes back under the main model's provider, since that is where its credentials point. `info` reports the route as the feature `delegation_model`.
  - `GET /api/plugins/memento/skills` answers `{ "object": "list", "data": [{ "name", "description", "category" }, …] }`, the skills the profile can actually run (enabled, platform-matching, loadable copies, the set `/name` would invoke), sorted by category then name. It reads Hermes's own listing under the request's profile scope, so a `/p/<profile>` twin answers that profile's list. The composer's `/` menu reads it. A Hermes that moved the internals it reads answers 501. `info` reports it as the feature `skills`.
  - `GET /api/plugins/memento/mcp` answers `{ "object": { "servers": [{ "name", "state", "enabled", "source", "reason", "access", "tools" }, …] } }`, the bot's MCP servers sorted by name, read from Hermes's own in-process machinery inside that bot's profile scope and never connecting one. `state` is one of Gots' own words: `on`, `off`, `connecting`, `failed`, `needs_access` (a server Hermes would need Server access for, because its configuration declares `auth: oauth` and no access is stored) and `plugin` (a server a Hermes plugin provides, which Hermes refuses to modify and the app therefore shows read-only); a server configured but not yet connected reads as `on`, as does one whose configuration never says whether it is enabled. `enabled` is that flag as a boolean, which the app's switch follows rather than the state word, since the word is cached runtime and can still read `connecting` for a server just switched off. `source` is `config` or `plugin`, and `reason` carries Hermes's own failure text for a `failed` server, else null. `tools` is how many tools Hermes has registered for it, and is null unless it has registered any — a server never spawned reports 0, which is not a count, so the app's row says *Healthy* alone rather than *Healthy: 0 tools*. The read reports cached runtime state only, so opening the screen cannot start a server. `info` reports it as the feature `mcps`, only when the Hermes built-ins it reads are present; a Hermes without them answers 501.
  - `GET /api/plugins/memento/mcp/catalogue` answers `{ "object": { "entries": [{ "name", "description", "installed", "needs_config" }, …] } }`, Hermes's own Catalogue as that bot is offered it, sorted by name: every entry Hermes's own `list_catalog` returns, each marked with whether this bot's configuration already has it (`installed`, Hermes's own `is_installed` read inside that bot's profile scope). `description` is what Hermes says the entry is, empty when it says nothing about one; `needs_config` is whether the entry's manifest declares a value to fill, which is what decides between the app adding it on a tap and opening its form. It is the browsing half of adding a server and nothing more: it connects nothing, writes nothing, and never answers a value an entry declares, so opening it cannot change the bot. `info` reports it as the feature `mcps_catalogue`, only when the catalogue's own built-ins are present — a set of its own, because a host can list a bot's servers without offering a Catalogue — so that host's bot gets no Add action rather than one whose every tap would be a 501; a Hermes without them answers 501. Adding one from an entry is `POST /mcp/install` below, its own route and its own step.
  - `GET /api/plugins/memento/mcp/catalogue/<name>` answers `{ "object": { "entry": { "name", "description", "installed", "values": [{ "name", "prompt", "required", "secret", "default", "set" }, …] } } }` — one entry of that Catalogue with the values its manifest declares (`auth.env`), which is what the form that adds it is built from. Each value carries what it is called, what the manifest prompts with, whether it is required and whether it is secret (a manifest that says neither reads as both, which is Hermes's own defaulting), the default the manifest pins, and `set`, whether this bot already holds a value for it. A **secret's** default is never answered, because the field is masked and a default in it would be a credential on screen; a plain value's default is what makes the common case one tap. `set` is the only thing this route ever says about a value the bot has — the value itself never leaves the host, and no route answers one — and the read runs inside that bot's profile scope (Hermes's own `get_env_value`), so a `/p/<profile>` twin answers that profile's. It builds nothing and writes nothing: reading an entry cannot change the bot. An entry the Catalogue has no such name for is a 400; a Hermes without the Catalogue's built-ins answers 501, and `info` reports this route under the feature `mcps_add` rather than `mcps_catalogue` beside it — reading one entry takes the adding set, because reporting whether a declared value is set means reading the profile's environment — which is where the app reaches for it anyway, since its form only opens where `mcps_add` is advertised. A value whose manifest pins a default is answered with it; a **secret's** is not, so a manifest that pinned one there would still be asked for rather than quietly used from a field nobody can see.
  - `GET /api/plugins/memento/mcp/<name>` answers `{ "object": { "server": { "name", "source", "transport", "url", "command", "args", "auth", "editable", "values": [{ "name", "set" }, …] } } }` — one server's block whole, which is what the Config tab is built from. `transport` is `http` or `stdio` and decides which of `url` and `command`/`args` the screen shows; `auth` is `none`, `header` or `oauth`; `editable` is false for a server a Hermes plugin provides, which Hermes refuses to modify. Each `values` row names an environment **key the block itself declares** and says only whether the bot holds a value for it — never the value, which no route answers — so a row the user added by hand is titled with its own name and nothing borrowed from the Catalogue. Reading this builds nothing, connects nothing and writes nothing. A name the bot doesn't have is a 400; a Hermes without the config read's built-ins answers 501, and `info` reports it under `mcps_config`.
  - `POST /api/plugins/memento/mcp/<name>/config` saves the Config tab's edit of one server and answers `{ "object": { "servers": [ … ], "server": { … } } }` — the servers left, and this one's block as the write landed it, so the screen that saved needs no second read. The body carries the transport the form ended on and its fields (`url`, or `command`/`args`), `auth` with an optional `token`, and `values`: the environment values typed over, by name. The block is built from the one the profile has, so every key this screen doesn't manage — a server's `enabled` flag, an OAuth client block, a connect timeout — is left exactly as it was; switching transport drops the old one's fields, since a URL and a command are never both. An empty value is nothing typed, so a value the bot holds is never asked for again; a typed one is written to the profile's `.env` and the block keeps its `${NAME}` reference, so no credential is ever part of a configuration. Hermes's own validator has the last word (a 400 carrying its own sentence, which leaves nothing half-written), a name the bot doesn't have or one a Hermes plugin provides is refused the same way, and Hermes's own reconcile follows so the change is live for the bot's next turn. `info` reports it under `mcps_config`, only when the write's built-ins are present.
  - `GET /api/plugins/memento/mcp/<name>/tools` answers `{ "object": { "tools": { "cached", "items": [{ "name", "description" }, …] } } }` from Hermes's own schema cache — the tools it wrote on each successful registration — so opening a server's Tools tab connects nothing; `cached` is false and the list empty for a server that has never connected or whose configuration moved since. `POST` on the same path is the probe: it connects that one server, lists what it offers and disconnects, which is why it is a deliberate tap rather than something opening the tab does, and it answers the same shape with `cached: false`. A probe the server refuses is a 400 carrying the reason Hermes gave; a name the bot doesn't have is a 400, and a Hermes without the cache or the probe answers 501. `info` reports both under `mcps_tools`.
  - `POST /api/plugins/memento/mcp/custom` with `{ "name", "transport", "url" | "command"\+\`args\`, "auth", "token", "values" }` adds a server the Catalogue doesn't offer, through the same write a Config save uses: Hermes's own create contract, its own name rules (lowercase letters, digits and dashes, not one this bot has, not one a plugin provides, and not a word this plugin's own routes answer such as `catalogue`) and its own validator, each refusal a 400 in its own words with nothing added. Its values land in the profile's `.env` behind `${NAME}` references exactly as a save's do. It answers `{ "object": { "servers": [ … ], "server": { … } } }`, the same pair a save answers. `info` reports it under the same `mcps_add` the Catalogue add uses, since neither can land without the config write.
  - `POST /api/plugins/memento/mcp/install` with `{ "name": "<entry>", "values": { "<NAME>": "…" } }` adds that entry to that bot, the same way Hermes's own connectors install one from a connection card rather than the way `hermes mcp install` does: that interactive path (`install_entry`) prompts on stdin and opens a curses checklist in the terminal it runs in, which a plugin answering an HTTP request has none of. Hermes's own `card_install_config` builds the `mcp_servers.<name>` block from the entry's manifest in memory — no prompts, no probe, no checklist — each collected value the manifest declares **non-secret** is inlined into it in place of the manifest's `${NAME}` reference (`_inline_non_secret_value`), and Hermes's own `_save_mcp_server` writes it, which is also the write that refuses an exfiltration-shaped command. Only once that block has landed is each value the manifest declares **secret** written, through Hermes's own `save_env_value` inside that bot's profile scope, so a refusal leaves nothing half-added. Hermes's own reconcile then runs, so the server is live for the bot's next turn, and the answer is `{ "object": { "servers": [ … ] } }` — the servers that profile has afterwards, shaped as the read above — so the app's list is the host's own answer rather than the entry it guessed was added. A value the bot already holds is reused rather than asked for again: the manifest's `${NAME}` reference stays in the block and the profile's `.env` keeps the value, which is why a removal leaves those values alone and re-adding needs no key hunting. An entry whose auth is OAuth is added with its marker and reads `needs_access` until that row's own flow grants the access; nothing here starts one. Four things are refused with 400 and leave the bot exactly as it was: a name the Catalogue has no entry for, a key the entry doesn't declare (configuring one MCP is not a general environment-writing primitive, so this is checked before anything is built), a name Hermes's own environment writer refuses, and a value the entry declares required that is neither given nor already held. A configuration Hermes's own validator refuses is a 400 carrying Hermes's own sentence about it. `info` reports the route as the feature `mcps_add`, only when every built-in it needs is present — the Catalogue's entry read and block builder together with the environment writer and its guard, a set of its own, because a host can read a Catalogue without being able to add from one — so that host's bots get no Add action rather than one whose every tap would be a 501; a Hermes without them answers 501.
  - `POST /api/plugins/memento/mcp/<name>/access` starts Server access for one of that profile's servers and answers `{ "object": { "access": { "name", "url", "expires" } } }`: the authorization URL the provider handed back and how many seconds Hermes waits for its callback, or `url: null` when the access Hermes already holds still works — not an error, since the row's own read then turns `on`. It is Hermes's own in-process start (`tools.connectors.mcp_oauth`), so the flow binds a `127.0.0.1` receiver on the host and the URL is finished in a browser there; Gots starts the flow and never grants it. A second start for the same server while one is running answers that attempt's URL instead of minting another, which matters because Hermes's own start cancels the older attempt and would leave the address the user is already opening dead. A server the profile doesn't have, one a Hermes plugin provides, and one whose configuration declares neither `auth: oauth` nor a URL are each refused with 400, carrying Hermes's own sentence where it has one; the row's *state* is deliberately not a gate, because the recovery this route exists for — a stored access that still works — answers `url: null` rather than an error while its row reads `on`, and refusing anything but `needs_access`/`failed` would refuse exactly that. A Hermes without the start's built-ins answers 501. `info` reports it as its own feature, `mcps_access`, only when `tools.connectors.mcp_oauth` imports.
  - `POST /api/plugins/memento/mcp/<name>/access/callback` with `{ "url": "…" }` takes the address a browser ended on and hands it to the flow that is running for that server: how a phone finishes an access whose callback only the host can reach (the browser shows a connection-refused page, but its address still carries `code` and `state`). The address must name that flow's own redirect, and the query then goes through Hermes's own `deliver_callback`, which compares `state` in constant time and refuses a second delivery — so a late or mismatched paste can't land an access. It answers `{ "object": { "access": { "name", "delivered": true } } }` and grants nothing itself: the flow's own probe connects to the server and records its status, which the screen's next read shows. A paste with no flow running, or for another flow, is a 400 with that reason. `info` reports it under the same `mcps_access`.
  - `POST /api/plugins/memento/mcp/<name>/enabled` with `{ "enabled": true|false }` switches one of that profile's MCP servers, answering `{ "object": { "server": { … } } }` with the row it landed in. The write sets only that server's `enabled` flag, through Hermes's own config read and write inside the profile's config write scope, then runs Hermes's own reconcile so the change is live for the bot's next turn; the consent-gated reload is never invoked, and nothing else of the server's configuration — transport, command, URL, environment, auth — is touched. A server the profile doesn't have, or one a Hermes plugin provides, is refused with 400. `info` reports it as its own feature, `mcps_write`, only when the write's built-ins (the config read and write, the config write scope and the reconcile) are all present, so a host that can list servers without being able to switch one offers no switch at all; a Hermes without them answers 501.
  - `DELETE /api/plugins/memento/mcp/<name>` takes one of that profile's MCP servers away, matching `hermes mcp remove`: the configuration entry and the directory Hermes cloned for it go through the catalogue's own uninstall, and its stored Server access goes through Hermes's own OAuth manager, which evicts the provider cached in the process too, while the values in the profile's `.env` stay because Hermes reuses one when the same server is added again. Hermes's own reconcile then runs, so the server's live connection is torn down and the bot's next turn can't use it. It answers `{ "object": { "servers": [ … ] } }` — the servers the profile has left, shaped as the read above — so the app's list is the host's own answer rather than the row it dropped. A server the profile doesn't have, or one a Hermes plugin provides, is refused with 400; a Hermes without the built-ins answers 501. `info` reports it as its own feature, `mcps_remove`, only when its own built-ins are present — the write's set plus the catalogue's uninstall and the OAuth manager — because a host can switch a server without being able to remove one, and the plugin that first shipped the switch is exactly that host: it advertises no `mcps_remove`, so the app offers its bots a switch and no removal rather than a removal whose every tap would be a 404.
  - `POST /api/plugins/memento/sessions/{id}/label` marks a Gots chat's session with the `memento` source, so the dashboard's Sessions page labels it **Gots**. It only relabels sessions the API server created.
- **A change stream** (`events.py`, `stream.py`). `GET events` tells an open app that a chat, a run's status, the chat list, a project or a routine changed, without any message text, so the app fetches only then. Everything works without it; the app falls back to polling.
- **Push to a closed app** (`push.py`). A device that turned on Notifications in Gots's PWA gives the plugin its browser push subscription (`POST push`); when a session starts waiting on you (an approval, a question, a plan) the plugin sends the device a small encrypted message through the browser's push service. The message names the kind of wait and the session, never what was asked. Needs nothing beyond what Hermes already installs.
- **A message queue** (`outbox.py`). What you send while the agent is busy waits on the host, not on your phone, and the plugin starts each message as its own turn when the run before it ends, so a queue you leave behind still goes with the app closed. A queued message can also steer the running reply; one the agent never got to read comes back first in the queue. A stopped reply pauses the queue until you send again.
- **A dashboard tab** (`dashboard/`). **Gots** in `hermes dashboard` shows the plugin's version, whether it's enabled, how many runs the ledger holds and how many chats it stores.

## Install

```bash
hermes plugins install thehaseebahmed/memento/plugin --enable
hermes gateway restart
```

Restart `hermes dashboard` too if it's running, so it picks up the new tab.

To update, run `hermes plugins update memento`, then restart the gateway.

## Linking to Gots

`hermes memento link <code> --site <url>` (from Gots's link screen; `hermes -p <name> memento link …` for another profile) links the profile to a Gots account, so it shows up in the app by itself:

- It claims the code, checks the account's key against the code's fingerprint, and keeps a host token in `$HERMES_HOME/memento/link.json` (owner-only).
- It always asks for the URL the app reaches the profile at. The default is the URL saved before, else `<main profile's URL>/p/<name>` for another profile, else Hermes's dashboard public URL (`HERMES_DASHBOARD_PUBLIC_URL`, then `dashboard.public_url`; Hermes has none for the API server), else `http://<hostname>:<API_SERVER_PORT>`. `--url` sets it without asking.
- It offers to add what `.env` still lacks: `API_SERVER_KEY`, `API_SERVER_ENABLED=true` and the app's origins in `API_SERVER_CORS_ORIGINS` (never for a profile under `/p/<name>`, which rides the main gateway). `--yes` accepts the defaults.
- It seals the bot record (name, URL, API key) to the account's key before it leaves; the registry can't read it.

The gateway then checks in at start and every 10 minutes for each profile it serves, re-publishing the record when the URL or key changed, when the app lost it, or when the account's key changed. A host removed in the app stops (`Check-in: removed in Gots`). `hermes memento status` checks in once and says how it went; `hermes memento unlink` removes the profile from the account.

The Hermes dashboard's **Gots** tab does the same for the dashboard's profile: paste the code, the address you open Gots at and the API server URL, then add the `.env` lines it lists if any. It also shows the link and unlinks.

Gots needs this plugin on every profile it uses: chat lists, context use, todos, questions and Code all live here.

## Requirements

- A Hermes version with the cron execution ledger and `ctx.register_platform_handler` (and `ctx.register_cli_command` for `hermes memento`).
- The API server enabled with an `API_SERVER_KEY`, the same setup Gots needs anyway.

## Limitations

- On a multiplexed gateway, a profile's routes are at `/api/plugins/memento/p/<profile>/...`, not `/p/<profile>/api/plugins/...`: Hermes's own catch-all for `/p/<profile>/` is registered before plugin routes. Gots handles that itself. The routes answer with the profile's own `API_SERVER_KEY`, home and chat list, but the hooks (context use, todos, plan files, labels) run only in profiles that have the plugin installed and enabled too; `info` reports `hooks: false` otherwise.
- The daily cleanup only covers the profile home the plugin was loaded in.
- The ledger keeps the newest 1,000 finished runs across all jobs.
- The queue starts a turn with the bot's own API key, which the plugin learns from the app's requests. After a gateway restart, a queue on a `/p/<profile>` bot waits until the app next talks to that bot; the default profile's carries on by itself.
