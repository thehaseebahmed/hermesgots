# AGENTS.md

Guidance for AI coding agents (and humans) working on Memento: a playful, minimal PWA companion for [Hermes Agent](https://github.com/NousResearch/hermes-agent).

## Repository

- `app/` is the web and Android app. Run every command below from `app/`; paths in the rest of this file are relative to it unless they start with `plugin/`.
- `plugin/` is the Memento Hermes plugin (Python, no build step). See **Plugin** below. `plugin/skills/` holds the vendored Theseus skill (JavaScript, run by the host's Node 20+); don't edit it by hand.
- `netlify.toml` stays at the root and sets `base = "app"`.

## Plugin first

**A user should be able to ask the agent for something, close the app, come back later and find it done.** So work that has to keep going, or stay correct, while the app is closed belongs in the plugin (`plugin/`), which runs on the Hermes host. It doesn't belong in app-side workarounds.

- Before building a feature, check whether it needs the app to be open, following a stream, polling or answering for the agent. If it does, and the plugin (or Hermes itself) could do it, build it in the plugin.
- If a feature can't be done reliably without app-side hacks, say so **up front**, before writing code. Name what breaks: a session that is broken, blocked or stuck waiting when the user comes back. Then propose the plugin route, or not doing it. Only build the app-side version if the user explicitly insists.
- The exceptions are things that wait for the user by design: a plan in plan mode, an approval in Accept edits mode, a clarify question. Pausing for the user there is expected. Losing work or stalling because the app was closed is not.
- The app is the view and the controls. It may make things smoother while it's open (live streaming, faster updates), but nothing should depend on that.

## Commands

```bash
cd app
pnpm install
pnpm dev         # Vite dev server
pnpm dev:netlify # Netlify CLI dev server (Identity + the sync function; needs a linked site)
pnpm mock        # fake Hermes API on :8642 (say "clean up" to trigger an approval)
```

Before you commit, run `pnpm lint`, `pnpm typecheck` and `pnpm build`. All three must pass.

## Git commits

**Always use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/).** The format is:

```
<type>(<optional scope>): <imperative summary, lower case, no trailing period>

<optional body: what changed and why>
```

- Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- Scopes, when they help: `chat`, `settings`, `bots`, `hermes`, `db`, `pwa`, `ui`, `deps`.
- Breaking changes: put `!` after the type or scope (e.g. `feat(db)!: ...`) and add a `BREAKING CHANGE:` footer.
- Keep the summary line to 72 characters or fewer.
- Use one logical change per commit.
- Examples:
  - `feat(chat): show approvals in place of the composer`
  - `fix(hermes): handle CRLF line endings in SSE frames`
  - `docs: document the HTTPS requirement for remote Hermes servers`

PR titles follow the same format. Fill in `.github/pull_request_template.md` for every PR.

## Stack

- Vite, React 19, TypeScript and Tailwind v4.
- React Router (`src/App.tsx`).
- **shadcn/ui on Base UI**, `base-maia` style (`components.json`). Components live in `src/components/ui/`.
  - Base UI uses the `render` prop, not Radix's `asChild`.
  - Use shadcn components wherever one fits before writing your own.
  - Add new ones with `pnpm dlx shadcn@latest add <name>`. Leave the generated files alone unless there's a reason to change them.
- Dexie (IndexedDB) for all app data. `vite-plugin-pwa` handles the manifest and service worker. Deployed on Netlify (`netlify.toml`).
- Capacitor 8 wraps the same build as an Android app (`capacitor.config.ts`, `android/`). `.github/workflows/android.yml` builds the APK on pushes to `main` and to PRs into `main`.

## Hermes API

These behaviours were verified against Hermes's `gateway/platforms/api_server*.py`. Check the source again before relying on anything new.

- Turns run on `POST /v1/runs` when `GET /v1/capabilities` reports `run_submission` and `run_events_sse`. A chat completion's agent is interrupted when its SSE client disconnects, which happens whenever a phone sleeps mid-reply. A run keeps going without a client.
  - `GET /v1/runs/{id}/events?last_seq=N` replays the buffered events after `N` and then follows live ones. CORS doesn't allow `Last-Event-ID`, so the cursor goes in the query. Each event carries `seq`, which the reply stores (`runSeq`, along with `runId`) so it can resume after a dropped stream or a reload.
  - The events stream sends a `: keepalive` comment every 10s while the run is quiet, so a stream silent for 30s is treated as dead and reopened from `last_seq`; a connection can die without the read ever failing (a phone that slept, a tunnel that dropped it). Polling reads time out after 15s for the same reason.
  - Hermes keeps the buffer (1000 events) for 5 minutes while nobody is listening. After that the events endpoint returns 404, and `GET /v1/runs/{id}` (whose `output` and `usage` are kept for 24h when the run was started with an `Idempotency-Key`) is polled instead.
  - Events: `message.delta`, `message.interim`, `tool.started` / `tool.completed` (no call id, so a completion matches the oldest running call of that tool; its `error` flag marks the card failed; the transcript doesn't store that, so `toMessages` reads it from the result the way Hermes's `_detect_tool_failure` does (`failureReason` in `src/lib/tools.ts`: a terminal command's non-zero exit, or an `error` field), and the reason shows on the call's row. Its `preview` is cut at 500 characters, so `src/lib/tools.ts` reads a cut JSON envelope as far as it goes, and catching up swaps a cut preview for the transcript's whole result), `reasoning.available` (a whole block, non-streaming providers only), `approval.request`, `replay.truncated` and the terminal `run.completed | failed | cancelled | interrupted`, which carries `output` and `usage` (`input_tokens`, `output_tokens`).
  - Hermes v2026.9.24 (the stable release as of 2026-10-05) sends the events stream without CORS headers and without `seq`, and drops the run's events once that blocked subscriber leaves. In a browser the events request then fails with no response; when `GET /v1/runs/{id}` still answers, the reply falls back to polling at once rather than retrying the stream (`MOCK_BLOCK_RUN_EVENTS=1` mimics it): the final `output` from `GET /v1/runs/{id}`, and, for a keyed session, the turn's progress from the transcript every 3s (`liveTurn` in `history.ts`: its tool calls, the ones without a result row shown running, its reasoning and its text so far). So tool cards show with a few seconds' lag, but no live text and no tok/s. Approval requests travel on that stream too, so while polling, `GET /v1/runs/{id}` is read for `status: waiting_for_approval`, whose `approval` field is the pending `approval.request` (command, description, choices; no plugin needed), and the card is raised from it. A final `output` that replaces the text moves the tool cards and approval to the nearest paragraph break. Hermes fixed it after that release (c7b8e44ffe). A stream without `seq` numbers its tool calls itself, and `reconcileHistory` fills a streamed turn's missing tool calls in from the transcript.
  - A keyed profile sends `session_id` in the body and only the new message as `input`. A keyless one sends the whole transcript.
  - `POST /v1/runs/{id}/stop` stops a run.
- Older servers fall back to `POST /v1/chat/completions` with `stream: true`, whose stream interleaves named SSE events with the normal chunks: `hermes.tool.progress`, `hermes.status` and `approval.request`.
- Approvals are answered with `POST /v1/runs/{completion_id}/approval` and a body of `{ choice }`.
- `X-Hermes-Session-Id` continues a session. Hermes only accepts it when `API_SERVER_KEY` is set.
- Hermes's CORS setup does not expose response headers, which is why the client mints its own session ids.
- **The agent asks the user questions with Hermes's `clarify` tool, which needs the Memento plugin.** The API server's own toolset (`hermes-api-server` in `toolsets.py`) leaves `clarify` out and its agents get no `clarify_callback`, so without the plugin the agent can't ask on this surface. The plugin (`plugin/clarify.py`) wraps the adapter's `_create_agent` to add the tool's definition and a callback to every agent it builds; a call puts `clarify.request` on the run's stream (`{ clarify_id, questions: [{ id, question, choices?, multi_select? }] }`, choices bare, the first one recommended) and the same object as `clarify` on `GET /v1/runs/{id}` while the run waits as `waiting_for_approval` (so `runs/live` and the project screen read it as waiting, and a client that can only poll still sees it); the app shows the questions in place of the composer (`QuestionCard`, `Message.clarify`; one question is shown as is, two or more are pages of one form, and a reply keeps only its latest question), posts the answers to the plugin's `POST runs/{run_id}/clarify` (`{ clarify_id, answers: { q0: "text" | ["several"] | null }, outcome: "submitted" | "cancelled" }`), and the run carries `clarify.responded` (with the answers, so another device or a replay resolves the form) before the agent carries on in the same turn. Once answered, a question is the `clarify` tool call's card in the thread (`ClarifyCard` in `session-cards.tsx`, in every chat) and reads from the call's result, Hermes's `{ responses: [{ question, choices_offered, status?, user_response }], outcome? }` (the stable server's persisted rows also use `responses`, with `timed_out: true` for an unanswered timeout): the app writes that result itself when the user answers, since the run stream's preview is cut at 500 characters. Transcript polling preserves that settled result by call id until a nonempty server result arrives; it never substitutes an answer from a different call. A device that loads the transcript reads the persisted `responses` without needing the local question form. Answered responses take precedence over the outcome; a submitted empty form is `Skipped`, cancelled or undelivered questions are `Not answered`, and a timeout is `No answer`. Waiting for an answer is the by-design pause the **Plugin first** rule names; Auto's approval bypass doesn't touch it. No mode answers for the user, `auto` included; an unanswered question ends as `timed_out` after Hermes's `agent.clarify_timeout` (an hour by default), a stopped run as `cancelled`, and a chat completion (no run stream) as `undelivered`, so the agent asks in prose. In plan mode the instructions ask the agent to settle every open choice this way before it writes the plan.
- **Attachments: images go inline, files through the plugin.** Both `/v1/runs` and chat completions take the OpenAI vision shape for a user message's `content` (`[{ type: "text" }, { type: "image_url", image_url: { url } }]`; checked at v2026.9.24 and main). Chat completions validate it (`_normalize_multimodal_content`: `http(s)` or `data:image/…` URLs only, and `file` / `input_file` parts are refused with `unsupported_content_type`); `/v1/runs` passes the last `input` item's `content` to the agent as is, so the app always sends the canonical `image_url` shape, only on the newest message (Hermes `str()`s `conversation_history` entries). Hermes stores such a message as text with each image replaced by a `[screenshot]` line (`_durable_content`), so a keyed session's later turns no longer see the image, and the request cap is 10 MB (`MAX_REQUEST_BYTES`). So the app scales images to a 1600px long edge (`attachments.ts`), and when the bot has the plugin it first saves every attachment on the host (`POST sessions/{id}/attachments`); the message then carries an `<attachment name="…" type="…" path="…" />` line per attachment (the path only once saved), followed by the image itself for a photo, so the agent can open it with its file or vision tools later. Files need the plugin, so **Files** is disabled without it; a photo whose upload fails still goes inline. Camera and Photos are disabled when models.dev says the model doesn't take images (`modalities.input` without `image`, stored as `Profile.imageInput` next to the context window; unknown counts as yes), and an image picked through Files then goes as a file. Files aren't gated on the model's own `attachment` flag: the agent opens them with its tools, which any model can do. `toMessages` splits those lines (and each photo's `[screenshot]`) back off a transcript row, which keeps the text matching the device's own copy; the photo itself lives only on the device that sent it (`Message.attachments[].blob`), and other devices show its name.
- `GET /v1/skills` lists skills for the `/` menu. The code returns `{ object: "list", data }` (the docs show a bare array), and on some versions it returns a 500, so the menu must work without it.
- The API server does **not** expand `/skill-name` messages (only the CLI and messaging gateway do). The composer sends them literally and the model decides what to do with them.
- **Profiles are bots.** Hermes has no endpoint that lists profiles, so each profile's Memento plugin registers it (see **Linking bots**) and the app keeps it as a `profiles` row with its URL, key and model. Secondary profiles are served at `/p/<profile>/...` (`gateway.multiplex_profiles`; newer Hermes always multiplexes unless a profile is `gateway.standalone`). Each profile has its own `API_SERVER_KEY`, and a named profile advertises its name as the `/v1/models` id. The mock serves the same `/p/<profile>/` prefix.
- The final stream chunk carries `usage`. Hermes sums it over **every** model call in the turn, so on a turn that ran tools `prompt_tokens` counts the prompt more than once. Memento doesn't use it for context; the plugin records each call instead (see **Plugin**). No endpoint reports the model's context window, so each bot stores its own.
- Hermes auto-titles API sessions (an instant slice of the opener, then a background model call that can land after the stream ends, and again on turns 2–3 for a placeholder like "Friendly greeting"). `GET /api/sessions/{id}` (server root) returns `{ session: { title } }` but not where the title came from. Memento polls it after the first three turns, which needs the session id and so an API key. CORS doesn't allow `PATCH`, so renames stay local (`titleEdited`) and Hermes's title never replaces them.
- `GET /api/model/options` (server root, not `/v1`) returns the configured `model` and `provider` behind a profile, and `providers`, Hermes's own model picker inventory: `[{ slug, name, is_current, authenticated?, models: [id] }]`, where a row with `authenticated: false` or no models is a provider without credentials. Older versions don't have it, so treat a failure as unknown.
- **A chat can run on another of the host's models.** The usage sheet's Model row opens a list of those providers' models (`getModelInfo`), and the pick is `Conversation.modelChoice` (`{ provider, model }`, synced through the chat list), sent as the turn's `model` and `provider`. `/v1/runs` honours both on every request (`_request_agent_overrides`; checked at v2026.9.24), and chat completions honour a bare model only with `direct_model_requests` but an explicit `provider` always. It needs neither the plugin nor `allow_model_override`, which gates only the plugin's own `ctx.llm` calls (Theseus's reviewers). Unset runs the bot's model.
- The context window is looked up in [models.dev](https://models.dev/api.json) (`limit.context`) by that `provider`/`model` (`src/lib/models.ts`). The bot remembers which model it was for and resets it when the model changes; if models.dev doesn't list the model, the user sets it by hand.
- Cron jobs are called **Routines** in the UI (`/routines`) and `cron` in code. `GET /api/jobs?include_disabled=true` (server root) returns `{ jobs }`. Each job carries `last_run_at`, `last_status` and `failure_streak`. Its `schedule` is Hermes's parsed `{ kind: interval | cron | once, minutes | expr | run_at, display }`; `src/lib/schedule.ts` puts it in words ("Weekdays at 9:30 AM", "Every 15 minutes") and falls back to `display` for shapes it doesn't know. Cron times are the host's clock, so when the next run's offset differs from the device's, the host's offset follows ("(UTC+5)"). `POST /api/jobs/{id}/pause | resume | run` control a job. A 501 means cron isn't available.
- The API server has **no run-history endpoint** (the dashboard's `/api/cron/jobs/{id}/runs` is localhost-only), so **run history needs the Memento plugin** (`plugin/`). `GET /api/plugins/memento/cron/runs?per_job=24` returns `{ jobs: { <jobId>: [run, ...] } }`, newest first, straight from Hermes's execution ledger (`status` `claimed | running | completed | failed | unknown`, plus `delivery_outcome`; a `completed` run whose delivery `failed` counts as failed). Without the plugin the route doesn't exist, and Hermes's 404 for an unknown route skips its CORS middleware, so the browser blocks it and `fetch` fails with no status. `syncCron` treats a failed plugin call as a missing plugin when `/api/jobs` on the same server succeeded, and the Routines screen shows the install commands instead. Runs aren't stored on the device.
- **Hermes Projects** (`hermes project create`, per profile in `$HERMES_HOME/projects.db`) have no API server route, so the Code screen (`/code`) reads them from the plugin's `GET /api/plugins/memento/projects`: `{ projects: [{ id, name, description, created_at, last_active, folders: [{ path, label, is_primary, git, repo, branch }] }] }`, where `branch` (0.17) is the one a session's worktree would start from: `origin/HEAD`'s branch, else what's checked out. The Code screen's rows and the project screen name the repos, and a session not started yet shows them with that branch. Hermes stores no last-worked-on time, so `last_active` is the newest session whose `cwd` sits in one of the project's folders (the innermost folder wins, like the desktop app's grouping), and null when none has. The screen merges every bot's list, newest first; bots on the same server share one list.
- **New projects are created, and their GitHub repos cloned, on the Hermes host**, with the host's GitHub account: `GITHUB_TOKEN`, then `GH_TOKEN` (process env, then `$HERMES_HOME/.env`), then `gh auth token`, the order Hermes's own GitHub calls use. The token never reaches the app. `GET /api/plugins/memento/github` reports `{ connected, login? }`, `github/repos` lists the account's 100 most recently pushed repos, and `POST projects` takes `{ name, description?, repos: ["owner/name"] }`. It makes `$HERMES_HOME/projects/<slug>/` (the profile's home, so profiles stay apart; the slug is the one `projects.db` gets), clones each repo into it over HTTPS (the token goes in an `http.extraheader`, so it isn't saved in `.git/config`), and creates the project with that folder as its primary and each clone as a folder. A repo in two projects gets two clones. Without an account, public repos still clone by name.
- **Creating a project is asynchronous** (`plugin/clones.py`), so it carries on with the app closed. `POST projects` validates, makes the folder, records the project in `memento.db`'s `project_clones` table and answers **202** with it at once; a daemon thread then clones each repo. Until the last clone is in, the project is `pending-<slug>`, **not in `projects.db`**: a project there is always whole, so a session can never get worktrees in only some of its repos, and Hermes's own dashboard never sees a half-made one. `GET projects` lists it after the real ones with `status: "cloning" | "failed"` (real projects carry `ready`; the app reads an absent `status` as ready, for an older plugin), `error`, and each folder's `status` (`queued | cloning | done | failed`). The last clone creates the real project (new id) and drops the row. A failed clone removes the folder and keeps the row with its error until `POST projects/{id}/retry` (starts over) or `…/remove` (also cancels a running clone: `github.clone` takes a cancel event). A restart mid-clone clones again from scratch (`clones.resume`, at startup for the default profile and on the first `GET projects` for any other). A pending project can't be edited (409) or opened; the Code screen shows it with Cloning n of m, or the error with Retry and Remove, and polls every 3s while one is cloning. `info` reports `projects_async`.
- **A ready project's repos are added and removed asynchronously too** (`plugin/repos.py`, `memento.db`'s `project_repos`). `POST projects/{id}/repos` `{ repo }` answers 202 and clones on a daemon thread into `$HERMES_HOME/projects/<slug>/`; the repo joins `projects.db` (`add_folder`) only once the clone is in. `POST …/repos/remove` `{ repo }` takes it out of `projects.db` at once (`remove_folder`) and deletes the clone on a thread, only when it's one the plugin made (a folder of a project folder under `$HERMES_HOME/projects/`) and no other project uses it; for a repo still being added it cancels the clone. `GET projects` lists such repos among the folders with `status: "cloning" | "failed" | "removing"` (and `error`), and a restart picks them up again (`repos.resume`). **While a repo is being added, no new session can start** in the project: the project screen shows a note in place of New session, and `POST sessions/{id}/workspace` answers 409 for a session with no record yet. **A session that works in a removed repo is read-only**: the workspace post answers 409 with the reason, and both workspace answers carry it as `blocked` (`Conversation.blocked`, local), which the chat shows in place of the composer (`BlockedCard`). An archived project blocks its sessions the same way.
- **Projects can be pinned, archived and measured.** `POST projects/{id}` also takes `archived` (Hermes's own `archive_project` / `restore_project`) and `pinned` (the plugin's `project_pins`, since Hermes has no pin). `GET projects` lists archived projects too, with `archived` and `pinned_at`; the Code screen puts pinned ones first and archived ones in a folded group. `GET projects/{id}/usage` sums `input_tokens`, `output_tokens`, the cache counts and `actual_cost_usd` (else `estimated_cost_usd`) over the `state.db` sessions whose `cwd` (or their root's) sits in one of the project's folders (read-only), folding compression children into their root as one session, and lists each one as `threads: [{ id, title, started_at, last_active, models: [{ model, <the four counts>, cost_usd }] }]` (0.21). The Usage view (`project-usage.tsx`) shows the totals, the split by kind and each session's share, and its **Est. cost** comes from `src/lib/pricing.ts`: Anthropic's first-party prices for a Claude model id (cache writes as Hermes's default 5-minute writes; Bedrock and Vertex sessions are priced the same), Hermes's own cost for any other model, and a `+` when some usage had neither. Update the price table when Anthropic's prices change.
- **Voice input uses the browser's Web Speech API (and, in the Android app, whose WebView has no recognizer, Android's `SpeechRecognizer` through `@capgo/capacitor-speech-recognition`), not Hermes STT.** Hermes exposes its STT provider config only on the dashboard server (`GET /api/audio/voice-config`), whose CORS allows only `localhost` origins and whose session token rotates each start; the API server reports `audio_api: false`. The wire shapes it hands out (OpenAI multipart, xAI, ElevenLabs) are upload-only, not streaming.
- `GET /api/sessions/{id}/messages?order=latest&limit&offset` (server root) pages a session's transcript back from the newest row, but returns each page oldest first. Rows carry `id` (increasing), `role`, `content`, `tool_calls`, `tool_call_id`, `tool_name`, `timestamp` (Unix seconds), `reasoning` and `display_kind` (`hidden` rows are compaction scaffolding; skip them). Memento uses it to fill in chats synced from another device.
- **The agent's todo list is Hermes's `todo_list` tool** (`tools/todo_tool.py`), not Kanban: one list per session of `{ id, content, status: pending | in_progress | completed | cancelled, parent? }`, where each call returns the whole list with a `revision` and is stored as a `tool` row (written after every tool round, so mid-turn too). It's a deferred tool by default (`tool_search.defer`) and a saved `platform_toolsets.api_server` without `todo` leaves it out of reach, so the plugin adds its definition to every agent the API server builds (`todos.wire`, over `_create_agent` like `clarify`; `info` reports `todo_tool`), whatever the user's tool config says. `startRun` sends a fixed `instructions` line (Hermes appends it to the system prompt) asking the agent to plan with it on work of three or more steps. The run stream's `tool.completed` preview is cut at 500 characters, so a live preview is applied only when it parses, and the list itself comes from the plugin. A tool-search bridge call reports as `tool_call`. Once the turn is over, an item still `in_progress` shows as stopped (a pause icon, in the pill too) rather than spinning. Kanban cards are shared, dispatched work on a board every profile sees, so they aren't used for this.
- **Project sessions work in git worktrees, through the plugin.** `POST /v1/runs` takes no working directory, tool list or approval mode (its fields are `input`, `session_id`, `instructions`, `conversation_history`, `previous_response_id`, `model`, `provider`, `model_options`, `author`). What it does have is a tool `task_id` equal to the `session_id` we send, and `tools/terminal_tool.py`'s `register_task_env_overrides(task_id, {"cwd": path})`, which makes `path` the session's cwd for the terminal and file tools (in memory only, keyed under the routed profile scope). A session spans its whole project: `POST sessions/{id}/workspace`, which `sendMessage` posts before every turn (`workspace.ts`), makes a worktree in every git folder of the project on the first post, with Hermes's own `hermes_cli/worktree_ops._setup_worktree` (`<repo>/.worktrees/<slug>`, branch `hermes/<slug>`, locked), registers the primary repo's as the cwd, and answers with an `instructions` line naming every worktree, which `startRun` adds to the run's `instructions` (fixed per session, so the prompt cache holds). Hermes's `-w` and `/worktree` are CLI-only; the gateway's own cwd is `terminal.cwd`. **Directories never reach the UI:** repos are named `user/repo` from each clone's GitHub `origin` (`folder.repo` on the projects route, `name` on a workspace's repos), and the app shows the branch, never a path.
- **Permission modes are Memento's, not Hermes's.** Hermes's `approvals.mode` is global config, and it only prompts for dangerous shell commands (and an SSH-config write), never for ordinary edits. So a project session's mode (`Conversation.mode`, held by the plugin) is: `accept_edits` (the default; Hermes's native behaviour), `auto` (the plugin's `pre_tool_call` hook turns on Hermes's own per-run approval bypass, `tools.approval.enable_session_yolo`, keyed by the run id, which is the approval key `get_current_session_key()` returns inside the hook (hooks run on a copy of the caller's context); the hook switches it off again when the mode isn't Auto, so a mid-run change applies to the next tool call. The bypass skips the prompt only: Hermes checks its hardline blocklist first, so that still blocks. Nothing needs the app open. Switching to Auto resolves, once, any approval a run of the session already waits on, except a guardian's DENY. The app doesn't answer approvals itself, so Auto needs the plugin and the mode menu disables it, with the reason, on a bot without one, where a session left in Auto shows as Accept edits), and `plan` (the plugin's `pre_tool_call` hook blocks `write_file`, `patch`, `execute_code`, `delegate_task`, `open_pull_request` and any `terminal` command that isn't a plain read; the workspace's `instructions` carry the plugin's plan-mode line, which asks for the whole final reply to be the plan in a fixed shape: `# Plan: <title>`, overview, approach, changes, checkpoints that each name their commit message in Conventional Commits form, verification, risks and assumptions; before writing it the agent settles every open choice, asking the user with the `clarify` tool where it can and recording its own decision where it can't, so a plan never leaves a question for the user). An "ask before every edit" mode would equal Accept edits today; the hook's `{"action": "approve"}` return could add one later.
- **Plans are files on the Hermes host.** The plugin's `post_llm_call` hook saves a plan-mode reply that has the `# Plan:` heading as `plans/<branch slug>-<YYYYMMDD-HHMMSS>.md` under the project's primary folder (`$HERMES_HOME/projects/<slug>/plans/` for projects the plugin created), with a YAML front matter (`session`, `branch`, `project`, `created`); every iteration is its own file, and `plans/` goes into the folder's `.git/info/exclude` when the folder is itself a repo. The workspace reports the newest as `plan_file` (`Conversation.planFile`, local only), and approving the plan (in Auto, or in Accept edits, which the plan card offers side by side) sends the agent to that file's checkpoints, each committed on the session branch with the message it names. Hermes doesn't fire `post_llm_call` for an interrupted turn, so no half-written plan is saved.
- **Session states** (`sessionState` in `workspace.ts`): `discarded` (`Conversation.discardedAt`, synced), `resolved` (`Conversation.resolvedAt`, set by the user or by the plugin when the session's pull request merges, synced), `waiting` (an unanswered approval or question here, `waiting_for_approval` from the plugin's `GET runs/live`, or a pending plan), `working` (a reply streaming here, or `running` from `runs/live`), else `idle`, which is where a draft session sits too (`Conversation.draftAt`, set when the user leaves a session they typed in and saves the draft, synced; the text is local in `Conversation.draft`; a session nothing was sent or saved in is deleted when the user leaves it, and the project screen hides any that remain). `runs/live` reads the API server adapter's in-memory `_run_statuses` (`queued | running | waiting_for_approval | stopping` and the terminal ones); Hermes has no run-list endpoint.
- **Theseus is the fourth session mode, run by the vendored `tha-theseus` skill** (`plugin/theseus.py`, the skill in `plugin/skills/tha-theseus/`, pinned by `plugin/skills/VENDORED.json`: repo, commit, `api` and every file's sha256). Never edit the skill here: change it in thehaseebahmed/agent-skills, then `pnpm sync:theseus --ref <tag|sha>` (or `--from <checkout>`); `--check` and `.github/workflows/theseus.yml` fail a PR that edited it by hand, and the same workflow opens a weekly bump PR. `info.theseus` is `{ skill, api, node, ready, reason, reviewers: { llm, model, provider } }`; the mode menu disables Theseus with `reason` when the host has no Node 20, and for a plugin without the field. Theseus is experimental and off by default: the mode menu lists it, marked Experimental (`ExperimentalBadge`, also on the switch and the intro), only while Developer settings and their Theseus switch are on (`useTheseusEnabled`); a session already in Theseus keeps showing it. A Theseus session is project-only, runs in Auto (`follow_auto`) and **keeps its mode**: `POST …/mode` and the workspace post answer 409 for any change into or out of it, and `post_workspace` refuses to start one when `available()` says no.
  - **The run is the skill's, in `.theseus/` in the session's worktree, or for a session over several repos in one folder of its own** (`$HERMES_HOME/memento/theseus/<session>/`, `theseus.session_folder`: the instructions name it and an `init --repos` line listing every worktree, the `pre_tool_call` hook refuses a `theseus init` anywhere else, and removing the session's worktrees deletes it). (`theseus.run_home`: `init` makes it wherever the agent runs it, so the plugin also finds one a few folders below a worktree, like `app/`, or a multi-repo run above that lists it; the newest wins). The agent runs the CLI itself (`instructions` name the script and rules, including `theseus wait --timeout 120` in a loop while the user decides). The plugin never writes the run: `GET sessions/{id}/theseus` answers `{ stage, state, models, unavailable }`, where `state` is `status --json --full` as is and `stage` is derived (`discovery | planning | plan | checkpoints | building | approval | closing | done`, `theseus.stage`); `POST …/theseus` `{ action }` (`confirm_plan`, `revise_plan` + `text`, `approve_checkpoints`, `approve` + `cp`, `request_changes` + `cp` + `text`, `settings`, `close` + `decision`) starts the run's `serve --headless` on a free port when it isn't up and calls the server's own routes, so approvals are recorded as the user's (`source: viewer`) and the agent can't make them. A refusal comes back as the skill's own sentence (409). `GET …/theseus/evidence/{cp}/{file}` serves a screenshot behind the bot's key. `runs/live` adds `waiting: { kind: "theseus", stage }` for plan/checkpoints/approval/closing, read from the run's files without a process; the agent sits in `theseus wait` (a running turn) meanwhile, so the chat shows the card whether or not it is busy.
  - **Reviews are model calls, not subagents.** The `theseus_review` tool (`ctx.llm`, so another model than the builder; `provider`/`model` need `plugins.entries.memento.llm.allow_*_override` in the host config, which `info.theseus.reviewers` reports; `plugin.yaml` declares them as the `llm.model_override` and `llm.provider_override` capabilities, so Hermes asks the user to grant them on install, update and `hermes plugins enable memento`, and a non-interactive install leaves them off) takes `gate` (`coverage`: the planned checkpoints against the confirmed plan, one reviewer on the first code reviewer's model; `review`: `a`/`b`; `visual`: `look`/`behave`), `checkpoint` and `since_review`. The skill won't let the user approve the checkpoints until the coverage review is clean, so the plugin reports the run as `planning` (the app: "Checking the checkpoints") until then. It gathers only the plan and checkpoints (coverage), the diff, the run's architecture docs and the learnings (code) or the evidence captures (visual), sends them with `reviewer.md` as the system prompt, retries once on a reply that isn't a verdict, and records it with `record … --verdict F --isolation model --via <provider/model>` (`coverage --verdict F …` for coverage). The `pre_tool_call` hook blocks a `terminal` call that records a verdict by hand. The user's choice per slot is `POST …/theseus/models` `{ review: [{ provider, model }], visual: [...] }` (two at most; an empty slot is the user's own model), kept in `project_sessions.theseus`. Models only: a whole bot is not a reviewer, since it would need its own session and tools.
  - The app (`lib/theseus.ts`, `components/chat/theseus*.tsx`) reads it every 4s while the chat is open and after each answer, maps the snapshot to `TheseusRun` (`toRun`), and answers through `run.actions`. A request for changes opens a text box; every answer shows the plugin's message when refused. `MOCK_THESEUS=<stage>` starts the mock's runs at a stage and `POST /__mock/theseus { stage }` moves them.
- **A session's pull requests** are found by the plugin on GitHub (`GET sessions/{id}/prs`, one per repo of the session): the branch as `head` on the repo's `origin`, with the host's token when it has one, plus `checks` (`success | failure | pending | null`) from the head commit's check runs and legacy statuses. Hermes tracks no PRs itself. The PR pill is coloured by state (green open, grey draft, purple merged with the `--merged` token, red closed) and orange when the checks fail; it names the repo when the session spans more than one.
- **The agent ships a session's work itself, with the plugin's `open_pull_request` tool** (`plugin/ship.py`); the app never pushes or manages pull requests, it only shows their state. The plugin registers the tool (`ctx.register_tool`, toolset `memento`) and adds it to every agent the API server builds (`ship.wire`, like `todos.wire`), and the workspace's `instructions` tell the agent to call it once the work is done and checked, without asking, and name each repo's pull request template (`ship.template`: `.github/pull_request_template.md` and the other standard places), else Summary, Changes and How to test. The handler finds the session by its `task_id`, commits what's uncommitted in each worktree with `commit_message` (`git add -A`; a host with no git identity commits as the GitHub account's no-reply address), pushes `HEAD` to the branch on `origin` with the host's token as an `http.extraheader` (like the clone), and opens a pull request into the branch the session started from with the GitHub API, or just pushes when one is open; the body ends with the Memento Code footer (`PR_FOOTER` in `sessions.py`). Each repo goes on its own: one failing returns its `error` and the others still ship. Plan mode blocks the tool. Approving a plan asks the agent to open the pull request once its checkpoints are committed.
- **A merged pull request resolves its session, with the app closed too** (`plugin/merges.py`). Every 5 minutes, and whenever `GET sessions/{id}/prs` finds a merged one, the plugin looks up the pull requests of the open project sessions in its chat list (active in the last 30 days); when none is open and one merged, it sets the chat's `resolvedAt` with a newer change clock, so every device gets it on its next sync (the app syncs at once when it sees a merge). `memento.db`'s `merged_prs` remembers which pull requests did it, so a session the user reopens stays open until another merges.
- **Delete and Discard both close a session's work on GitHub** (`POST sessions/{id}/close`, `closeSessionWork` in `workspace.ts`): the plugin removes the worktrees first (keeping those with uncommitted or unpushed work, like `workspace/remove`), then closes each repo's open pull request from the branch and deletes the branch on GitHub when it was pushed. Delete then deletes the chat (`deleteConversation`, a tombstone); Discard sets `Conversation.discardedAt` (synced), which puts the session in the project screen's folded Discarded group with the composer replaced by `DiscardedCard`, and it's never waiting or resolved again. A plugin without the route only has its worktrees removed.
- If you change how the API is used, update `scripts/mock-hermes.mjs` to match.

## Plugin

- `plugin/` installs with `hermes plugins install thehaseebahmed/memento/plugin --enable` (Hermes clones the subdirectory into `~/.hermes/plugins/memento`). `plugin.yaml` holds the version; `dashboard/manifest.json` repeats it, so bump both.
- **The app can't reach dashboard plugin routes.** The dashboard (`hermes dashboard`, :9119) only allows `localhost` origins, and its session token changes on every start. So the routes the app needs go on the API server: `register(ctx)` calls `ctx.register_platform_handler("api_server", factory)`, and Hermes hands the factory the API server's aiohttp app before its router freezes. Those routes get the API server's CORS handling, and they check the key with the adapter's `_check_auth`.
- Routes live under `/api/plugins/memento/` (and again at `/api/plugins/memento/p/<profile>/` for a bot served at `/p/<profile>`: the API server registers its catch-all for `/p/{profile}/...` before plugin routes, so `/p/<profile>/api/plugins/...` is a 404, but any path with `{profile}` still gets its prefix middleware, which validates the profile, scopes the home and takes that profile's key; `mirror_for_profiles` registers the copies behind a guard that 404s unless the middleware scoped the request to that profile, and `runs/live` keeps only the runs the caller's profile and key started; `info` reports `hooks`, false when the profile hasn't loaded the plugin, whose hooks are per profile; `pluginRoot` in `hermes.ts` builds the URL): `info`, `chats` (GET, and POST to merge), `runs/{run_id}/clarify` (POST), `sessions/{id}/context`, `sessions/{id}/todos`, `sessions/{id}/workspace` (GET, POST to create or re-point, and POST `…/remove`; the record carries `plan_file`), `sessions/{id}/mode` (POST), `sessions/{id}/prs`, `sessions/{id}/close` (POST; removes the worktrees, closes the pull requests and deletes the branches on GitHub), `sessions/{id}/attachments` (POST; the raw file as the body, `?name=`, saved as `$HERMES_HOME/memento/attachments/<session>/<name>` without replacing an existing file, answering `{ name, path, size }`), `runs/live`, `events[?since=N][&device=id]`, `push` and `push/remove` (POST), `projects` (GET, and POST to create, which clones in the background), `projects/{id}` (POST to edit its name and description, archive it or pin it), `projects/{id}/repos` and `projects/{id}/repos/remove` (POST; add or remove a repo in the background), `projects/{id}/usage`, `projects/{id}/retry` (POST; a failed clone starts over) and `projects/{id}/remove` (POST; deletes the record, never the folders; for a pending project it stops and wipes the clone), `github`, `github/repos` and `cron/runs?per_job=N[&job_id=]`. The latter reads `cron.executions.list_executions`, the ledger behind the API server's `latest_execution`. `POST sessions/{id}/label` sets a session's `source` to `Memento` (`Memento Code` for a project session), which the Hermes dashboard shows as its label.
- **Chats carry a `Memento` label, and project sessions `Memento Code`, in the Hermes dashboard.** The dashboard shows a session's `source`. `POST /api/sessions` only accepts a fixed list of sources (anything else becomes `api_server`), so the plugin relabels the row after Memento's first turns (`api_server` or `unknown` rows, and the lower-case `memento` older plugins wrote, never another surface's; a project session also upgrades a `Memento` row, and a `Memento Code` row is never downgraded). Hermes's session upsert never overwrites a set source, and a compression child inherits its parent's, so the label sticks. Keyless bots can't be labelled: Memento doesn't know their session ids. Unlike `api_server`, a `Memento` source isn't in Hermes's stale-open auto-close list, so its sessions are never closed and pruned for inactivity.
- **Context use comes from a hook.** `register(ctx)` also adds a `post_api_request` hook (`context.py`), which Hermes fires on every model call with that call's own `usage.prompt_tokens` (input plus cache) and the `context_length` it compresses against. It keeps the latest per session in `memento.db` (API server turns only). `GET sessions/{id}/context` follows compression to the live session with `resolve_resume_session_id` and answers 200 with nulls when it has nothing, never 404 (the app reads a 404 as no plugin).
- **Todo lists come from the transcript.** `GET sessions/{id}/todos` (`todos.py`) follows compression with `resolve_resume_session_id`, loads the session and its ancestors with `get_messages_as_conversation(include_ancestors=True)`, and returns the newest `todo_list` result as `{ revision, todos }`. A result counts only when the nearest earlier assistant message made that call (`tools.todo_tool.is_todo_tool_call`, which knows the `todo` alias and the tool-search bridge), the same check Hermes uses when it restores the list. It answers 200 with nulls when there's none, never 404.
- **Project sessions live in `memento.db`'s `project_sessions` table** (`sessions.py`: `session_id`, `project_id`, `mode`, `plan_pending`, `repos` as JSON `[{ name, repo_root, path, branch }]`, plus `repo_root`, `path`, `branch` for the cwd repo; a row from before `repos` reads as one repo). `POST sessions/{id}/workspace` `{ project_id, task?, mode? }` takes the project's git folders primary first (`hermes_cli.projects_db`; none → 400), makes a worktree in each on the first call (`_setup_worktree` with a fetch, then without; `None` → 502; a later call only makes the ones still missing, all under the first name, so a half-made workspace heals on retry), and on every call calls `register_task_env_overrides` on the loop thread (the key is qualified by the request's profile scope, which `to_thread` doesn't see) and stamps `cwd`, `git_branch` and `git_repo_root` on the Hermes session row when it exists, so Hermes's own grouping and the project's `last_active` see it. `GET` follows `parent_session_id` (read-only from `state.db`) so a compressed session still resolves; it answers 200 with null, never 404. Both answer with `instructions` (`sessions.instructions`) for the run. `POST …/mode` clears `plan_pending` even for the same mode (how the app dismisses a plan everywhere) and answers 404 before the first turn, which the app ignores. `POST …/workspace/remove` removes each tree whose `git status --porcelain` is empty and whose `rev-list HEAD --not --remotes` is 0 (so with no remote nothing is ever removed), after `git worktree unlock`; the others are kept and named (`{ removed: false, kept: [{ name, reason: "dirty" | "unpushed" }] }`), and the row goes only when none is left.
- **A daily cleanup** (`cleanup.py`, started from `_wire_api_server` as an aiohttp `cleanup_ctx`) runs at the server's local midnight. It drops every chat that has had no activity (`updatedAt` never moved past `createdAt`, the app's own test), is a day old, and has no message in Hermes's `state.db` (read-only; anything it can't check is kept): the project session's worktrees through `sessions.remove` (kept ones stay, and so does the chat, until the next run), the Hermes session row when `SessionDB.delete_session` exists, its attachments folder, and a tombstone in the chat list so every device drops its copy. A project session missing from the chat list is judged by its own age. It covers the profile home the plugin was loaded in; profiles served at `/p/<profile>` keep their own homes, which it doesn't reach. A session the user saved as a draft (`draftAt`, synced) is spared.
- **The hooks** (`register(ctx)`, all best effort): `pre_tool_call(tool_name, args, task_id, session_id)` re-registers the cwd when `get_session_cwd(task_id)` is empty (the gateway restarted) and in plan mode returns `{"action": "block", "message"}` for mutating tools (the read-only `terminal` allowlist is in `sessions.py`; redirections and substitutions never pass); `pre_llm_call` clears `plan_pending`; `post_llm_call(session_id, task_id, assistant_response)` saves a plan-mode reply as the plan file (`sessions.save_plan`); `on_session_end` sets `plan_pending` after a completed plan-mode turn; `on_session_start` (once, on a brand-new session's first turn) labels it `Memento Code` when it has a project session record, else `Memento` when its id starts with `memento-` (every chat the app starts), so neither waits for the app's own label call. Both `instructions` (the worktree line, `PR_INSTRUCTIONS` and the repos' templates, plus `PLAN_INSTRUCTIONS` in plan mode) and the plan file's shape live in `sessions.py`; the mock repeats the instructions text, so change both.
- **`clarify.py`** serves Hermes's `clarify` tool on the API server (see **Hermes API**): `wire(adapter)` wraps `_create_agent`, the callback (`Asker`) serves both of Hermes's contracts (the whole normalized list at once, and the stable release's per-question or `questions=` kwarg forms), the wait runs in 1s slices so a stop or the timeout ends it, and `POST runs/{run_id}/clarify` resolves it. `info` reports `clarify: true` when the wiring took. Every Hermes internal it touches is read with `getattr` and a failure only means no questions.
- **`delegation.py` keeps `delegate_task` in the turn that called it.** Hermes runs a top-level delegation in the background, and on a keyed `/v1/runs` session the finished result is saved "for the next client turn" with no model wake (`_resolve_async_wake_sid` in `tools/delegate_tool_dispatch.py`), so the agent never sees it until the user writes again. `wire(adapter)` wraps `_create_agent` and swaps each agent's `_dispatch_delegate_task` for one that calls `delegate_task(background=False)`, so the child's result is the tool's answer; `info` reports `sync_delegation`. A child starts in the parent's current folder, so in a Theseus session the `pre_tool_call` hook moves the session's folder to the run's (`theseus.run_home`) just before a `delegate_task`. Hermes keeps each delegated child as its own `state.db` session (source `subagent`, its parent in `parent_session_id` and in `model_config`'s `_delegate_from`, on main and v2026.9.24), so `GET sessions/{id}/agents` (`delegation.children`) lists a session's children, its compression continuations' included, as `agents: [{ id, goal, model, started_at, ended_at, end_reason, tool_calls, status: running | done | stopped }]` (an open child is `stopped` once its parent has no run in flight; never a 404). In the thread each `delegate_task` call is a card of its own (`AgentCards` in `agent-card.tsx`, matched to its child by the goal its label starts, else by time; `lib/agents.ts`), titled "Sub-Agent: " and its name from the brief ("Builder · CP3" in a Theseus run, else the goal), with the child's last two steps and its status icon beside how long it worked; tapping it opens the child's transcript read-only in a pop-up from `GET /api/sessions/{id}/messages`, which on both versions returns only the child's own rows. Both are read every 4s while the call or the child is working.
- `GET runs/live` maps the adapter's `_run_statuses` to `sessions: { <session_id>: "running" | "waiting_for_approval" }` and `run_ids: { <session_id>: <run_id> }` (0.12; `reattachRun` in `chat.ts` uses it, when a chat opens, to follow a reply left streaming by a connection that gave up or a reload before its run id was saved) with `getattr`, so a Hermes that renames it just reports nothing It also carries `waiting: { <session_id>: { kind: "question", count } | { kind: "approval", command? } | { kind: "plan" }, project? }` (0.16; `sessions.waiting`): a waiting run's `clarify` (questions) or `approval` (its command as the API server hands it to clients), else a project session's `plan_pending`, with the project's name for a project session. The sidebar polls it every 10s while visible (every 5 minutes for a server whose change stream is open, which says when `runs` moves), across the server of every keyed bot that isn't turned off, and lists the project sessions it names that aren't resolved. `GET sessions/{id}/prs` caches each repo's answer for 30s (the app asks after every turn and catch-up); without a GitHub token public repos still answer.
- `dashboard/` is a status tab with a **Link to Memento** card (a code, the app's address and the API server URL; `GET`/`POST link`, `POST link/env` to add the `.env` lines it showed, `POST unlink`), which loads `../link.py` under a stand-in package since Hermes imports `plugin_api.py` on its own. `dist/index.js` is hand-written against `window.__HERMES_PLUGIN_SDK__` (no React import, no bundler), and `plugin_api.py` serves `/api/plugins/memento/status` on the dashboard.
- **The plugin must scan clean under Hermes's install scanner** (`tools/plugin_guard.py`). Any `high` finding makes the verdict `caution`, which asks for confirmation on install and prints a scary report on every update (`medium` ones, like `subprocess.run`, are informational). Its patterns are plain regexes over every file, `dashboard/dist/index.js` included, so code that merely looks like an attack trips them: `env ||` reads as `env |`, dumping the environment. The vendored Theseus skill is scanned too (`host '${x}'` in a message reads as a DNS lookup), so a finding there is fixed in thehaseebahmed/agent-skills and re-vendored.
- Python changes need `hermes gateway restart` (API routes) and a dashboard restart (the tab's backend).
- If you change the plugin's routes, update `app/scripts/mock-hermes.mjs` to match.

## Sync

- Sign-in is Netlify Identity with the GitHub provider (`@netlify/identity`). It only identifies the owner. **Never send plaintext, a key or anything that derives one to the server.** Every document the function stores is sealed with `vault.ts` first, and the associated data names its owner and slot (`memento:<userId>:<doc>`).
- **In the Android app** the page is `https://localhost`, and `@netlify/identity` only talks to its own origin. So `account.ts` hands off to `native-account.ts`, which calls `${VITE_SITE_URL}/.netlify/identity` and the sync function through `CapacitorHttp.request` with a Bearer token. Don't turn on `CapacitorHttp`'s fetch patching: it would buffer Hermes's SSE streams. GoTrue ignores `redirect_to` and returns to the page that started sign-in (its `Referer`, when on the site's host), so sign-in starts from `/auth/native.html`. The function skips its origin check for Bearer requests. Passkeys are off in the app, so it unlocks with the recovery code.
- **Sign-in is compulsory where Identity is available.** `SetupGate` (`src/routes/setup.tsx`) keeps the app behind GitHub sign-in and unlocked sync unless the account is `unavailable` (plain `pnpm dev`, no Identity, no `VITE_SITE_URL`, or offline), and behind the first-run wizard until `Settings.onboarded`: Sign in, Turn on sync, Link your bots (Start chatting once a linked bot answers from this device). The wizard's link step comes back whenever the untouched seed is the only bot (`needsBotSetup`), say after the last bot is removed. An upgrade with configured bots is marked onboarded without it. Where Identity is `unavailable` nothing can link, so the seed bot is set up by hand in Settings.
- **Chat lists live on the Memento plugin** (`plugin/chats.py`, `$HERMES_HOME/memento/memento.db`, under the profile home the API server scopes the request to). `POST /api/plugins/memento/chats` takes this device's `{ id: { at, deleted?, value? } }` record set, keeps the newer record per id in one SQLite transaction, and returns the whole list; `mergeDocs` then picks what to pull. It's plaintext, like the transcripts Hermes already holds. **The plugin is mandatory**: there's no other place for a chat list, and a server that doesn't answer shows as `unreachable` (a flag on the bot's card) until it does.
  - Older versions kept a bot's list in a Netlify `chats/<botId>` document when its server had no plugin. Each bot's first sync with an unlocked vault pulls that document onto the device, and once the plugin has merged it the document is deleted and the bot recorded in `Settings.movedChats`, so it's read once.
  - Plugin chat sync needs no account, so it also runs where Identity is `unavailable`. Two bots on one server share its list; a chat stays with the bot that already has it. Deleting a bot leaves its chats on the plugin.
- Documents are `vault` (the wrapped data keys and the inbox) and `bots` (what the user changed about each bot: name, character, context window). Writes carry the etag they read; a 412 means re-pull, merge and retry.
- Records merge last-write-wins on a change clock: `Profile.updatedAt` and `Conversation.changedAt`. Change synced fields through `updateProfile` / `updateConversation` so the clock moves, and delete through `deleteProfile` / `deleteConversation` so a tombstone is left for sync.
- Message bodies don't sync. They come from Hermes (`history.ts`): with `X-Hermes-Session-Id`, Hermes builds the turn's history from its own session store and ignores the body's, so its transcript holds every device's turns. An open chat catches up (`reconcileHistory`) on open, when its `updatedAt` changes, on focus, when the plugin's stream says its session moved, every 30s while visible (every 5 minutes while its bot's stream is open), and before a send. `Conversation.hermesTip` (local only) lets that start with a one-row probe. Turns streamed on this device are kept (they carry stats and approvals) and matched to their rows by `hermesRowId`.
- **Changes are pushed, not polled, where the plugin is** (`plugin/events.py`, `plugin/stream.py`, `src/lib/live.ts`). Hooks (`pre_llm_call`, `post_api_request`, `pre_tool_call` / `post_tool_call`, `pre_approval_request`, `post_approval_response`, `on_session_end`, API server sessions only) and the plugin's own writes (a chat-list merge that changed something, a session's mode or pending plan, a clarify status, a project clone or repo change) note a content-free row in an `events` table in `memento.db` (`session`, `runs`, `chats`, `projects`; an hour, 2,000 rows, a quarter second per kind and session). `GET events[?since=N]` is SSE per profile: `hello` with the cursor, those rows (a session id walked back through compression parents for `session`), `title` (watched for 90s after a session moves, since Hermes titles in a background thread whose hooks carry no session), `cron` (a fingerprint of the jobs and the ledger's newest runs, every 4s, shared by a profile's streams) and `reset` when the cursor fell out of the table. A stream wakes on an in-process signal and also reads the table every 2s, for hooks run in other processes. It sets its own CORS headers before `prepare()` and pings every 20s for proxies and tunnels (Cloudflare cuts a quiet one at 100s). Events never carry content: the app fetches as it always has.
- **A session that needs the user is pushed to a closed PWA** (`plugin/push.py`, `src/lib/push.ts`, `public/push-sw.js`; the Android app has no Push API in its WebView and gets Firebase messaging through the registry, below). A browser subscription is tied to one VAPID key, so the key is the *device's* (made in the app, kept in `Settings.push`, local only) and goes to each bot's plugin with the subscription: `POST push` `{ device, subscription, vapid_key, subject }` (a public https endpoint only, the plugin posts to it; at most 20 per profile) and `POST push/remove` `{ endpoint }`, kept in `memento.db`'s `push_subscriptions`. The plugin encrypts a `{ kind: approval | question | plan, session_id }` message to the device (RFC 8291 `aes128gcm`, with `cryptography`, which Hermes already depends on) and signs it with the device's key (RFC 8292), sent from `pre_approval_request`, the clarify callback and a pending plan; never what was asked. A 404 or 410 from the push service drops the subscription. A device that holds an `events` stream with its `device` id is skipped, since the app is on screen (a stream whose client vanished without a FIN can keep a device skipped until the server notices). The service worker (imported by the generated one) shows "Needs your approval" and friends tagged by session, silent and closed after 3s when a window is visible (Safari revokes subscriptions that get pushes without a notification), and a tap opens `/s/<session id>`, which finds the chat by `hermesSessionId` (a session that compression moved on isn't matched). **The Android app is pushed through Firebase, by the registry** (`netlify/lib/fcm.ts`, `src/lib/push.ts`): the service account key can't live on every user's Hermes host, so it is the Netlify environment variable `FCM_SERVICE_ACCOUNT` (the registry answers 503 to a push without it), and the plugin asks for the send with `POST registry?route=push` `{ kind, session_id, skip }` (the host token authenticates; `skip` is the devices with the app open; one a second per host; `push.py`'s `_relay`). The app gives the registry its Firebase token with `POST devices&id=<device>` `{ token }` (Identity; at most 10 per account) and `DELETE devices&id=`, through `@capacitor/push-notifications`; the message is a notification message (`notification` + `data`), so Android shows it with the app closed and a tap opens `/s/<session id>` (`PushLinks`). A token Firebase reports unregistered is dropped. `Settings.fcm` is the device's id and switch, which `followEvents` sends like the PWA's. CI writes `android/app/google-services.json` from the secret `FIREBASE_GOOGLE_SERVICES` (the file's JSON, raw or base64); without it the APK builds with push off. iOS only delivers to a PWA added to the Home Screen, and asks for permission only from a tap; the Notifications row is hidden where the browser has no Push API.
- **Live bots** (`live.ts`): the app keeps one `fetch` stream (EventSource can't send the key) per distinct server and key while the page is visible and online, closes it when hidden, resumes from its cursor and treats 50s without a byte as dead. `session` catches up the open chat, `title` re-reads Hermes's title, `chats` runs `syncNow`, `runs` (settled for 300ms, since the status follows the approval hook) refreshes Waiting for input and a project's sessions, `projects` the Code and project screens, `cron` Routines, and a first `hello` or a `reset` does all of it. A live screen keeps its timer at `SAFETY_MS` (5 minutes) as a safety net; a bot whose stream isn't open (an older plugin without the `events` feature, which is asked again after 5 minutes, a proxy that buffers it, a page in the background) polls as it always did.
- **A chat's context use needs the Memento plugin** (`Conversation.liveContext`, local only, read on every catch-up and after each turn): the latest model call's prompt and Hermes's own window, the same on every device. Hermes's API has nothing exact to work it out from (a turn's `prompt_tokens` and the session's `input_tokens` are summed over every call, and message rows' `token_count` is unset), so bots without the plugin aren't tracked: the usage sheet keeps an empty bar under a `Banner` saying the plugin is needed. A hand-set window beats Hermes's, which beats models.dev's.
- **A project session's `projectId`, `resolvedAt` and `discardedAt` sync** through the chat list (`CHAT_FIELDS` in `sync.ts`, applied field by field so a field a newer record dropped, like a reopened session's `resolvedAt`, clears here too; add any new synced chat field there). Its `mode`, `worktree` (branch, repos and the instructions line), `planPending` and `prs` are local copies of what the plugin holds, read on open, on every catch-up and a moment after each turn (`refreshWorkspace`, `refreshPrs`), written with `db.conversations.update` so the clock doesn't move. Before the first turn the mode is only local, and the first workspace post carries it.
- **A chat's todo list needs the Memento plugin too** (`Conversation.todos`, local only, read on every catch-up, at turn end and just after a `todo_list` call). Keyless bots and bots without the plugin show no list, even though a run's live events carry one, so a chat shows the same on every device. A list from the live stream wins for 10s over an older revision from the plugin, whose transcript may not have caught up.

## Linking bots

Bots register themselves instead of being typed in (design: https://claude.ai/code/artifact/2ecc0ba3-e01e-4604-a8d5-bdacd8285650). The app shows a link code; on the host, `hermes memento link <code> --site <app>` (or the Hermes dashboard's Memento tab) claims it and publishes the profile's sealed record; every device turns the record into a bot.

- **The inbox.** The vault carries `inbox: { keyId, publicKey, privateKey }` (`vault.ts`): a P-256 key whose private half is sealed with the data key for `memento:<userId>:inbox`. `setUpSync` makes it, and `ensureInbox` (every sync) adds one to an older vault and keeps this device's non-extractable copy in `db.vault` (`id: "inbox"`). `keyId` is the hex of the first 8 bytes of the public key's SHA-256. **The plugin never gets the recovery code or the data key.**
- **Link codes** are minted by the app: `mk_<codeId>-<secret>-<fingerprint>`, Crockford base32 of 5, 10 and 8 random/derived bytes (8, 16 and 13 characters); the fingerprint is the same 8 bytes as `keyId`. The app posts only `codeId` and the secret's SHA-256 hex (`POST ?route=codes`), so the registry can't forge a code or swap the key: the plugin checks the public key it's handed against the fingerprint. A code lasts 30 minutes and 20 claims; 10 wrong secrets burn it.
- **The registry** (`/.netlify/functions/registry?route=…`, Blobs store `memento-registry`) reads the inbox from the account's `vault` document in `memento-sync`. Hosts send `Authorization: Bearer mh_…` (stored only as a SHA-256 under `tokens/`): `POST claim` (no auth; `{ codeId, secret }` → `{ userId, hostId, token, inbox, origins }`), `GET inbox`, `PUT bots&id=` (`{ keyId, sealed }`), `DELETE bots&id=`, `POST seen` (`{ bots, pluginVersion }` → each bot's `enabled`, or null to publish again, and the current `keyId`) and `DELETE host`. The app (Identity): `POST codes`, `GET bots` (records with `seen`), `PATCH bots&id=` (`{ enabled?, adopts? }`) and `DELETE hosts&id=`. `enabled` and `adopts` belong to the app; a host's publish keeps them.
- **A bot record** is `{ name, profile, baseUrl, apiKey, pluginVersion }`, sealed to the inbox (`openFromInbox`): an ephemeral P-256 key, ECDH, HKDF-SHA256 with the ephemeral point as salt and `memento-inbox-v1` as info, AES-256-GCM, associated data `memento:<userId>:bot:<botId>`. `botId` is the first 16 hex of SHA-256 of `<hostId>:<profile>`.
- **Records become bots** (`syncRegistry` in `registry.ts`, on every sync with an unlocked vault and every 3s while a link screen is open). A bot's id is its `botId`, or the `adopts` id when it took over a bot added by hand with the same server and key (the app sets `adopts` the first time it sees the record, so its chats stay with it on every device). `baseUrl` (plus `/v1`), `apiKey` and `hostId` come from the record; name, character and context window stay the user's and sync through `bots`. `disabled` and `seenAt` are local copies of the registry's. A failed read changes nothing; a bot whose record is gone is deleted (the last one is replaced by a fresh seed). Records sealed to another inbox key are skipped until the host re-seals.
- **Online** is a check-in within 25 minutes (the plugin checks in at gateway start, every 10 minutes and right after linking). **Reachable** is `/health` answering from this device (`useReachable`).
- **Disable** only hides a bot in the app and stops every live check for it (decided): it leaves the bot picker, Recents, Code, Routines, Waiting for input and chat sync, and context, todos and PRs aren't read. The host, its routines and its heartbeat carry on.
- **Remove** revokes the bot's host (`DELETE hosts`), which takes every bot that host linked; the host sees a 401 on its next check-in and stops. Its chats stay on the plugin.
- **Bots added by hand** before linking keep working and stay editable (address and key), flagged Not linked, with a one-time notice (`Settings.linkNoticeSeen`); new ones can't be added. A bot without an API key can't send.

## Conventions

- **The UI renders from Dexie live queries.** Streaming writes into IndexedDB (throttled), and components never hold stream state.
- **History mirrors the sidebar.** Top-level screens (chats, Code, Routines, Settings) open with `root` as the only history entry, so back leaves the app; a deeper screen (a project, a session, a Settings section) is pushed on its parent, goes back with `up`, and sets `setBackGuard` so Android's back does the same. From a top-level screen Android's back shows a "Press back again to exit" toast at the bottom (above anything marked `data-toast-above`, like the composer), and a second press within 2s minimizes the app.
- **Screens and tabs animate in.** `AppShell` slides the main pane in from the right on a push, from the left on back, and fades it on a replace; a `replace` navigation that keeps the same screen passes `state: { quiet: true }`. Tab panels slide in from the side of the tab they were opened from. Everything respects `prefers-reduced-motion`.
- **If you change the schema, bump the Dexie version** in `src/lib/db.ts` and keep existing data loading.
- **Every screen must work at phone (390px) and tablet (≥768px) widths, in light and dark mode.**
- **Pop-ups are sheets on phones and dialogs on bigger screens.** Build them with `Popup` / `PopupContent` (`src/components/popup.tsx`), which picks with `useWide`, rather than a bare `Sheet` or dialog. Side drawers (the sidebar) and the tool-details drawer are not pop-ups.
  - Use the theme tokens. Don't hard-code colours, except for the fixed character palettes in the bots.
  - Respect safe-area insets.
  - Keep touch targets at 44px or larger.
- **Bots:** they are still by default. Only the header (and the empty-state hero) passes `animate`. Animations must respect `prefers-reduced-motion`.
- **Assets must be original or properly licensed.** Never copy third-party characters, mascots or brand assets, even as "inspiration" copies.
- **Never commit secrets.** API keys live only in the user's browser.
- **No explanatory copy.** Don't add UI text that explains how the app works or where its data comes from (footnotes, "from X" captions) unless asked. If it seems needed, ask first.
- Match the surrounding code: Prettier style (no semicolons, 100 columns) and few comments. Comments explain *why*.
