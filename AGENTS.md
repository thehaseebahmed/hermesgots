# AGENTS.md

Guidance for AI coding agents (and humans) working on Gots: a playful, minimal PWA companion for [Hermes Agent](https://github.com/NousResearch/hermes-agent).

## Repository

- `app/` is the web and Android app. Run every command below from `app/`; paths in the rest of this file are relative to it unless they start with `plugin/`.
- `plugin/` is the Gots Hermes plugin (Python, no build step). See **Plugin** below. `plugin/skills/` holds the vendored Theseus skill (JavaScript, run by the host's Node 20+); don't edit it by hand.
- `website/` is the public site for **Gots** (the product name from 2026-10-14, at hermesgots.dev; tagline "Hermes Bots that got your back!", SEO term "Hermes Bots"; the app and plugin show Gots, while the package ids, storage keys, plugin id and repo name still say memento; a text wordmark, with a green G favicon; Astro, static, plain CSS on the app's tokens): the landing page at `/` (a sticky scroll story, design only: its waiting-list form stores nothing yet) and the leaderboard at `/community`: its own Netlify site with the base directory set to `website/`, configured by `website/netlify.toml`. Run its commands (`pnpm dev`, `pnpm build`) from `website/`. Its leaderboard shows sample data until the community function exists (`src/lib/board.ts`).
- `netlify.toml` stays at the root and sets `base = "app"`; it belongs to the app's site.

## Plugin first

**Always read credentials and configuration through Hermes's `agent.credential_pool.get_env_prefer_dotenv(key)`, never `os.environ` directly.** The plugin runs inside a Hermes process that may serve several profiles, so `os.environ` holds the launch profile's values — a bare read is a silent cross-profile leak. The helper resolves the profile's `.env` and the profile-scoped secret, never the process env. The exception is code that intentionally manages or inspects the `.env` file itself (like `link.py` during linking): those operations read and write the file by design and must not go through the helper.

**A user should be able to ask the agent for something, close the app, come back later and find it done.** So work that has to keep going, or stay correct, while the app is closed belongs in the plugin (`plugin/`), which runs on the Hermes host. It doesn't belong in app-side workarounds.

- Before building a feature, check whether it needs the app to be open, following a stream, polling or answering for the agent. If it does, and the plugin (or Hermes itself) could do it, build it in the plugin.
- If a feature can't be done reliably without app-side hacks, say so **up front**, before writing code. Name what breaks: a session that is broken, blocked or stuck waiting when the user comes back. Then propose the plugin route, or not doing it. Only build the app-side version if the user explicitly insists.
- The exceptions are things that wait for the user by design: a plan in plan mode, an approval in Accept edits mode, a clarify question. Pausing for the user there is expected. Losing work or stalling because the app was closed is not.
- The app is the view and the controls. It may make things smoother while it's open (live streaming, faster updates), but nothing should depend on that.

## Commands

```bash
cd app
pnpm install
pnpm dev         # Vite dev server
pnpm dev:netlify # Netlify CLI dev server (Identity + the sync function; needs a linked site)
pnpm mock        # fake Hermes API on :8642 (say "clean up" to trigger an approval)
pnpm e2e <flow>  # browser flows against the mock (list, all, shot <path>, up, down)
pnpm lint        # oxlint
pnpm typecheck   # tsc -b
pnpm build       # typecheck + production build (also generates the service worker)
pnpm build:android # native-mode build (no service worker) synced into android/; set VITE_SITE_URL for sync
pnpm format      # prettier (with the Tailwind class sorter) over src/
pnpm sync:theseus --ref <tag|sha> # vendor the Theseus skill into plugin/skills (--check verifies it)
```

Before you commit, run `pnpm lint`, `pnpm typecheck` and `pnpm build`. All three must pass.

For a change to chats, sessions, polling or sync, also run the browser flows against the mock: `pnpm e2e <flow>` (or `pnpm e2e all`); `pnpm e2e list` names them and `pnpm e2e shot <path>` screenshots a screen. The e2e-testing skill (`.agents/skills/e2e-testing/`) says how to add a flow.

CI (`.github/workflows/tests.yml`) runs the plugin tests (`python3 -m unittest discover -s plugin/tests`, from the repo root) and the three app gates on every pull request and on pushes to `main`, so merged work stays green.

## Git commits

**Always use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/).** The format is:

```
<type>(<optional scope>): <imperative summary, lower case, no trailing period>

<optional body: what changed and why>
```

- Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- Scopes, when they help: `chat`, `settings`, `bots`, `hermes`, `db`, `pwa`, `ui`, `deps`.
- Breaking changes: put `!` after the type or scope (e.g. `feat(db)!: ...`) and add a `BREAKING CHANGE:` footer.
- Keep the summary line to 72 characters or fewer.
- Use one logical change per commit.
- Examples:
  - `feat(chat): show approvals in place of the composer`
  - `fix(hermes): handle CRLF line endings in SSE frames`
  - `docs: document the HTTPS requirement for remote Hermes servers`

PR titles follow the same format. Fill in `.github/pull_request_template.md` for every PR.

## Stack

- Vite, React 19, TypeScript and Tailwind v4.
- React Router (`src/App.tsx`).
- **shadcn/ui on Base UI**, `base-maia` style (`components.json`). Components live in `src/components/ui/`.
  - Base UI uses the `render` prop, not Radix's `asChild`.
  - Use shadcn components wherever one fits before writing your own.
  - Add new ones with `pnpm dlx shadcn@latest add <name>`. Leave the generated files alone unless there's a reason to change them.
- Dexie (IndexedDB) for all app data. `vite-plugin-pwa` handles the manifest and service worker. Deployed on Netlify (`netlify.toml`).
- Capacitor 8 wraps the same build as an Android app (`capacitor.config.ts`, `android/`). `.github/workflows/android.yml` builds a debug APK on pushes to `main` and on PRs into `main` (signed with the release key when the secret is set, so tester builds update over each other), and a push's build also goes to Firebase App Distribution's tester groups once the `FIREBASE_SERVICE_ACCOUNT` secret is set (the same service account key Netlify's registry sends push with; app id from `vars.FIREBASE_APP_ID`, else `google-services.json`). `.github/workflows/android-release.yml` builds the signed release APK when a `v*` tag is pushed, or by hand (`workflow_dispatch`) on a version tag or a branch whose head carries one: the tag is the version name and must equal `app/package.json`'s version, the version code is `major·10⁶ + minor·10⁴ + patch·100` plus 99 for a release or a prerelease's trailing number, and the APK goes on the tag's GitHub release.

## Hermes API

These behaviours were verified against Hermes's `gateway/platforms/api_server*.py`. Check the source again before relying on anything new.

- Turns run on `POST /v1/runs` when `GET /v1/capabilities` reports `run_submission` and `run_events_sse`. A chat completion's agent is interrupted when its SSE client disconnects, which happens whenever a phone sleeps mid-reply. A run keeps going without a client.
  - `GET /v1/runs/{id}/events?last_seq=N` replays the buffered events after `N` and then follows live ones. CORS doesn't allow `Last-Event-ID`, so the cursor goes in the query. Each event carries `seq`, which the reply stores (`runSeq`, along with `runId`) so it can resume after a dropped stream or a reload.
  - The events stream sends a `: keepalive` comment every 10s while the run is quiet, so a stream silent for 30s is treated as dead and reopened from `last_seq`; a connection can die without the read ever failing (a phone that slept, a tunnel that dropped it). Polling reads time out after 15s for the same reason. Coming back to the app after 5s or more away (or back online, or Android's `resume`) drops a run's connection and reads it again at once (`onWake` in `src/lib/wake.ts`), since a phone that slept may not count that time towards either timeout.
  - Hermes keeps the buffer (1000 events) for 5 minutes while nobody is listening. After that the events endpoint returns 404, and `GET /v1/runs/{id}` (whose `output` and `usage` are kept for 24h when the run was started with an `Idempotency-Key`) is polled instead.
  - Events: `message.delta`, `message.interim`, `tool.started` / `tool.completed` (no call id, so a completion matches the oldest running call of that tool; its `error` flag marks the card failed; the transcript doesn't store that, so `toMessages` reads it from the result the way Hermes's `_detect_tool_failure` does (`failureReason` in `src/lib/tools.ts`: a terminal command's non-zero exit, or an `error` field), and the reason shows on the call's row. Its `preview` is cut at 500 characters, so `src/lib/tools.ts` reads a cut JSON envelope as far as it goes, and catching up swaps a cut preview for the transcript's whole result), `reasoning.available` (a whole block, non-streaming providers only), `approval.request`, `replay.truncated` and the terminal `run.completed | failed | cancelled | interrupted`, which carries `output` and `usage` (`input_tokens`, `output_tokens`).
  - Hermes v2026.9.24 (the stable release as of 2026-10-05) sends the events stream without CORS headers and without `seq`, and drops the run's events once that blocked subscriber leaves. In a browser the events request then fails with no response; when `GET /v1/runs/{id}` still answers, the reply falls back to polling at once rather than retrying the stream (`MOCK_BLOCK_RUN_EVENTS=1` mimics it): the final `output` from `GET /v1/runs/{id}`, and, for a keyed session, the turn's progress from the transcript every 3s (`liveTurn` in `history.ts`: its tool calls, the ones without a result row shown running, its reasoning and its text so far). So tool cards show with a few seconds' lag, but no live text and no tok/s. Approval requests travel on that stream too, so while polling, `GET /v1/runs/{id}` is read for `status: waiting_for_approval`, whose `approval` field is the pending `approval.request` (command, description, choices; no plugin needed), and the card is raised from it. A final `output` that replaces the text keeps the tool cards, approval and steers at their recorded offsets when it is already the reply's tail, and otherwise maps them exactly through the common prefix and suffix of the old and new text (an offset inside a rewritten region parks at the rewrite's start, in call order). Hermes fixed it after that release (c7b8e44ffe). A stream without `seq` numbers its tool calls itself, and `reconcileHistory` fills a streamed turn's missing tool calls in from the transcript.
  - A keyed profile sends `session_id` in the body and only the new message as `input`. A keyless one sends the whole transcript.
  - `POST /v1/runs/{id}/stop` stops a run.
  - **Messages sent while a reply runs wait faded at the end of the thread** (`Message.status: "queued"`, `QueuedActions` in `message-item.tsx`: Queued, Remove, and Send now once paused); the next one goes when the reply finishes, and a stop or error pauses the queue. **How a message sent mid-reply goes** is the user's choice: `/steer text` steers it, `/queue text` queues it (both in the `/` menu only while a reply runs, `SEND_COMMANDS` in `slash.ts`), and a plain message does what the **Steer by default** switch says (Settings > Appearance, `Settings.steerByDefault`, off: queue). A plain message steers only when the run takes it (`steerable`) and carries no files; an explicit `/steer` always asks, and `steerText` queues it with a toast when Hermes refuses. **The queue lives on the plugin** (`plugin/outbox.py`, `info` feature `queue`) so it goes with the app closed: `queueMessage` uploads the attachments, builds the whole `POST /v1/runs` body (`runRequest`: model, provider, instructions with the workspace's line, the message) and posts it to `sessions/{id}/queue`, and the local copy is `Message.hostQueued` with the plugin's item id. The plugin's dispatcher (a loop on the API server, woken by `on_session_end` and every second) starts a session's first item with that body once no run of the session (or its compression tip) is active, posting to its own API server on loopback with the key the app's requests came with (the default profile also has the adapter's own key) and the item id as `Idempotency-Key`, so the run is an ordinary one any device can follow; a latest run that was `cancelled`, `failed` or `interrupted` after the user last sent pauses it until `…/queue/{item}/send`, and Hermes refusing the body (a 4xx) marks the item's `error` and holds the queue. `syncQueue` (`refreshQueue`, run before every catch-up, a moment after each turn and every 3s while an open chat's host queue waits) mirrors the items, follows a run the plugin started (`sent`, kept an hour, with `run_status`) live as a streaming reply when it's still going, and otherwise leaves it to the transcript. Without the feature (or when the post fails) the message waits on the device as before, and only goes with the app open. **Steer is Hermes's own `POST /v1/runs/{id}/steer`** `{ input }` (capability `run_steer`; on v2026.9.24 and main): the agent gets the text as a user row after its current tool calls, without stopping, so it reaches the agent with the app closed. Hermes refuses it (409) unless the run is `running`, and takes text only, so a queued message with attachments can't steer. The transcript keeps it as a `role: user` row with `display_kind: "steer"` wrapped in Hermes's `[OUT-OF-BAND USER MESSAGE …]` marker; it's part of the turn, not a new one (`isTurnStart`), and `toMessages` puts it on the reply as `Message.steers`, shown as a user bubble marked Steered where it was sent. A steer that arrives while the agent writes its last reply is never read: Hermes hands it back as `pending_steer` on the terminal event and on `GET /v1/runs/{id}`, and it goes first as the next turn (Hermes's messaging gateway does the same): the plugin queues it itself (`s_<run id>`, from the session's last queued body), and without the plugin the app takes it off the reply and queues it. A queued item steers through the plugin (`…/queue/{item}/steer`, which forwards the app's own key to Hermes's route), so its leftover comes back to the plugin too. A hard stop drops an unread steer.
- Older servers fall back to `POST /v1/chat/completions` with `stream: true`, whose stream interleaves named SSE events with the normal chunks: `hermes.tool.progress`, `hermes.status` and `approval.request`.
- Approvals are answered with `POST /v1/runs/{completion_id}/approval` and a body of `{ choice }`. **An approval that stopped waiting leaves the composer's slot.** Hermes's route puts `approval.responded` `{ choice }` on the run's stream and sets the status back to `running`; one that times out, is withdrawn or that the plugin answers for Auto does neither (the status keeps the old request until the run moves on), so the plugin's `post_approval_response` hook (`plugin/approvals.py`, 0.40) does both, with `choice` `timeout`, `cancelled` or `notify_failed`, unless another request of the run still waits. The app settles the card on that event (a choice it doesn't know reads as `expired`, "No longer waiting for an answer"), expires it when a status read begun after the card went up no longer waits, tells requests apart by Hermes's `timestamp` (the status and the event share it), so a stale one on the status is never raised again, and treats an answer refused with the error code `approval_not_pending`, `approval_not_active` or `run_not_found` (`HermesError.code`, from the error envelope; never the message) as the approval missed. `POST /__mock/approvals { outcome: "timeout" | "lost" }` ends the mock's pending approvals with or without the plugin (`pnpm e2e approval-missed`).
- `X-Hermes-Session-Id` continues a session. Hermes only accepts it when `API_SERVER_KEY` is set.
- Hermes's CORS setup does not expose response headers, which is why the client mints its own session ids.
- **The agent asks the user questions with Hermes's `clarify` tool, which needs the Gots plugin.** The API server's own toolset (`hermes-api-server` in `toolsets.py`) leaves `clarify` out and its agents get no `clarify_callback`, so without the plugin the agent can't ask on this surface. The plugin (`plugin/clarify.py`) wraps the adapter's `_create_agent` to add the tool's definition and a callback to every agent it builds; a call puts `clarify.request` on the run's stream (`{ clarify_id, questions: [{ id, question, choices?, multi_select? }] }`, choices bare, the first one recommended) and the same object as `clarify` on `GET /v1/runs/{id}` while the run waits as `waiting_for_approval` (so `runs/live` and the project screen read it as waiting, and a client that can only poll still sees it); the app shows the questions in place of the composer (`QuestionCard`, `Message.clarify`; one question is shown as is, two or more are pages of one form, and a reply keeps only its latest question), posts the answers to the plugin's `POST runs/{run_id}/clarify` (`{ clarify_id, answers: { q0: "text" | ["several"] | null }, outcome: "submitted" | "cancelled" }`), and the run carries `clarify.responded` (with the answers, so another device or a replay resolves the form) before the agent carries on in the same turn. Once answered, a question is the `clarify` tool call's card in the thread (`ClarifyCard` in `session-cards.tsx`, in every chat) and reads from the call's result, Hermes's `{ responses: [{ question, choices_offered, status?, user_response }], outcome? }` (the stable server's persisted rows also use `responses`, with `timed_out: true` for an unanswered timeout): the app writes that result itself when the user answers, since the run stream's preview is cut at 500 characters. Transcript polling preserves that settled result by call id until a nonempty server result arrives; it never substitutes an answer from a different call. A device that loads the transcript reads the persisted `responses` without needing the local question form. Answered responses take precedence over the outcome; a submitted empty form is `Skipped`, cancelled or undelivered questions are `Not answered`, and a timeout is `No answer`. Waiting for an answer is the by-design pause the **Plugin first** rule names; Auto's approval bypass doesn't touch it. No mode answers for the user, `auto` included; an unanswered question ends as `timed_out` after Hermes's `agent.clarify_timeout` (an hour by default), a stopped run as `cancelled`, and a chat completion (no run stream) as `undelivered`, so the agent asks in prose. In plan mode the instructions ask the agent to settle every open choice this way before it writes the plan.
- **Attachments: images go inline, files through the plugin.** Both `/v1/runs` and chat completions take the OpenAI vision shape for a user message's `content` (`[{ type: "text" }, { type: "image_url", image_url: { url } }]`; checked at v2026.9.24 and main). Chat completions validate it (`_normalize_multimodal_content`: `http(s)` or `data:image/…` URLs only, and `file` / `input_file` parts are refused with `unsupported_content_type`); `/v1/runs` passes the last `input` item's `content` to the agent as is, so the app always sends the canonical `image_url` shape, only on the newest message (Hermes `str()`s `conversation_history` entries). Hermes stores such a message as text with each image replaced by a `[screenshot]` line (`_durable_content`), so a keyed session's later turns no longer see the image, and the request cap is 10 MB (`MAX_REQUEST_BYTES`). So the app scales images to a 1600px long edge (`attachments.ts`), and when the bot has the plugin it first saves every attachment on the host (`POST sessions/{id}/attachments`); the message then carries an `<attachment name="…" type="…" path="…" />` line per attachment (the path only once saved), followed by the image itself for a photo, so the agent can open it with its file or vision tools later. Files need the plugin, so **Files** is disabled without it; a photo whose upload fails still goes inline. Camera and Photos are disabled when models.dev says the model doesn't take images (`modalities.input` without `image`, stored as `Profile.imageInput` next to the context window; unknown counts as yes), and an image picked through Files then goes as a file. Files aren't gated on the model's own `attachment` flag: the agent opens them with its tools, which any model can do. `toMessages` splits those lines (and each photo's `[screenshot]`) back off a transcript row, which keeps the text matching the device's own copy; the photo itself lives only on the device that sent it (`Message.attachments[].blob`), and other devices show its name.
- **Images the agent returns show in the thread.** A reply names an image with a `MEDIA:<path>` tag (the shape Hermes's `MEDIA_TAG_CLEANUP_RE` strips for its messaging adapters, which send the file as a photo). The run events, run output and transcript rows keep that tag as text; only the chat-completions routes resolve it (`_resolve_media_to_data_urls`, to `![image](data:…)`). The app renders both through `MediaImage` (`src/components/chat/media-image.tsx`): a markdown image (including those data URLs, which react-markdown's own `urlTransform` would drop), and every tag in an assistant reply, read from the plugin's `GET /api/plugins/memento/media?path=…` (the `media` feature in `info`), which serves the file behind the bot's key using Hermes's own `validate_media_delivery_path`. `mediaImages` (`src/lib/media-tags.ts`) ports the tag shape and skips fenced code blocks, so an example tag stays text; each image in a reply takes one cell of the same grid — a lone image, the tags sent together (only whitespace between, which put two, or three from five, side by side), or an image written into the reply's own Markdown — sized by breakpoint, and an image still being read holds that cell with a `Skeleton` (`src/components/ui/skeleton.tsx`) until it lands, so nothing moves under it (the only smaller one is a photo you attached yourself: the square tile in `attachments.tsx`); tapping an image opens it in the platform's own viewer on a phone (the Android app's system photo viewer through `OpenImage`, a browser tab) or a pop-up on tablet and desktop. Only the raster extensions the plugin serves (`.png .jpg .jpeg .gif .webp .bmp`, `media.MEDIA_TYPES`, under `media.MAX_BYTES` = 25 MB) become images; any other tag, and one on a bot without the plugin or with a plugin from before the `media` feature (checked like the todo list, retried every 5 minutes), stays visible as text.
- `GET /v1/skills` lists skills for the `/` menu. The code returns `{ object: "list", data }` (the docs show a bare array), and on some versions it returns a 500, so the menu must work without it.

- **Profiles are bots.** Hermes has no endpoint that lists profiles, so each profile's Gots plugin registers it (see **Linking bots**) and the app keeps it as a `profiles` row with its URL, key and model. Secondary profiles are served at `/p/<profile>/...` (`gateway.multiplex_profiles`; newer Hermes always multiplexes unless a profile is `gateway.standalone`). Each profile has its own `API_SERVER_KEY`, and a named profile advertises its name as the `/v1/models` id. The mock serves the same `/p/<profile>/` prefix.

Gots doesn't use it for context; the plugin records each call instead (see **Plugin**). No endpoint reports the model's context window, so each bot stores its own.
- Hermes auto-titles API sessions (an instant slice of the opener, then a background model call that can land after the stream ends, and again on turns 2–3 for a placeholder like "Friendly greeting"). `GET /api/sessions/{id}` (server root) returns `{ session: { title } }` but not where the title came from. Gots polls it after the first three turns, which needs the session id and so an API key. CORS doesn't allow `PATCH`, so renames stay local (`titleEdited`) and Hermes's title never replaces them.
- `GET /api/model/options` (server root, not `/v1`) returns the configured `model` and `provider` behind a profile, and `providers`, Hermes's own model picker inventory: `[{ slug, name, is_current, authenticated?, models: [id] }]`, where a row with `authenticated: false` or no models is a provider without credentials. Older versions don't have it, so treat a failure as unknown.
- **A chat can run on another of the host's models.** The composer's model pill opens a list of those providers' models (`getModelInfo`, cached a minute per server by `useModelInfo` in `lib/model-info.ts`), and the pick is `Conversation.modelChoice` (`{ provider, model }`, synced through the chat list; a new chat holds it until its first message creates the chat). It changes that chat only. A turn runs the chat's pick, else the bot's default (`Profile.modelChoice`, synced through `bots`), else the host's model. A turn with no pick sends no `model` on `/v1/runs`: a profile served at `/p/<profile>` advertises its name on `/v1/models`, but the run handler only treats the launch profile's name (or `hermes-agent`) as the virtual model, so sending it fails with `HTTP 400: <profile> is not a valid model ID` (read in `_request_agent_overrides` and `_handle_models` on the hermes-agent fork's main, 2026-10-09). The picker lists the bot's last three picks first as `provider/model` (`Profile.recentModels`, newest first, from both pickers through `rememberModel`, synced with the bot; one the host no longer offers is left out), then the providers (A to Z, each with its model count), each opening its own models (A to Z; a host with one provider lists its models at once); a search looks through every provider's. The list has a fixed height, so it doesn't resize between views. A pick is sent as the turn's `model` and `provider`. `/v1/runs` honours both on every request (`_request_agent_overrides`; checked at v2026.9.24), and chat completions honour a bare model only with `direct_model_requests` but an explicit `provider` always. It needs neither the plugin nor `allow_model_override`, which gates only the plugin's own `ctx.llm` calls (Theseus's reviewers). **The bot editor's Default model is the host's main model** (`setDefaultModel` in `lib/model-info.ts`): Hermes's only route for it is the dashboard's `POST /api/model/set`, which the app can't reach, so the plugin's `POST model` `{ provider, model }` (`plugin/host_model.py`, `info` feature `host_model`) runs Hermes's own `switch_model` and `persist_model_selection`, as a messaging `/model --global` does: Hermes checks the pick (a refusal is a 400 with its reason, shown as a toast), only the `model.*` keys it changes are written, comments stay, and the API server reads `config.yaml` for every agent it builds, so every surface of the profile (Telegram, cron, new CLI sessions, the dashboard) runs it from the next turn. The bot then keeps no `modelChoice` of its own, so a change made in the dashboard shows here too. The field reads `provider/model`, and until the host answers it shows, greyed out, the model this device last read (`Profile.hostModel`, local only). Without the plugin feature (or reachable plugin) the pick stays the bot's own `modelChoice`, as before. Hermes locks `config.yaml` only within a process, so a dashboard save at the same moment can win over it.
- The context window is looked up in [models.dev](https://models.dev/api.json) (`limit.context`) by that `provider`/`model` (`src/lib/models.ts`). The bot remembers which model it was for and resets it when the model changes; if models.dev doesn't list the model, the window is unknown. Nothing sets a window by hand: the sheet reads the window the bot holds for the model, then Hermes's for the call that ran it, then models.dev's.
- Cron jobs are called **Routines** in the UI (`/routines`) and `cron` in code. `GET /api/jobs?include_disabled=true` (server root) returns `{ jobs }`. Each job carries `last_run_at`, `last_status` and `failure_streak`. Its `schedule` is Hermes's parsed `{ kind: interval | cron | once, minutes | expr | run_at, display }`; `src/lib/schedule.ts` puts it in words ("Weekdays at 9:30 AM", "Every 15 minutes") and falls back to `display` for shapes it doesn't know. Cron times are the host's clock, so when the next run's offset differs from the device's, the host's offset follows ("(UTC+5)"). `POST /api/jobs/{id}/pause | resume | run` control a job. A 501 means cron isn't available.
- The API server has **no run-history endpoint** (the dashboard's `/api/cron/jobs/{id}/runs` is localhost-only), so **run history needs the Gots plugin** (`plugin/`). `GET /api/plugins/memento/cron/runs?per_job=24` returns `{ jobs: { <jobId>: [run, ...] } }`, newest first, straight from Hermes's execution ledger (`status` `claimed | running | completed | failed | unknown`, plus `delivery_outcome`; a `completed` run whose delivery `failed` counts as failed). Without the plugin the route doesn't exist, and Hermes's 404 for an unknown route skips its CORS middleware, so the browser blocks it and `fetch` fails with no status. `syncCron` treats a failed plugin call as a missing plugin when `/api/jobs` on the same server succeeded, and the Routines screen shows the install commands instead. Runs aren't stored on the device.
- **Hermes Projects** (`hermes project create`, per profile in `$HERMES_HOME/projects.db`) have no API server route, so the Code screen (`/code`) reads them from the plugin's `GET /api/plugins/memento/projects`: `{ projects: [{ id, name, description, created_at, last_active, folders: [{ path, label, is_primary, git, repo, branch }] }] }`, where `branch` (0.17) is the one a session's worktree would start from: `origin/HEAD`'s branch, else what's checked out. The Code screen's rows and the project screen name the repos, and a session not started yet shows them with that branch. Hermes stores no last-worked-on time, so `last_active` is the newest session whose `cwd` sits in one of the project's folders (the innermost folder wins, like the desktop app's grouping), and null when none has. The screen merges every bot's list, newest first; bots on the same server share one list.
- **New projects are created, and their GitHub repos cloned, on the Hermes host**, with the host's GitHub account: `GITHUB_TOKEN`, then `GH_TOKEN` (process env, then `$HERMES_HOME/.env`), then `gh auth token`, the order Hermes's own GitHub calls use. The token never reaches the app. `GET /api/plugins/memento/github` reports `{ connected, login? }`, `github/repos` lists the account's 100 most recently pushed repos, and `POST projects` takes `{ name, description?, repos: ["owner/name"] }`. It makes `$HERMES_HOME/projects/<slug>/` (the profile's home, so profiles stay apart; the slug is the one `projects.db` gets), clones each repo into it over HTTPS (the token goes in an `http.extraheader`, so it isn't saved in `.git/config`), and creates the project with that folder as its primary and each clone as a folder. A repo in two projects gets two clones. Without an account, public repos still clone by name.
- **Creating a project is asynchronous** (`plugin/clones.py`), so it carries on with the app closed. `POST projects` validates, makes the folder, records the project in `memento.db`'s `project_clones` table and answers **202** with it at once; a daemon thread then clones each repo. Until the last clone is in, the project is `pending-<slug>`, **not in `projects.db`**: a project there is always whole, so a session can never get worktrees in only some of its repos, and Hermes's own dashboard never sees a half-made one. `GET projects` lists it after the real ones with `status: "cloning" | "failed"` (real projects carry `ready`; the app reads an absent `status` as ready, for an older plugin), `error`, and each folder's `status` (`queued | cloning | done | failed`). The last clone creates the real project (new id) and drops the row. A failed clone removes the folder and keeps the row with its error until `POST projects/{id}/retry` (starts over) or `…/remove` (also cancels a running clone: `github.clone` takes a cancel event). A restart mid-clone clones again from scratch (`clones.resume`, at startup for the default profile and on the first `GET projects` for any other). A pending project can't be edited (409) or opened; the Code screen shows it with Cloning n of m, or the error with Retry and Remove, and polls every 3s while one is cloning. `info` reports `projects_async`.
- **A ready project's repos are added and removed asynchronously too** (`plugin/repos.py`, `memento.db`'s `project_repos`). `POST projects/{id}/repos` `{ repo }` answers 202 and clones on a daemon thread into `$HERMES_HOME/projects/<slug>/`; the repo joins `projects.db` (`add_folder`) only once the clone is in. `POST …/repos/remove` `{ repo }` takes it out of `projects.db` at once (`remove_folder`) and deletes the clone on a thread, only when it's one the plugin made (a folder of a project folder under `$HERMES_HOME/projects/`) and no other project uses it; for a repo still being added it cancels the clone. `GET projects` lists such repos among the folders with `status: "cloning" | "failed" | "removing"` (and `error`), and a restart picks them up again (`repos.resume`). **While a repo is being added, no new session can start** in the project: the project screen shows a note in place of New session, and `POST sessions/{id}/workspace` answers 409 for a session with no record yet. **A session that works in a removed repo is read-only**: the workspace post answers 409 with the reason, and both workspace answers carry it as `blocked` (`Conversation.blocked`, local), which the chat shows in place of the composer (`BlockedCard`). An archived project blocks its sessions the same way.
- **Projects can be pinned, archived and measured.** `POST projects/{id}` also takes `archived` (Hermes's own `archive_project` / `restore_project`) and `pinned` (the plugin's `project_pins`, since Hermes has no pin). `GET projects` lists archived projects too, with `archived` and `pinned_at`; the Code screen puts pinned ones first and archived ones in a folded group. `GET projects/{id}/usage` sums `input_tokens`, `output_tokens`, the cache counts and `actual_cost_usd` (else `estimated_cost_usd`) over the `state.db` sessions whose `cwd` (or their root's) sits in one of the project's folders (read-only), folding compression children into their root as one session, and lists each one as `threads: [{ id, title, started_at, last_active, models: [{ model, <the four counts>, cost_usd }] }]` (0.21). A session's `model` column is overwritten on a mid-session switch, so the split comes from `session_model_usage` (each call under the model that ran it, auxiliary calls included) and whatever those rows don't cover is counted under the session's own model; the totals stay the session rows', so the split can't disagree with them. An older Hermes without that table falls back to one model per session. The Usage view (`project-usage.tsx`) shows the totals, the split by kind and each session's share, and its **Est. cost** comes from `src/lib/pricing.ts`: Anthropic's first-party prices for a Claude model id (cache writes as Hermes's default 5-minute writes; Bedrock and Vertex sessions are priced the same), Hermes's own cost for any other model, and a `+` when some usage had neither. Update the price table when Anthropic's prices change.
- **Dictation is the host's own faster-whisper, through the plugin** (`plugin/dictation.py`, `src/lib/dictation.ts`; decided with Haseeb 2026-10-12, plan: https://claude.ai/code/artifact/059a9f63-6ba4-42c5-b145-f52b5fd684b2). Hermes's transcription routes (`POST /api/audio/transcribe`, `/api/audio/stt-lease`) live on the dashboard, whose CORS allows only `localhost`, and the API server reports `audio_api: false`, so the plugin serves `POST dictation` and `POST dictation/warm` (see **Plugin**). The app records mono Opus at 24 kbps with `MediaRecorder` (`audio/webm` in Chrome and the Android WebView, `audio/mp4` in Safari; faster-whisper decodes either with its bundled PyAV), and warms the model when the mic opens. Hermes streams partial text only for its cloud providers (`tools/transcription_streaming.py`), never for the local model, so **the recording is cut at the user's pauses** and each piece is sent while they carry on: a level meter on the same stream (a `setInterval`, so it runs without animation too) cuts a piece of 6s or more at 700ms of quiet (one of 25s or more at 350ms), quiet being under a few times the room's own noise floor, by starting a new `MediaRecorder` on the stream before stopping the old one, so every piece is a whole file and nothing between them is lost. Pieces are transcribed one at a time in order, each with the text before it as `context` (plugin 0.35; Whisper's prompt is what was just said), so on Stop only the last piece is left to wait for; a piece that fails is tried again with the next one, and on Stop. **A recording is kept on the device until its text is in** (`db.dictations`, under the composer's draft key, its pieces and their text so far, the open piece saved every 2s), so a reload, leaving the chat mid-recording or a failed host keeps it: the composer shows it again with Retry and Discard. **The mic works only when the bot's `info.dictation.ready` is true** (read on mount and every 5 minutes, again after a failed clip, and kept when a later read fails, so it doesn't flicker): it's greyed out and inert while the host is first asked, and greyed out with a pop-over saying why when the host says no (no plugin, an older one, faster-whisper missing or `stt.enabled: false`, with the plugin's reason) or couldn't be asked (a tap asks again). There is no Web Speech fallback. A tap toggles recording (the voice bar takes the mic's place under the finger, so its buttons only answer a press that began on the bar, or the keyboard); a press held 400ms or more is push-to-talk (letting go finishes, letting go 80px away cancels). The text goes in at the cursor, or Send sends it; a recording under 300ms is dropped. Clips stop at 10 minutes. In the Android app the WebView's `getUserMedia` needs `RECORD_AUDIO` and `MODIFY_AUDIO_SETTINGS` in the manifest (Capacitor's `BridgeWebChromeClient` asks for both). `MOCK_DICTATION=off|fail` in the mock hides the mic or fails every clip.
- `GET /api/sessions/{id}/messages?order=latest&limit&offset` (server root) pages a session's transcript back from the newest row, but returns each page oldest first. Rows carry `id` (increasing), `role`, `content`, `tool_calls`, `tool_call_id`, `tool_name`, `timestamp` (Unix seconds), `reasoning` and `display_kind` (`hidden` rows are compaction scaffolding; skip them). Gots uses it to fill in chats synced from another device. A `role: user` row starting `[System:` is a note Hermes wrote to keep the turn going (a reply cut off by the network or the output limit, a fragment it asks the model to send again, a verification nudge); it's never shown and doesn't start a turn (`isNotice` in `history.ts`). The reply's text before it, back to the last tool call, is joined with what follows the way Hermes joins them for the run's `output` when the note asks to continue "where you left off" (unless the model started over), and replaced otherwise. Live, the stream never carries the note but streams every attempt, so a completed run's `output` replaces the text streamed since the last tool call when they differ (`settleFinalText` in `chat.ts`).
- **The agent's todo list is Hermes's `todo_list` tool** (`tools/todo_tool.py`), not Kanban: one list per session of `{ id, content, status: pending | in_progress | completed | cancelled, parent? }`, where each call returns the whole list with a `revision` and is stored as a `tool` row (written after every tool round, so mid-turn too). - **Permission modes are Gots's, not Hermes's.** Hermes's `approvals.mode` is global config, and it only prompts for dangerous shell commands (and an SSH-config write), never for ordinary edits. An "ask before every edit" mode would equal Accept edits today; the hook's `{"action": "approve"}` return could add one later.

Hermes doesn't fire `post_llm_call` for an interrupted turn, so no half-written plan is saved.
- **Session states** (`sessionState` in `workspace.ts`): `discarded` (`Conversation.discardedAt`, synced), `resolved` (`Conversation.resolvedAt`, set by the user or by the plugin when the session's pull request merges, synced), `waiting` (an unanswered approval or question here, `waiting_for_approval` from the plugin's `GET runs/live`, or a pending plan), `working` (a reply streaming here, or `running` from `runs/live`), else `idle`, which is where a draft session sits too (`Conversation.draftAt`, set when the user leaves a session they typed in and saves the draft, synced; the text is the session's composer draft, below; a session nothing was sent or saved in is deleted when the user leaves it, and the project screen hides any that remain). The screenshots, images, charts, reports and markdown a session makes for the user belong under the session's library folder — `<project's primary folder>/files/<worktree slug>/`, computed when the worktree is made and kept on the session row as `files_dir` (schema v15) — not in the worktree, so they stay out of the branch's diff and the app's Library tab can link them later. The workspace's `instructions` name the folder (`sessions._files_line`, right after the worktree line) and tell the agent to file each generated file with the tool instead; the handler finds the session by its `task_id` like `ship.handle` does, resolves a relative path against the session's cwd, and files the file at `files_dir/<folder>/<name>` — the `folder` argument is required, one level. **Folders and file names are kebab-case slugs** (`^[a-z0-9]+(-[a-z0-9]+)*$`; a file name is a slug plus one extension, `dashboard-light.png`), and folders are named after the flow or change the files belong to — `library-tab` for work on the library tab, `library-tab-tree-view` for a follow-up change to it — never the file type, so one project's library reads as a tree of what was done; the tool's description and the `instructions` teach this. A name that isn't a slug is an error, never rewritten, carrying the rule and the nearest correction (`'Library Tab' is not a slug (kebab-case: …); name the folder after the flow … Call again with folder 'library-tab'.`); a file name that isn't one tells the agent to rename it on disk first. A file of that name already in the folder is an error naming the file and the folder — the agent renames it and calls again, and nothing is renamed for it.

A result counts only when the nearest earlier assistant message made that call (`tools.todo_tool.is_todo_tool_call`, which knows the `todo` alias and the tool-search bridge), the same check Hermes uses when it restores the list. It answers 200 with nulls when there's none, never 404.
- **Project sessions live in `memento.db`'s `project_sessions` table** (`sessions.py`: `session_id`, `project_id`, `mode`, `plan_pending`, `repos` as JSON `[{ name, repo_root, path, branch }]`, `files_dir`, plus `repo_root`, `path`, `branch` for the cwd repo; a row from before `repos` reads as one repo). `POST sessions/{id}/workspace` `{ project_id, task?, mode? }` takes the project's git folders primary first (`hermes_cli.projects_db`; none → 400), makes a worktree in each on the first call (`_setup_worktree` with a fetch, then without; `None` → 502; a later call only makes the ones still missing, all under the first name, so a half-made workspace heals on retry), and on every call calls `register_task_env_overrides` on the loop thread (the key is qualified by the request's profile scope, which `to_thread` doesn't see) and stamps `cwd`, `git_branch` and `git_repo_root` on the Hermes session row when it exists, so Hermes's own grouping and the project's `last_active` see it. `GET` follows `parent_session_id` (read-only from `state.db`) so a compressed session still resolves; it answers 200 with null, never 404. Both answer with `instructions` (`sessions.instructions`) for the run. `POST …/mode` clears `plan_pending` even for the same mode (how the app dismisses a plan everywhere) and answers 404 before the first turn, which the app ignores. `POST …/workspace/remove` removes each tree whose `git status --porcelain` is empty and whose `rev-list HEAD --not --remotes` is 0 (so with no remote nothing is ever removed), after `git worktree unlock`; the others are kept and named (`{ removed: false, kept: [{ name, reason: "dirty" | "unpushed" }] }`), and the row goes only when none is left.
- **A daily cleanup** (`cleanup.py`, started from `_wire_api_server` as an aiohttp `cleanup_ctx`) runs at the server's local midnight. It drops every chat that has had no activity (`updatedAt` never moved past `createdAt`, the app's own test), is a day old, and has no message in Hermes's `state.db` (read-only; anything it can't check is kept): the project session's worktrees through `sessions.remove` (kept ones stay, and so does the chat, until the next run), the Hermes session row when `SessionDB.delete_session` exists, its attachments folder, and a tombstone in the chat list so every device drops its copy. A project session missing from the chat list is judged by its own age. It covers the profile home the plugin was loaded in; profiles served at `/p/<profile>` keep their own homes, which it doesn't reach. A session the user saved as a draft (`draftAt`, synced) is spared.
- **The hooks** (`register(ctx)`, all best effort): `pre_tool_call(tool_name, args, task_id, session_id)` re-registers the cwd when `get_session_cwd(task_id)` is empty (the gateway restarted) and in plan mode returns `{"action": "block", "message"}` for mutating tools (the read-only `terminal` allowlist is in `sessions.py`; redirections and substitutions never pass); `pre_llm_call` clears `plan_pending`; `post_llm_call(session_id, task_id, assistant_response)` saves a plan-mode reply as the plan file (`sessions.save_plan`); `on_session_end` sets `plan_pending` after a completed plan-mode turn; `on_session_start` (once, on a brand-new session's first turn) labels it `Gots Code` when it has a project session record, else `Gots` when its id starts with `memento-` (every chat the app starts), so neither waits for the app's own label call. Both `instructions` (the worktree line, `PR_INSTRUCTIONS` and the repos' templates, plus `PLAN_INSTRUCTIONS` in plan mode and the library line, `_files_line`, naming `files_dir`) and the plan file's shape live in `sessions.py`; the mock repeats the instructions text, so change both.
- **`clarify.py`** serves Hermes's `clarify` tool on the API server (see **Hermes API**): `wire(adapter)` wraps `_create_agent`, the callback (`Asker`) serves both of Hermes's contracts (the whole normalized list at once, and the stable release's per-question or `questions=` kwarg forms), the wait runs in 1s slices so a stop or the timeout ends it, and `POST runs/{run_id}/clarify` resolves it. `info` reports `clarify: true` when the wiring took. Every Hermes internal it touches is read with `getattr` and a failure only means no questions.
- **`delegation.py` keeps `delegate_task` in the turn that called it.** Hermes runs a top-level delegation in the background, and on a keyed `/v1/runs` session the finished result is saved "for the next client turn" with no model wake (`_resolve_async_wake_sid` in `tools/delegate_tool_dispatch.py`), so the agent never sees it until the user writes again. `wire(adapter)` wraps `_create_agent` and swaps each agent's `_dispatch_delegate_task` for one that calls `delegate_task(background=False)`, so the child's result is the tool's answer; `info` reports `sync_delegation`. A child starts in the parent's current folder, so in a Theseus session the `pre_tool_call` hook moves the session's folder to the run's (`theseus.run_home`) just before a `delegate_task`. Hermes keeps each delegated child as its own `state.db` session (source `subagent`, its parent in `parent_session_id` and in `model_config`'s `_delegate_from`, on main and v2026.9.24), so `GET sessions/{id}/agents` (`delegation.children`) lists a session's children, its compression continuations' included, as `agents: [{ id, goal, model, started_at, ended_at, end_reason, tool_calls, status: running | done | stopped }]` (an open child is `stopped` once its parent has no run in flight; never a 404). In the thread each `delegate_task` call is a card of its own (`AgentCards` in `agent-card.tsx`, matched to its child by the goal its label starts, else by time; `lib/agents.ts`), titled "Sub-Agent: " and its name from the brief ("Builder · CP3" in a Theseus run, else the goal), with the child's last two steps and its status icon beside how long it worked; tapping it opens the child's transcript read-only in a pop-up from `GET /api/sessions/{id}/messages`, which on both versions returns only the child's own rows. Both are read every 4s while the call or the child is working.
- `GET runs/live` maps the adapter's `_run_statuses` to `sessions: { <session_id>: "running" | "waiting_for_approval" }` and `run_ids: { <session_id>: <run_id> }` (0.12; `reattachRun` in `chat.ts` uses it, when a chat opens, to follow a reply left streaming by a connection that gave up or a reload before its run id was saved) with `getattr`, so a Hermes that renames it just reports nothing It also carries `waiting: { <session_id>: { kind: "question", count } | { kind: "approval", command? } | { kind: "plan" }, project? }` (0.16; `sessions.waiting`): a waiting run's `clarify` (questions) or `approval` (its command as the API server hands it to clients), else a project session's `plan_pending`, with the project's name for a project session. The sidebar polls it every 10s while visible (every 5 minutes for a server whose change stream is open, which says when `runs` moves), across the server of every keyed bot that isn't turned off, and lists the project sessions it names that aren't resolved. `GET sessions/{id}/prs` caches each repo's answer for 30s (the app asks after every turn and catch-up); without a GitHub token public repos still answer.
- `dashboard/` is a status tab with a **Link to Gots** card (a code, the app's address and the API server URL; `GET`/`POST link`, `POST link/env` to add the `.env` lines it showed, `POST unlink`), which loads `../link.py` under a stand-in package since Hermes imports `plugin_api.py` on its own. `dist/index.js` is hand-written against `window.__HERMES_PLUGIN_SDK__` (no React import, no bundler), and `plugin_api.py` serves `/api/plugins/memento/status` on the dashboard.
- **The plugin must scan clean under Hermes's install scanner** (`tools/plugin_guard.py`). Any `high` finding makes the verdict `caution`, which asks for confirmation on install and prints a scary report on every update (`medium` ones, like `subprocess.run`, are informational). Its patterns are plain regexes over every file, `dashboard/dist/index.js` included, so code that merely looks like an attack trips them: `env ||` reads as `env |`, dumping the environment. The vendored Theseus skill is scanned too (`host '${x}'` in a message reads as a DNS lookup), so a finding there is fixed in thehaseebahmed/agent-skills and re-vendored.
- Python changes need `hermes gateway restart` (API routes) and a dashboard restart (the tab's backend).
- If you change the plugin's routes, update `app/scripts/mock-hermes.mjs` to match.

## Research missions

- **A mission runs on the plugin** (`plugin/research.py`, `memento.db`'s `research_missions`, `research_sources`, `research_claims` and `research_outputs`), so it carries on with the app closed. Its `stage` is `brief → scope → reading → drafting → reviewing → delivered`; `busy` is a model call under way (`brief`, `outline`) and `error` a step that failed, which `…/retry` runs again. `info` lists the `research` feature and `research: { ready, reason }` (not ready without `ctx.llm`). Missions belong to the profile that started them; the app lists every bot's (`useMissions`) and starts one on the active bot.
- **Brief and outline are `ctx.llm.complete_structured` calls** on the profile's own model (no override, so no extra trust): the question read back as title, goal, format, audience and depth, which the user edits and confirms (`…/brief`), then an outline of 3 to 6 points. The Scope Gate (`…/start` `{ outline, source_kinds }`) is the mission's one designed pause: nothing is read before it.
- **The researcher is an ordinary Hermes run**, session `research-<mission id>`, started over loopback with the key the app's `…/start` came with (`outbox.post`), with fixed `instructions` and the brief as its message. It searches and reads with Hermes's web tools (`web_search`, `web_extract`, in the API server's toolset; a host with no web backend records nothing and the reading fails with a hint). `research.wire` adds the plugin's `claim_add` tool to that session's agents only, and its `pre_tool_call` hook blocks the terminal, file writes, delegation, `clarify` and the other tools that could stall or change things. `claim_add` `{ claim, url, title, kind, snippet, confidence? }` fetches the page (`urllib`, 20s, 6 MB; scripts and tags stripped, compared as lower-case words, an ellipsis splitting the passage) and refuses a passage the page doesn't hold; a page it can't read (a PDF, a blocked site) records the claim as `uncertain`. Sources (`s1…`) and claims (`c1…`) are numbered per mission. A background loop (`research.run`) watches the run in `_run_statuses` and, once it stops, moves on to drafting with 3 claims or more, else fails the reading; a restart resumes each mission's step (`research.resume`, also on the first list of a `/p/<profile>` bot).
- **Writing is `ctx.llm` from the ledger alone**: one call per outline point for a guide, saved section by section (`written`), where every sentence must end with the ids of its claims (`[c3]`); one call for a quiz or a glossary, whose items must cite a claim in the ledger or are dropped. **The review is plain code** (`research.spans`): a sentence without a marker, or whose markers name no claim, is `flagged` ("No source" in the app). `…/formats` `{ format }` writes another format from the same ledger, without new reading. Every change notes a `research` event (the mission's id), which `live.ts` turns into a refresh; without the stream the screens poll every 3s while a mission works.
- **Questions a delivered mission missed are read for and added** (plugin 0.38, `info` feature `research_followup`). Once delivered, `research._suggest` asks the profile's model (`ctx.llm`, best effort) for up to 3 questions the outline and the ledger leave open (`suggestions`, dropped when a follow-up is asked meanwhile). `…/followup` `{ questions }` (1 to 3, none already an outline point, the outline at most `MAX_OUTLINE` = 12) records the round in `followups` (`{ questions, from, claims, at }`) and as the mission's `pending` rewrite, and starts the researcher again in the same `research-<id>` session with a prompt naming what's covered and what was missed, adding to the same ledger (schema v17); the write-up stays on show meanwhile. The round needs at least one new claim, else it fails with Try again. **Drafting then writes the whole mission again** (plugin 0.39, decided with Haseeb 2026-10-14: no section tacked on at the end): one `ctx.llm` call plans the outline again with each question worked in where it belongs (`research._replan`, falling back to adding them as points), every section of the guide is written afresh, every other format made before is written again, and `research_done` is pushed again. An older guide's follow-up sections may still carry `question`, which the app labels. The app offers **Missed something?** in a delivered mission's options menu, a pop-up with the suggestions as chips to pick and a question of the user's own, only when the plugin sends `followups`.
- **Every delivery is kept as a revision** (plugin 0.39, schema v18, `research_revisions`): its number, `reason` (`first`, `followup` with its `questions`, `rewrite` with its `model`), the claim count, when, and a snapshot of the outline and every format as delivered, so the app's Revisions list says why each was written and opens an earlier one read-only. A mission delivered before revisions were kept gets its first one just before it's written again. `GET research/{id}` carries `revisions`, `pending` (the rewrite under way) and `writer`.
- **A Learn & understand mission can be rewritten with another model** (`…/rewrite` `{ provider, model }`, `info` feature `research_rewrite`; an empty body is the profile's own model). It writes the whole mission again from the same ledger, without new reading, and the pick stays the mission's `writer` for later writing (a follow-up, another format). It's a `ctx.llm` override, so it needs `plugins.entries.memento.llm.allow_model_override` (and `allow_provider_override` with a provider), which `info.research.writers` reports and the route checks first (403); the app's picker (the host's models, `ModelPicker`) shows a warning when the host doesn't allow it. A rewrite that failed can be taken over by another model from the same menu item.
- **A mission names its main agent** (plugin 0.40, schema v19): the bot is the profile that owns it, and the model is the one the researcher ran on, which `finished_reading` reads from the `research-<id>` session's row in Hermes's `state.db` (read-only, best effort; `researcher: { provider, model }` on the mission, absent until reading has finished or when the plugin is older). The app shows the bot's picture on each row of the Research list and "<type> · <bot name> · <model>" under the mission's title.
- **A mission tells the user when it needs them, is ready or failed** (plugin 0.37): `research_brief` when the brief is read back, `research_scope` when the outline is ready for the Scope Gate, `research_done` when the first format is delivered and `research_failed` when a step fails (`research._tell`, through `push.notify` with the mission's id and title; another format asked for later isn't news). They are the Research feature's categories `research_input`, `research_done` and `research_failed`, all on by default, and a tap opens `/research/<id>`. A muted bot mutes them; there is no per-mission mute.

## Sync

- Sign-in is Netlify Identity with the GitHub provider (`@netlify/identity`). It only identifies the owner. **Never send plaintext, a key or anything that derives one to the server.** Every document the function stores is sealed with `vault.ts` first, and the associated data names its owner and slot (`memento:<userId>:<doc>`).
- **In the Android app** the page is `https://localhost`, and `@netlify/identity` only talks to its own origin. So `account.ts` hands off to `native-account.ts`, which calls `${VITE_SITE_URL}/.netlify/identity` and the sync function through `CapacitorHttp.request` with a Bearer token. Don't turn on `CapacitorHttp`'s fetch patching: it would buffer Hermes's SSE streams. GoTrue ignores `redirect_to` and returns to the page that started sign-in (its `Referer`, when on the site's host), so sign-in starts from `/auth/native.html`. The function skips its origin check for Bearer requests. Passkeys are off in the app, so it unlocks with the recovery code.
- **Sign-in is compulsory where Identity is available.** `SetupGate` (`src/routes/setup.tsx`) keeps the app behind GitHub sign-in and unlocked sync unless the account is `unavailable` (plain `pnpm dev`, no Identity, no `VITE_SITE_URL`, or offline), and behind the first-run wizard until `Settings.onboarded`: Sign in, Turn on sync, Link your bots (Start chatting once a linked bot answers from this device). The wizard's link step comes back whenever the untouched seed is the only bot (`needsBotSetup`), say after the last bot is removed. An upgrade with configured bots is marked onboarded without it. Where Identity is `unavailable` nothing can link, so the seed bot is set up by hand in Settings.
- **Chat lists live on the Gots plugin** (`plugin/chats.py`, `$HERMES_HOME/memento/memento.db`, under the profile home the API server scopes the request to). `POST /api/plugins/memento/chats` takes this device's `{ id: { at, deleted?, value? } }` record set, keeps the newer record per id in one SQLite transaction, and returns the whole list; `mergeDocs` then picks what to pull. It's plaintext, like the transcripts Hermes already holds. **The plugin is mandatory**: there's no other place for a chat list, and a server that doesn't answer shows as `unreachable` (a flag on the bot's card) until it does.
  - Older versions kept a bot's list in a Netlify `chats/<botId>` document when its server had no plugin. Each bot's first sync with an unlocked vault pulls that document onto the device, and once the plugin has merged it the document is deleted and the bot recorded in `Settings.movedChats`, so it's read once.
  - Plugin chat sync needs no account, so it also runs where Identity is `unavailable`. Two bots on one server share its list; a chat stays with the bot that already has it. Deleting a bot leaves its chats on the plugin.
- Documents are `vault` (the wrapped data keys and the inbox), `bots` (what the user changed about each bot: name, character, default model) and `settings` (the Appearance section's switches: `simplifiedChats`, `steerByDefault`, `breakReminders`, one record merged on `Settings.appearanceAt`; the colour mode is this device's own, in next-themes' storage). Writes carry the etag they read; a 412 means re-pull, merge and retry.
- Records merge last-write-wins on a change clock: `Profile.updatedAt` and `Conversation.changedAt`. Change synced fields through `updateProfile` / `updateConversation` so the clock moves, and delete through `deleteProfile` / `deleteConversation` so a tombstone is left for sync.
- Message bodies don't sync. They come from Hermes (`history.ts`): with `X-Hermes-Session-Id`, Hermes builds the turn's history from its own session store and ignores the body's, so its transcript holds every device's turns. An open chat catches up (`reconcileHistory`) on open, when its `updatedAt` changes, on focus, when the plugin's stream says its session moved, every 30s while visible (every 5 minutes while its bot's stream is open), and before a send. `Conversation.hermesTip` (local only) lets that start with a one-row probe. Turns streamed on this device are kept (they carry stats and approvals) and matched to their rows by `hermesRowId`.
- **Changes are pushed, not polled, where the plugin is** (`plugin/events.py`, `plugin/stream.py`, `src/lib/live.ts`). Hooks (`pre_llm_call`, `post_api_request`, `pre_tool_call` / `post_tool_call`, `pre_approval_request`, `post_approval_response`, `on_session_end`, API server sessions only) and the plugin's own writes (a chat-list merge that changed something, a session's mode or pending plan, a clarify status, a project clone or repo change) note a content-free row in an `events` table in `memento.db` (`session`, `runs`, `chats`, `projects`; an hour, 2,000 rows, a quarter second per kind and session). `GET events[?since=N]` is SSE per profile: `hello` with the cursor, those rows (a session id walked back through compression parents for `session`), `title` (watched for 90s after a session moves, since Hermes titles in a background thread whose hooks carry no session), `cron` (a fingerprint of the jobs and the ledger's newest runs, every 4s, shared by a profile's streams) and `reset` when the cursor fell out of the table. A stream wakes on an in-process signal and also reads the table every 2s, for hooks run in other processes. It sets its own CORS headers before `prepare()` and pings every 20s for proxies and tunnels (Cloudflare cuts a quiet one at 100s). Events never carry content: the app fetches as it always has.
- **A session that needs the user is pushed to a closed PWA** (`plugin/push.py`, `src/lib/push.ts`, `public/push-sw.js`; the Android app has no Push API in its WebView and gets Firebase messaging through the registry, below). A browser subscription is tied to one VAPID key, so the key is the *device's* (made in the app, kept in `Settings.push`, local only) and goes to each bot's plugin with the subscription: `POST push` `{ device, subscription, vapid_key, subject }` (a public https endpoint only, the plugin posts to it; at most 20 per profile) and `POST push/remove` `{ endpoint }`, kept in `memento.db`'s `push_subscriptions`. The plugin encrypts a `{ kind: approval | question | plan, session_id }` message to the device (RFC 8291 `aes128gcm`, with `cryptography`, which Hermes already depends on) and signs it with the device's key (RFC 8292), sent from `pre_approval_request`, the clarify callback and a pending plan; never what was asked. A 404 or 410 from the push service drops the subscription. A device that holds an `events` stream with its `device` id is skipped, since the app is on screen (a stream whose client vanished without a FIN can keep a device skipped until the server notices). The service worker (imported by the generated one) shows the notification (see **What a push says**) tagged by session, silent and closed after 3s when a window is visible (Safari revokes subscriptions that get pushes without a notification), and a tap opens `/s/<session id>`, which finds the chat by `hermesSessionId` (a session that compression moved on isn't matched). **The Android app is pushed through Firebase, by the registry** (`netlify/lib/fcm.ts`, `src/lib/push.ts`): the service account key can't live on every user's Hermes host, so it is the Netlify environment variable `FIREBASE_SERVICE_ACCOUNT` (JSON or base64; the same key as the CI secret of that name, which uploads to App Distribution; the registry answers 503 to a push without it), and the plugin asks for the send with `POST registry?route=push` `{ kind, session_id, skip }` (the host token authenticates; `skip` is the devices with the app open; one a second per host; `push.py`'s `_relay`). The app gives the registry its Firebase token with `POST devices&id=<device>` `{ token }` (Identity; at most 10 per account) and `DELETE devices&id=`, through `@capacitor/push-notifications`; the message is a notification message (`notification` + `data`), so Android shows it with the app closed and a tap opens `/s/<session id>` (`PushLinks`). A token Firebase reports unregistered is dropped. `Settings.fcm` is the device's id and switch, which `followEvents` sends like the PWA's. CI writes `android/app/google-services.json` from the secret `FIREBASE_GOOGLE_SERVICES` (the file's JSON, raw or base64); without it the APK builds with push off. That step runs before the web build, which sets `VITE_FIREBASE=1` only when the file is there: `pushAvailable()` is false in an APK without it (the plugin's `register()` throws natively without Firebase, which ends the app), and `Settings.fcm.trying` is set across each native `register()`, so a launch that finds it left behind (the app died there) turns push off instead of crashing again. Developer settings has a Send test notification row in the Android app (`sendTestPush`: `POST registry?route=push-test&id=<device>` with Identity, answering Google's own reason as a 502 on a refusal, which the row shows as a toast): it pushes to that one device whether or not the app is open, and `presentationOptions: ["alert"]` in `capacitor.config.ts` makes the push plugin show the tray notification while the app is in the foreground (a real push also shows then, only if the plugin didn't skip the device). iOS only delivers to a PWA added to the Home Screen, and asks for permission only from a tap; the Notifications row is hidden where the browser has no Push API.
- **A push has a kind, and a device picks which it wants** (`plugin/push.py` `KINDS`, `netlify/lib/fcm.ts` `PUSH_KINDS`, `src/lib/push-kinds.ts`, which keep the same list). `approval`, `question` and `plan` wait on the user, as before; `theseus` (`alerts.theseus_tool`: the first `theseus wait` of a round that finds the run at plan, checkpoints, approval or closing, not again until the agent has run something else), `run_failed` (a turn of a Gots chat ended with `failed`, a stop doesn't count) and `run_done` (a turn that completed after 60s or more, not a plan-mode one) come from the `pre_tool_call`, `pre_llm_call` and `on_session_end` hooks (`plugin/alerts.py`, so only for chats whose id starts `memento-` or that have a project workspace, never a delegated child), `pr_merged` from `merges.py` (the same moment it resolves the session), `clone_failed` from `clones.py` and `repos.py` (the project's id or slug), the `research_*` kinds from `research.py` (the mission's id; see **Research missions**), and `pr_checks` and `routine_failed` from `alerts.run`, which looks every 5 minutes, only when a device could be told: an open session's PR whose checks went to `failure` (pushed once, and again after they stop failing) and a routine run that failed (or whose delivery did) in the last 30 minutes, which `push_seen` in `memento.db` (`push.once` / `clear`) remembers so a pass never repeats one. The plugin's `session_id` is the session the news is about, or the routine's job id or the project's id, and the kind picks where a tap goes (`pushPath`: `/routines`, `/code`, `/research/<id>`, else `/s/<id>`). Kinds fall into categories (`category_of(kind, project)` in `push.py`, `PUSH_CATEGORIES` in `fcm.ts` and `push-kinds.ts`: `chat_input`, `chat_run_failed`, `chat_run_done`, `code_input`, `code_theseus`, `code_run_failed`, `code_run_done`, `code_pr_checks`, `code_pr_merged`, `code_setup_failed`, `routine_failed`, `research_input`, `research_done`, `research_failed`), grouped by feature (Chats, Code, Routines, Research). Every category is a switch under Settings, Notification types (`usePushCategories`, `Settings.pushCategories`, local to the device; a feature's master switch sets all its categories; a run finished and a pull request merged start off) and an Android channel of its own (`createChannel` per category, so Android's own settings can turn each off). The device says which categories it wants: the PWA with its subscription (`categories` on `POST push`, kept in `push_subscriptions.categories`, null for an older app, which gets `chat_input` and `code_input`) and the Android app with its token (`categories` on `POST devices`, `PATCH devices` when only they change; the registry keeps them on the device and counts the others as `muted`); the plugin relays `{ kind, category, session_id, skip }` and the registry derives the category for an older plugin. **Muting is held by the plugin**, so it works with the app closed and covers every device: a bot is muted with `POST push/mute` `{ muted }` (`push_prefs`; `Profile.muted` syncs through `bots` and `syncMutes` tells each bot's plugin), which silences all its pushes, and a thread through the chat list's `muted` field (`Conversation.muted`, `CHAT_FIELDS`), which silences only the pushes about its session (compression lineage followed). Muted bots show a bell-off in the sidebar, muted threads in the chat header and on the bot's thread card. The registry takes one push a second from a host, so the plugin's relay tries again after a 429. A new kind goes in all three lists, `WORDS` in `fcm.ts` and `push-sw.js`, and a category if the user should pick it; `test_push_kinds.py` fails when the lists drift apart.
- **What a push says** (plugin 0.33): its title is what it is about and its body what happened there. The plugin adds `title` to the message (a session's: its chat's title from the chat list, renames included, else Hermes's `state.db` title, compression lineage followed; a routine's name; a project's name; cut at 80 characters), `stage` for `theseus`, and `bot`, the bot character the app told it with `POST push/mute` `{ muted, bot }` (`push_prefs`, sent by `syncMutes` whenever the character changes). The body is one sentence per kind (`WORDS` in `public/push-sw.js` and `netlify/lib/fcm.ts`, which keep the same text, and `THESEUS_WORDS` per stage); a push without a title reads "Gots" ("A routine", "A project"). The PWA's icon is the bot's picture (`/bots/<bot>.png`); Android's is the app's, since Haseeb didn't like Firebase's notification image, and the plugin keeps `bot` from the registry. The title, unlike what was asked, reaches the registry and Firebase in the clear on Android; Web Push carries it encrypted to the device.
- **Live bots** (`live.ts`): the app keeps one `fetch` stream (EventSource can't send the key) per distinct server and key while the page is visible and online, closes it when hidden, resumes from its cursor and treats 50s without a byte as dead. `session` catches up the open chat, `title` re-reads Hermes's title, `chats` runs `syncNow`, `runs` (settled for 300ms, since the status follows the approval hook) refreshes Waiting for input and a project's sessions, `projects` the Code and project screens, `cron` Routines, and a first `hello` or a `reset` does all of it. A live screen keeps its timer at `SAFETY_MS` (5 minutes) as a safety net; a bot whose stream isn't open (an older plugin without the `events` feature, which is asked again after 5 minutes, a proxy that buffers it, a page in the background) polls as it always did.
- **A chat's context use needs the Gots plugin** (`Conversation.liveContext`, local only, read on every catch-up and after each turn): the latest model call's prompt and Hermes's own window, the same on every device. Hermes's API has nothing exact to work it out from (a turn's `prompt_tokens` and the session's `input_tokens` are summed over every call, and message rows' `token_count` is unset), so bots without the plugin aren't tracked: the usage sheet keeps an empty bar under a `Banner` saying the plugin is needed. The window the bot holds for the model shows first, then Hermes's for the call that ran it, then models.dev's. The usage sheet opens from Context in the chat header's options menu, which shows the percentage (not in a simplified chat).
- **A project session's `projectId`, `resolvedAt` and `discardedAt` sync** through the chat list (`CHAT_FIELDS` in `sync.ts`, applied field by field so a field a newer record dropped, like a reopened session's `resolvedAt`, clears here too; add any new synced chat field there). Its `mode`, `worktree` (branch, repos and the instructions line), `planPending` and `prs` are local copies of what the plugin holds, read on open, on every catch-up and a moment after each turn (`refreshWorkspace`, `refreshPrs`), written with `db.conversations.update` so the clock doesn't move. Before the first turn the mode is only local, and the first workspace post carries it.
- **A chat's todo list needs the Gots plugin too** (`Conversation.todos`, local only, read on every catch-up, at turn end and just after a `todo_list` call). Keyless bots and bots without the plugin show no list, even though a run's live events carry one, so a chat shows the same on every device. A list from the live stream wins for 10s over an older revision from the plugin, whose transcript may not have caught up.

## Linking bots

Bots register themselves instead of being typed in (design: https://claude.ai/code/artifact/2ecc0ba3-e01e-4604-a8d5-bdacd8285650). The app shows a link code; on the host, `hermes memento link <code> --site <app>` (or the Hermes dashboard's Gots tab) claims it and publishes the profile's sealed record; every device turns the record into a bot.

- **The inbox.** The vault carries `inbox: { keyId, publicKey, privateKey }` (`vault.ts`): a P-256 key whose private half is sealed with the data key for `memento:<userId>:inbox`. `setUpSync` makes it, and `ensureInbox` (every sync) adds one to an older vault and keeps this device's non-extractable copy in `db.vault` (`id: "inbox"`). `keyId` is the hex of the first 8 bytes of the public key's SHA-256. **The plugin never gets the recovery code or the data key.**
- **Link codes** are minted by the app: `mk_<codeId>-<secret>-<fingerprint>`, Crockford base32 of 5, 10 and 8 random/derived bytes (8, 16 and 13 characters); the fingerprint is the same 8 bytes as `keyId`. The app posts only `codeId` and the secret's SHA-256 hex (`POST ?route=codes`), so the registry can't forge a code or swap the key: the plugin checks the public key it's handed against the fingerprint. A code lasts 30 minutes and 20 claims; 10 wrong secrets burn it.
- **The registry** (`/.netlify/functions/registry?route=…`, Blobs store `memento-registry`) reads the inbox from the account's `vault` document in `memento-sync`. Hosts send `Authorization: Bearer mh_…` (stored only as a SHA-256 under `tokens/`): `POST claim` (no auth; `{ codeId, secret }` → `{ userId, hostId, token, inbox, origins }`), `GET inbox`, `PUT bots&id=` (`{ keyId, sealed }`), `DELETE bots&id=`, `POST seen` (`{ bots, pluginVersion }` → each bot's `enabled`, or null to publish again, and the current `keyId`) and `DELETE host`. The app (Identity): `POST codes`, `GET bots` (records with `seen`), `PATCH bots&id=` (`{ enabled?, adopts? }`) and `DELETE hosts&id=`. `enabled` and `adopts` belong to the app; a host's publish keeps them.
- **A bot record** is `{ name, profile, baseUrl, apiKey, pluginVersion }`, sealed to the inbox (`openFromInbox`): an ephemeral P-256 key, ECDH, HKDF-SHA256 with the ephemeral point as salt and `memento-inbox-v1` as info, AES-256-GCM, associated data `memento:<userId>:bot:<botId>`. `botId` is the first 16 hex of SHA-256 of `<hostId>:<profile>`.
- **Records become bots** (`syncRegistry` in `registry.ts`, on every sync with an unlocked vault and every 3s while a link screen is open). A bot's id is its `botId`, or the `adopts` id when it took over a bot added by hand with the same server and key (the app sets `adopts` the first time it sees the record, so its chats stay with it on every device). `baseUrl` (plus `/v1`), `apiKey` and `hostId` come from the record; name, character and default model stay the user's and sync through `bots`. `disabled` and `seenAt` are local copies of the registry's. A failed read changes nothing; a bot whose record is gone is deleted (the last one is replaced by a fresh seed). Records sealed to another inbox key are skipped until the host re-seals.
- **Online** is a check-in within 25 minutes (the plugin checks in at gateway start, every 10 minutes and right after linking). **Reachable** is `/health` answering from this device (`useReachable`).
- **Disable** only hides a bot in the app and stops every live check for it (decided): it leaves the bot picker, Recents, Code, Routines, Waiting for input and chat sync, and context, todos and PRs aren't read. The host, its routines and its heartbeat carry on.
- **Remove** revokes the bot's host (`DELETE hosts`), which takes every bot that host linked; the host sees a 401 on its next check-in and stops. Its chats stay on the plugin.
- **Bots added by hand** before linking keep working and stay editable (address and key); new ones can't be added. A bot without an API key can't send.

## Sharing into Gots

- **Links, text and images shared from another app open `/share`**: the shared content, a note, the bot (every one turned on) and a new chat or one of that bot's 30 newest, where tapping one sends at once (project sessions left out; called threads when bot threads are on). Sending is the chat's own send: a new chat is created, an existing one catches up first (as its composer does) and gets the message queued while a reply streams. The message is the note, then the title (with a link), the text and the links; images become its attachments through `prepareAttachment`, so they follow the attachment rules above.
- **Android app**: `ShareTargetPlugin` (registered in `MainActivity`) takes `ACTION_SEND` text and `ACTION_SEND`/`SEND_MULTIPLE` images (the intent filters in `AndroidManifest.xml`), copies up to 10 images (20 MB each) into the cache, since the sender's grant ends with the intent, and sends a retained `share` event, so the share that launched the app reaches the page too (`skipLaunchRestore` then keeps the launch from reopening the last chat). The page reads the copies through `Capacitor.convertFileSrc`.
- **Installed PWA**: the manifest's `share_target` posts to `/share-target`, which `public/share-sw.js` (imported by the generated service worker before Workbox's routes) keeps in the `memento-share` cache and redirects to `/share?id=`. Chromium only (Chrome and Samsung Internet on Android, desktop Chrome and Edge); Safari has no share target (MDN's compat data, checked 2026-10-09), and a browser tab that isn't installed is never offered.
- **iOS has nothing yet**: there is no iOS app, and receiving shares there needs one with a Share Extension and an App Group, so a paid Apple Developer Program account.
- `window.mementoShare({ title, text, url, images })` opens the screen in development.

## Conventions

- **The UI renders from Dexie live queries.** Streaming writes into IndexedDB (throttled), and components never hold stream state.
- **Every write re-runs every live query over its range**, and a streaming reply writes every `FLUSH_INTERVAL_MS` (`chat.ts`). So keep the work each write causes small:
  - Read only what a screen shows, through an index: a list row reads its chat's tail or opener (or a count over `[conversationId+role]`), never every message, and never `anyOf(...)` filtered in JS. Add the index (bumping the Dexie version) rather than scan.
  - Don't write what didn't change: compare before a `put` or `update`, since a fresh object wakes every query that covers it (`saveSettings` skips equal writes).
  - A live query hands back new objects on every run, so memoize rows that render them on their value (`MessageItem`), and depend on ids, not live-query objects, in effects and memos.
  - Work that grows with streamed text keeps its finished part: markdown renders as memoized blocks (`markdown-blocks.ts`), so only the open block is parsed again.
- **Requests are bounded and independent.** Every read to a host carries a timeout (`READ_TIMEOUT_MS`), and per-bot work runs side by side, so one hung host never stalls another bot, sync or onboarding. Follow-up reads (title, context, provider limits, todos, workspace, PRs) run when the transcript moved, else at most every `FOLLOW_UP_MS` (`freshness.ts`), and never on the send path. A cooldown starts only when the route is missing (`lacksRoute`), never on any failure.
- **Release what you take.** A guard, lock or `streaming` status set at the start of an async flow is released in `finally`, so a throw or a dropped stream can't leave a chat stuck. Deleting a record deletes its device-only rows too (drafts, saved dictations).
- **Startup stays small.** Only the chat route loads up front: every other route, heavy library (the markdown renderer, highlight.js) and anything behind a feature switch (Theseus, Research) is a lazy import. A returning device renders from what it has on the device; network checks (Identity, the vault) run behind it, never in front of it.
- **Measure performance changes.** Profile before and after (CDP `ScriptDuration` while a reply streams, or the build's chunk sizes) and give the numbers in the PR. `pnpm e2e stream-writes` and `pnpm e2e idle-requests` guard the write and request budgets; keep them passing, and add a flow when you fix a regression.
- **History mirrors the sidebar.** Top-level screens (chats, Code, Routines, Settings) open with `root` as the only history entry, so back leaves the app; a deeper screen (a project, a session, a Settings section) is pushed on its parent, goes back with `up`, and sets `setBackGuard` so Android's back does the same. From a top-level screen Android's back shows a "Press back again to exit" toast at the bottom (above anything marked `data-toast-above`, like the composer), and a second press within 2s minimizes the app.
- **Screens and tabs animate in.** `AppShell` slides the main pane in from the right on a push, from the left on back, and fades it on a replace; a `replace` navigation that keeps the same screen passes `state: { quiet: true }`. Tab panels slide in from the side of the tab they were opened from. Everything respects `prefers-reduced-motion`.
- **If you change the schema, bump the Dexie version** in `src/lib/db.ts` and keep existing data loading.
- **Every screen must work at phone (390px) and tablet (≥768px) widths, in light and dark mode.**
- **Pop-ups are sheets on phones and dialogs on bigger screens.** Build them with `Popup` / `PopupContent` (`src/components/popup.tsx`), which picks with `useWide`, rather than a bare `Sheet` or dialog. Side drawers (the sidebar) and the tool-details drawer are not pop-ups.
  - A pop-up's width is its `size` (`lg` by default, or `md`, `xl`, `2xl`), never a max-width class. A side sheet takes its own width, so a size can't cap it.
  - Every pop-up renders a `PopupHeader` with a title — it's pinned, reserves room for the close button, and keeps content from ever sitting against it. The heading is centred in every form, like Material's bottom-sheet title, and a title cuts with an ellipsis rather than running under the close button; a header carrying a back button of its own in the row passes `text-left` to keep its title beside it. The close button lives in the header (dialogs and side sheets only; phone sheets have none — swipe, the scrim or the handle dismisses). `PopupContent` reports to the dev console when a pop-up renders with no `PopupHeader`.
  - Use the theme tokens. Don't hard-code colours, except for the fixed character palettes in the bots.
  - Respect safe-area insets.
  - Keep touch targets at 44px or larger.
- **Bots:** they are still by default. Only the header (and the empty-state hero) passes `animate`. Animations must respect `prefers-reduced-motion`.
- **Assets must be original or properly licensed.** Never copy third-party characters, mascots or brand assets, even as "inspiration" copies.
- **Never commit secrets.** API keys live only in the user's browser.
- **No explanatory copy.** Don't add UI text that explains how the app works or where its data comes from (footnotes, "from X" captions) unless asked. If it seems needed, ask first.
- Match the surrounding code: Prettier style (no semicolons, 100 columns) and few comments. Comments explain *why*.
