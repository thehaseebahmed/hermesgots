# AGENTS.md

Guidance for AI coding agents (and humans) working on Gots: a playful, minimal PWA companion for [Hermes Agent](https://github.com/NousResearch/hermes-agent).

## Repository

- `app/` is the web and Android app. Run every command below from `app/`; paths in the rest of this file are relative to it unless they start with `plugin/`.
- `plugin/` is the Gots Hermes plugin (Python, no build step). See **Plugin** below.
- `website/` is the public site for **Gots** (the product name from 2026-10-14, at hermesgots.dev; tagline "Hermes Bots that got your back!", SEO term "Hermes Bots"; the app and plugin show Gots, while the package ids, storage keys, plugin id and repo name still say memento; a text wordmark, with a green G favicon; Astro, static, plain CSS on the app's tokens): the landing page at `/` (a hero, then a sticky scroll story with one slide per highlight — Chat, Code, Research, Meetings, Routines, Community and Yours — then the extras, the coming-soon cards and pricing; its waiting-list form posts to Netlify Forms, and the header and footer link to the GitHub repo) and the leaderboard at `/community`: its own Netlify site with the base directory set to `website/`, configured by `website/netlify.toml`. Run its commands (`pnpm dev`, `pnpm build`) from `website/`. Its leaderboard (`src/lib/board.ts`, `render.ts`, `components/Board.astro`) shows sample data, marked as such, until the build has `PUBLIC_COMMUNITY_URL` (the app site's base URL; the page adds `/.netlify/functions/community?route=board`); it then reads that board in the browser and replaces the sample.
- `netlify.toml` stays at the root and sets `base = "app"`; it belongs to the app's site.

## Plugin first

**Always read credentials and configuration through Hermes's `agent.credential_pool.get_env_prefer_dotenv(key)`, never `os.environ` directly.** The plugin runs inside a Hermes process that may serve several profiles, so `os.environ` holds the launch profile's values — a bare read is a silent cross-profile leak. The helper resolves the profile's `.env` and the profile-scoped secret, never the process env. The exception is code that intentionally manages or inspects the `.env` file itself (like `link.py` during linking): those operations read and write the file by design and must not go through the helper.

**A user should be able to ask the agent for something, close the app, come back later and find it done.** So work that has to keep going, or stay correct, while the app is closed belongs in the plugin (`plugin/`), which runs on the Hermes host. It doesn't belong in app-side workarounds.

- Before building a feature, check whether it needs the app to be open, following a stream, polling or answering for the agent. If it does, and the plugin (or Hermes itself) could do it, build it in the plugin.
- If a feature can't be done reliably without app-side hacks, say so **up front**, before writing code. Name what breaks: a session that is broken, blocked or stuck waiting when the user comes back. Then propose the plugin route, or not doing it. Only build the app-side version if the user explicitly insists.
- The exceptions are things that wait for the user by design: a plan in plan mode, an approval in Accept edits mode, a clarify question. Pausing for the user there is expected. Losing work or stalling because the app was closed is not.
- The app is the view and the controls. It may make things smoother while it's open (live streaming, faster updates), but nothing should depend on that.

## Commands

```bash
cd app
pnpm install
pnpm dev         # Vite dev server
pnpm dev:netlify # Netlify CLI dev server (Identity + the sync function; needs a linked site)
pnpm mock        # fake Hermes API on :8642 (say "clean up" to trigger an approval)
pnpm e2e <flow>  # browser flows against the mock (list, all, shot <path>, up, down)
pnpm lint        # oxlint
pnpm typecheck   # tsc -b on TypeScript 7 (`typescript-7`); `typescript` stays 6 for editors and tools
pnpm test        # unit (scripts/test-*.mjs) then component (scripts/test-*.tsx) tests
pnpm build       # typecheck + production build (also generates the service worker)
pnpm build:android # native-mode build (no service worker) synced into android/; set VITE_SITE_URL for sync
pnpm format      # prettier (with the Tailwind class sorter) over src/
```

Before you commit, run `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build`. All four must pass.

For a change to chats, sessions, polling or sync, also run the browser flows that change touches against the mock: `pnpm e2e <flow>`, never `pnpm e2e all` unless asked, since `.github/workflows/e2e-nightly.yml` runs the whole registry on `main` every night and skips a night `main` didn't move (`docs/adr/0029-the-e2e-registry-runs-nightly.md`); `pnpm e2e list` names them and `pnpm e2e shot <path>` screenshots a screen. The e2e-testing skill (`.agents/skills/e2e-testing/`) says how to add a flow.

Tests come in three tiers — **unit** (a pure rule run by `node --test`, with no DOM, database or HTTP), **component** (a screen or sheet rendered over a seeded device database with the HTTP boundary faked, in one process) and **end-to-end** (a flow in a real browser against a test host; the flows run together as the sweep). **A test belongs to the cheapest tier that would fail for the reason the change can fail**, so a new flow is an argument that the lower tiers cannot reach the behaviour, never a default, and geometry — anything a DOM without layout cannot measure — escalates to the sweep (`docs/adr/0019-a-test-belongs-to-the-cheapest-tier-that-would-fail-for-its-reason.md`). Every flow has a row and a verdict in `docs/e2e-flow-audit.md`, and `scripts/test-e2e-registry.mjs` fails the gates on a flow without one.

Plugin tests (`plugin/tests/`, `python3 -m unittest plugin.tests.<module> -v`) carry three harness traps: `commit()` every insert a harness makes into `state.db` — an uncommitted write is invisible to the code's own connection, so every end-to-end case fails identically while direct probes pass (suspect the harness wiring first, not the code); plant the host modules a function imports lazily in `sys.modules` before calling it (`agent.credential_pool`, `agent.secret_scope` — see `plugin/tests/test_token_scope.py`); and where `plugin/__init__.py`'s import chain is the only heavy pull (cryptography via `push.py`, aiohttp via `outbox.py`), load the module by file path (`importlib.util.spec_from_file_location`) and register a stub package for its relative imports. Assert the invariant the design guarantees, not numbers guessed for one case.

CI (`.github/workflows/tests.yml`) runs the plugin tests (`python3 -m unittest discover -s plugin/tests -t .`, from the repo root; `plugin/tests/__init__.py` takes the machine's GitHub account out of reach and refuses any request off the host, so a test that would reach the network fails wherever it runs), the app gates and the CI's own checks (`.github/scripts/release.test.mjs`, the release decision's logic), chosen by what the diff touched (`.github/scripts/changed-areas.sh`): a pull request runs only the gates its own paths can have changed, a push to `main` runs the plugin tests and the app gates its diff touches, and the website build is a pull request's alone because Netlify builds that site on a merge. Every gate runs when the diff can't be worked out, so merged work stays green. A push to `main` touching `app/**` or `netlify.toml` is tested by `.github/workflows/deploy.yml` instead — it calls this workflow as its gate, over the same diff-gated jobs — and deploys the `app/dist` that run built (uploaded as an artifact, not rebuilt) as an unpublished Netlify branch deploy aliased `candidate`, which publishes nothing. Production is published by running that workflow by hand on `main` with `promote` on — a real production deploy, at 15 of the team's credits where a branch deploy costs none — and a debug build's sign-in and sync go through the candidate, not production. A release is an annotated dated tag on `main`'s head, cut by `.github/workflows/release.yml` (dispatch it with the date, which defaults to today): the workflow runs the release's checks (`.github/scripts/release.mjs` — the app must not need a newer plugin than the release carries, each artifact whose code moved must have had its version bumped, and the date must not be one already released) and only then creates and pushes the tag, and the tag publishes what moved: the production deploy and the release APK, both only when `app/**` moved. A merge still publishes nothing, and `docs/adr/0004-a-release-is-a-dated-tag-on-main.md` is the decision. Netlify's own Git builds are off for the app site, so this repo is its only builder, and `netlify.toml`'s `[build]` section stays for anyone following the README to have Netlify build their own (`docs/adr/0003-deploys-are-built-in-github-actions-and-promoted-by-hand.md`). `.github/workflows/plugin-scan.yml` runs Hermes's own plugin install scanner (`tools/plugin_guard.py`, from NousResearch/hermes-agent's latest release and its main) over `plugin/` on pull requests that touch it and weekly, and fails unless the verdict is `safe`.

## Git commits

**Always use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/).** The format is:

```
<type>(<optional scope>): <imperative summary, lower case, no trailing period>

<optional body: what changed and why>
```

- Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- Scopes, when they help: `chat`, `settings`, `bots`, `hermes`, `db`, `pwa`, `ui`, `deps`.
- Breaking changes: put `!` after the type or scope (e.g. `feat(db)!: ...`) and add a `BREAKING CHANGE:` footer.
- Keep the summary line to 72 characters or fewer.
- Use one logical change per commit.
- Examples:
  - `feat(chat): show approvals in place of the composer`
  - `fix(hermes): handle CRLF line endings in SSE frames`
  - `docs: document the HTTPS requirement for remote Hermes servers`

PR titles follow the same format. Fill in `.github/pull_request_template.md` for every PR.

## Stack

- Vite, React 19, TypeScript and Tailwind v4.
- React Router (`src/App.tsx`).
- **shadcn/ui on Base UI**, `base-maia` style (`components.json`). Components live in `src/components/ui/`.
  - Base UI uses the `render` prop, not Radix's `asChild`.
  - Use shadcn components wherever one fits before writing your own.
  - Add new ones with `pnpm dlx shadcn@latest add <name>`. Leave the generated files alone unless there's a reason to change them.
- Dexie (IndexedDB) for all app data. `vite-plugin-pwa` handles the manifest and service worker. Deployed on Netlify (`netlify.toml`).
- Capacitor 8 wraps the same build as an Android app (`capacitor.config.ts`, `android/`). `.github/workflows/android.yml` builds a debug APK on pushes to `main` — signed with the release key when the secret is set, so tester builds update over each other — and checks a pull request with Gradle's `lintDebug` instead, assembling an APK only when the native project or `capacitor.config.ts` moved, and a push's build also goes to Firebase App Distribution's tester groups once the `FIREBASE_SERVICE_ACCOUNT` secret is set (the same service account key Netlify's registry sends push with; app id from `vars.FIREBASE_APP_ID`, else `google-services.json`). `.github/workflows/android-release.yml` builds the signed release APK for a release — a dated tag cut by `release.yml`, or by hand on such a tag: the tag names the release rather than carrying a version, so the version name comes from `app/package.json` and the version code from that version (`major·10⁶ + minor·10⁴ + patch·100` plus 99 for a release or a prerelease's trailing number), an APK is built only when the release moved `app/**` (a repeated version code couldn't install over the last one), and it goes on the tag's GitHub release.

## Hermes API

These behaviours were verified against Hermes's `gateway/platforms/api_server*.py`. Check the source again before relying on anything new.

- Turns run on `POST /v1/runs` when `GET /v1/capabilities` reports `run_submission` and `run_events_sse`. A chat completion's agent is interrupted when its SSE client disconnects, which happens whenever a phone sleeps mid-reply. A run keeps going without a client.
  - `GET /v1/runs/{id}/events?last_seq=N` replays the buffered events after `N` and then follows live ones. CORS doesn't allow `Last-Event-ID`, so the cursor goes in the query. Each event carries `seq`, which the reply stores (`runSeq`, along with `runId`) so it can resume after a dropped stream or a reload.
  - The events stream sends a `: keepalive` comment every 10s while the run is quiet, so a stream silent for 30s is treated as dead and reopened from `last_seq`; a connection can die without the read ever failing (a phone that slept, a tunnel that dropped it). Polling reads time out after 15s for the same reason. Coming back to the app after 5s or more away (or back online, or Android's `resume`) drops a run's connection and reads it again at once (`onWake` in `src/lib/wake.ts`), since a phone that slept may not count that time towards either timeout.
  - Hermes keeps the buffer (1000 events) for 5 minutes while nobody is listening. After that the events endpoint returns 404, and `GET /v1/runs/{id}` (whose `output` and `usage` are kept for 24h when the run was started with an `Idempotency-Key`) is polled instead.
  - Events: `message.delta`, `message.interim`, `tool.started` / `tool.completed` (no call id, so a completion matches the oldest running call of that tool; its `error` flag marks the card failed; the transcript doesn't store that, so `toMessages` reads it from the result the way Hermes's `_detect_tool_failure` does (`failureReason` in `src/lib/tools.ts`: a terminal command's non-zero exit, or an `error` field), and the reason shows on the call's row. Its `preview` is cut at 500 characters, so `src/lib/tools.ts` reads a cut JSON envelope as far as it goes, and catching up swaps a cut preview for the transcript's whole result), `reasoning.available` (a whole block, non-streaming providers only), `approval.request`, `replay.truncated` and the terminal `run.completed | failed | cancelled | interrupted`, which carries `output` and `usage` (`input_tokens`, `output_tokens`).
  - Hermes v2026.9.24 (the stable release as of 2026-10-05) sends the events stream without CORS headers and without `seq`, and drops the run's events once that blocked subscriber leaves. In a browser the events request then fails with no response; when `GET /v1/runs/{id}` still answers, the reply falls back to polling at once rather than retrying the stream (`MOCK_BLOCK_RUN_EVENTS=1` mimics it): the final `output` from `GET /v1/runs/{id}`, and, for a keyed session, the turn's progress from the transcript every 3s (`liveTurn` in `history.ts`: its tool calls, the ones without a result row shown running, its reasoning and its text so far). So tool cards show with a few seconds' lag, but no live text and no tok/s. Approval requests travel on that stream too, so while polling, `GET /v1/runs/{id}` is read for `status: waiting_for_approval`, whose `approval` field is the pending `approval.request` (command, description, choices; no plugin needed), and the card is raised from it. A final `output` that replaces the text keeps the tool cards, approval and steers at their recorded offsets when it is already the reply's tail, and otherwise maps them exactly through the common prefix and suffix of the old and new text (an offset inside a rewritten region parks at the rewrite's start, in call order). Hermes fixed it after that release (c7b8e44ffe). A stream without `seq` numbers its tool calls itself, and `reconcileHistory` fills a streamed turn's missing tool calls in from the transcript.
  - A keyed profile sends `session_id` in the body and only the new message as `input`. A keyless one sends the whole transcript.
  - `POST /v1/runs/{id}/stop` stops a run.
  - **Messages sent while a reply runs wait faded at the end of the thread** (`Message.status: "queued"`, `QueuedActions` in `message-item.tsx`: Queued, Remove, and Send now once paused); the next one goes when the reply finishes, and a stop or error pauses the queue. **How a message sent mid-reply goes** is the user's choice: `/steer text` steers it, `/queue text` queues it (both in the `/` menu only while a reply runs, `SEND_COMMANDS` in `slash.ts`), and a plain message does what the **Steer by default** switch says (Settings > Appearance, `Settings.steerByDefault`, off: queue). A plain message steers only when the run takes it (`steerable`) and carries nothing that has to ride in it — a file steers, since its marker line is text, and a photo doesn't (`canSteer`/`midReply` in `lib/steer.ts`), which the composer says under the field; an explicit `/steer` always asks, and `steerText` queues it with a toast when Hermes refuses. **The queue lives on the plugin** (`plugin/outbox.py`, `info` feature `queue`) so it goes with the app closed: `queueMessage` uploads the attachments, builds the whole `POST /v1/runs` body (`runRequest`: model, provider, instructions with the workspace's line, the message) and posts it to `sessions/{id}/queue`, and the local copy is `Message.hostQueued` with the plugin's item id. The plugin's dispatcher (a loop on the API server, woken by `on_session_end` and every second) starts a session's first item with that body once no run of the session (or its compression tip) is active, posting to its own API server on loopback with the key the app's requests came with (the default profile also has the adapter's own key) and the item id as `Idempotency-Key`, so the run is an ordinary one any device can follow; a latest run that was `cancelled`, `failed` or `interrupted` after the user last sent pauses it until `…/queue/{item}/send`, and Hermes refusing the body (a 4xx) marks the item's `error` and holds the queue. `syncQueue` (`refreshQueue`, run before every catch-up, a moment after each turn and every 3s while an open chat's host queue waits) mirrors the items, follows a run the plugin started (`sent`, kept an hour, with `run_status`) live as a streaming reply when it's still going, and otherwise leaves it to the transcript. Without the feature (or when the post fails) the message waits on the device as before, and only goes with the app open. **Steer is Hermes's own `POST /v1/runs/{id}/steer`** `{ input }` (capability `run_steer`; on v2026.9.24 and main): the agent gets the text as a user row after its current tool calls, without stopping, so it reaches the agent with the app closed. Hermes refuses it (409) unless the run is `running`, and takes text only: a message carrying files steers as the markers it would have sent (the app composes them with `attachmentsText` for a row on the device, and the plugin composes them from the item's own body for one in its queue, `outbox.steer_text`), while one carrying a photo queues. The transcript keeps it as a `role: user` row with `display_kind: "steer"` wrapped in Hermes's `[OUT-OF-BAND USER MESSAGE …]` marker; it's part of the turn, not a new one (`isTurnStart`), and `toMessages` puts it on the reply as `Message.steers`, shown as a user bubble marked Steered where it was sent. A steer that arrives while the agent writes its last reply is never read: Hermes hands it back as `pending_steer` on the terminal event and on `GET /v1/runs/{id}`, and it goes first as the next turn (Hermes's messaging gateway does the same): the plugin queues it itself (`s_<run id>`, from the session's last queued body), and without the plugin the app takes it off the reply and queues it, its markers read back as the files they name (`requeueSteer`). A queued item steers through the plugin (`…/queue/{item}/steer`, which forwards the app's own key to Hermes's route), so its leftover comes back to the plugin too. A hard stop drops an unread steer.
- Older servers fall back to `POST /v1/chat/completions` with `stream: true`, whose stream interleaves named SSE events with the normal chunks: `hermes.tool.progress`, `hermes.status` and `approval.request`.
- Approvals are answered with `POST /v1/runs/{completion_id}/approval` and a body of `{ choice }`. **An approval that stopped waiting leaves the composer's slot.** Hermes's route puts `approval.responded` `{ choice }` on the run's stream and sets the status back to `running`; one that times out, is withdrawn or that the plugin answers for Auto does neither (the status keeps the old request until the run moves on), so the plugin's `post_approval_response` hook (`plugin/approvals.py`, 0.40) does both, with `choice` `timeout`, `cancelled` or `notify_failed`, unless another request of the run still waits. The app settles the card on that event (a choice it doesn't know reads as `expired`, "No longer waiting for an answer"), expires it when a status read begun after the card went up no longer waits, tells requests apart by Hermes's `timestamp` (the status and the event share it), so a stale one on the status is never raised again, and treats an answer refused with the error code `approval_not_pending`, `approval_not_active` or `run_not_found` (`HermesError.code`, from the error envelope; never the message) as the approval missed. `POST /__mock/approvals { outcome: "timeout" | "lost" }` ends the mock's pending approvals with or without the plugin (`pnpm e2e approval-missed`).
- `X-Hermes-Session-Id` continues a session. Hermes only accepts it when `API_SERVER_KEY` is set.
- Hermes's CORS setup does not expose response headers, which is why the client mints its own session ids.
- **The agent asks the user questions with Hermes's `clarify` tool, which needs the Gots plugin.** The API server's own toolset (`hermes-api-server` in `toolsets.py`) leaves `clarify` out and its agents get no `clarify_callback`, so without the plugin the agent can't ask on this surface. The plugin (`plugin/clarify.py`) wraps the adapter's `_create_agent` to add the tool's definition and a callback to every agent it builds; a call puts `clarify.request` on the run's stream (`{ clarify_id, questions: [{ id, question, choices?, multi_select? }] }`, choices bare, the first one recommended) and the same object as `clarify` on `GET /v1/runs/{id}` while the run waits as `waiting_for_approval` (so `runs/live` and the Code screen read it as waiting, and a client that can only poll still sees it); the app shows the questions in place of the composer (`QuestionCard`, `Message.clarify`; one question is shown as is, two or more are pages of one form, and a reply keeps only its latest question), posts the answers to the plugin's `POST runs/{run_id}/clarify` (`{ clarify_id, answers: { q0: "text" | ["several"] | null }, outcome: "submitted" | "cancelled" }`), and the run carries `clarify.responded` (with the answers, so another device or a replay resolves the form) before the agent carries on in the same turn. Once answered, a question is the `clarify` tool call's card in the thread (`ClarifyCard` in `session-cards.tsx`, in every chat) and reads from the call's result, Hermes's `{ responses: [{ question, choices_offered, status?, user_response }], outcome? }` (the stable server's persisted rows also use `responses`, with `timed_out: true` for an unanswered timeout): the app writes that result itself when the user answers, since the run stream's preview is cut at 500 characters. Transcript polling preserves that settled result by call id until a nonempty server result arrives; it never substitutes an answer from a different call. A device that loads the transcript reads the persisted `responses` without needing the local question form. A transcript loaded while the host still runs the session (its last row a call without a result, and `runs/live` naming the session) keeps that turn's open calls running, so a question opened from a notification reads as waiting, never as `No answer`, until the run is followed and the form shows. Answered responses take precedence over the outcome; a submitted empty form is `Skipped`, cancelled or undelivered questions are `Not answered`, and a timeout is `No answer`. Waiting for an answer is the by-design pause the **Plugin first** rule names; Auto's approval bypass doesn't touch it. No mode answers for the user, `auto` included; an unanswered question ends as `timed_out` after Hermes's `agent.clarify_timeout` (an hour by default), a stopped run as `cancelled`, and a chat completion (no run stream) as `undelivered`, so the agent asks in prose. In plan mode the instructions ask the agent to settle every open choice this way before it writes the plan.
- **Attachments: images go inline, files through the plugin.** Both `/v1/runs` and chat completions take the OpenAI vision shape for a user message's `content` (`[{ type: "text" }, { type: "image_url", image_url: { url } }]`; checked at v2026.9.24 and main). Chat completions validate it (`_normalize_multimodal_content`: `http(s)` or `data:image/…` URLs only, and `file` / `input_file` parts are refused with `unsupported_content_type`); `/v1/runs` passes the last `input` item's `content` to the agent as is, so the app always sends the canonical `image_url` shape, only on the newest message (Hermes `str()`s `conversation_history` entries). Hermes stores such a message as text with each image replaced by a `[screenshot]` line (`_durable_content`), so a keyed session's later turns no longer see the image, and the request cap is 10 MB (`MAX_REQUEST_BYTES`). So the app scales images to a 1600px long edge (`attachments.ts`) — that scaled JPEG is only what the request carries inline and the fallback for an original past the cap, while the bytes the host stores and this device caches are the file the user chose (`keptImage` in `attachment-caps.ts`), so a clip, an animation or a transparent PNG keeps what it was — and when the bot has the plugin it first saves every attachment on the host (`POST sessions/{id}/attachments`); the message then carries an `<attachment name="…" type="…" size="…" path="…" />` line per attachment (the path only once saved), followed by the image itself for a photo, and a message carrying a file says once, after the last marker, that the content isn't inlined and the agent should open the path and extract the text itself (`attachment-text.ts`: the marker, that sentence and the read-back that gives a restored message its attachments, name, type, size and path, without the bytes), so the agent can open it with its file or vision tools later and the thread can draw or download it on any device. Files need the plugin, so **Files** is offered only where the host advertises `attachments` (`features.ts`) and refused at the `+` menu, with the reason, where it doesn't; a photo whose upload fails still goes inline. Camera and Photos are disabled when models.dev says the model doesn't take images (`modalities.input` without `image`, stored as `Profile.imageInput` next to the context window; unknown counts as yes), and an image picked through Files then goes as a file. Files aren't gated on the model's own `attachment` flag: the agent opens them with its tools, which any model can do. `toMessages` splits those lines (and each photo's `[screenshot]`) back off a transcript row, which keeps the text matching the device's own copy; the photo itself lives only on the device that sent it (`Message.attachments[].blob`), and another device reads it from the host path (`useMediaSources`).
- **Images the agent returns show in the thread.** A reply names an image with a `MEDIA:<path>` tag (the shape Hermes's `MEDIA_TAG_CLEANUP_RE` strips for its messaging adapters, which send the file as a photo). The run events, run output and transcript rows keep that tag as text; only the chat-completions routes resolve it (`_resolve_media_to_data_urls`, to `![image](data:…)`). The app renders both through `MediaImage` (`src/components/chat/media-image.tsx`): a markdown image (including those data URLs, which react-markdown's own `urlTransform` would drop), and every tag in an assistant reply, read from the plugin's `GET /api/plugins/memento/media?path=…` (the `media` feature in `info`), which serves the file behind the bot's key using Hermes's own `validate_media_delivery_path`. `mediaImages` (`src/lib/media-tags.ts`) ports the tag shape and skips fenced code blocks, so an example tag stays text; each image in a reply takes one cell of the same grid — a lone image, the tags sent together (only whitespace between, which put two, or three from five, side by side), or an image written into the reply's own Markdown — sized by breakpoint, and an image still being read holds that cell with a `Skeleton` (`src/components/ui/skeleton.tsx`) until it lands, so nothing moves under it (a photo or clip you sent takes the same cell, in the Gallery `media-gallery.tsx` draws); tapping an image opens it in the platform's own viewer on a phone (the Android app's `OpenImage`, a browser tab) or a pop-up on tablet and desktop. Only the raster extensions the plugin serves (`.png .jpg .jpeg .gif .webp .bmp`, `media.MEDIA_TYPES`, under `media.MAX_BYTES` = 25 MB) become images; any other tag, and one on a bot without the plugin or with a plugin from before the `media` feature (checked like the todo list, retried every 5 minutes), stays visible as text. **The route itself serves every type a message carries** (`plugin/media.py`'s `media_file`), because a reply's tag and a message's `<attachment>` marker both name a host path the thread has to draw or download: the suffix's own content type where the plugin's map has it (images, video, audio, PDF, JSON, text, code, data, SVG), `application/octet-stream` otherwise, and a `Content-Disposition: attachment` naming the file (RFC 5987 for a name outside ASCII) for every type a browser can't show — images, video, audio, `text/*`, PDF, JSON and SVG serve in place. A message's own upload, under `$HERMES_HOME/memento/attachments/<session>/`, is reachable through it too: the same `_validated_path` (Hermes's `validate_media_delivery_path`) and the same 25 MB cap as a library file. What a message carries draws as what it is — images (SVG too) and clips in the Gallery, a recording in its own row, anything else a row that downloads (`mediaCell` in `src/lib/media-kind.ts`, the rule a reply's widened tags will read too). A clip's cell shows its first frame and nothing is embedded: a tap hands the file to the platform's own viewer or player (`openMediaViewer` in `native.ts`: a VIEW intent for the file's type in the Android app, a new tab in a browser). Each draws from the bytes this device holds, else through the media route by the path the message kept, so a message restored on another device shows the real media while this device's own photos survive the host being unreachable. The thread draws a file it doesn't hold as a row naming it and its size, and a tap fetches the bytes with the bot's key (a plain link can't carry it) and saves them under the file's own name (`downloadAttachment` in `attachments.ts`).

It isn't scoped to a profile, and on current Hermes it 500s (`_handle_skills` passes an `include_editorial` kwarg `_find_all_skills` doesn't take), so the app doesn't call it. The `/` menu reads the plugin's `GET /api/plugins/memento/skills` (see § Plugin).

- Hermes auto-titles API sessions (an instant slice of the opener, then a background model call that can land after the stream ends, and again on turns 2–3 for a placeholder like "Friendly greeting"). `GET /api/sessions/{id}` (server root) returns `{ session: { title } }` but not where the title came from. Older versions don't have it, so treat a failure as unknown.
- **A chat can run on another of the host's models.** The composer's model pill opens a list of those providers' models (`getModelInfo`, cached a minute per server by `useModelInfo` in `lib/model-info.ts`), and the pick is `Conversation.modelChoice` (`{ provider, model }`, synced through the chat list; a new chat holds it until its first message creates the chat). It changes that chat only. A turn runs the chat's pick, else the bot's default (`Profile.modelChoice`, synced through `bots`), else the host's model. A turn with no pick sends no `model` on `/v1/runs`: a profile served at `/p/<profile>` advertises its name on `/v1/models`, but the run handler only treats the launch profile's name (or `hermes-agent`) as the virtual model, so sending it fails with `HTTP 400: <profile> is not a valid model ID` (read in `_request_agent_overrides` and `_handle_models` on the hermes-agent fork's main, 2026-10-09). The picker lists the bot's last three picks first as `provider/model` (`Profile.recentModels`, newest first, from both pickers through `rememberModel`, synced with the bot; one the host no longer offers is left out), then the providers (A to Z, each with its model count), each opening its own models (A to Z; a host with one provider lists its models at once); a search looks through every provider's. The list has a fixed height, so it doesn't resize between views. Each model's row carries a second, muted line that keeps one shape, in a fixed order: the BenchLM score, the cost, the model's capabilities, then the context window. The cost is five dollar slots with the ones past the model's band dimmed, and both capability marks always show, dimmed when the model doesn't support them or models.dev doesn't say. A model models.dev doesn't list shows its score with a dash where the rest of the line would be, or `—` when BenchLM doesn't rank it either. A pick is sent as the turn's `model` and `provider`. `/v1/runs` honours both on every request (`_request_agent_overrides`; checked at v2026.9.24), and chat completions honour a bare model only with `direct_model_requests` but an explicit `provider` always. It needs neither the plugin nor `allow_model_override`, which gates only the plugin's own `ctx.llm` calls. **The bot editor's Default model is the host's main model** (`setDefaultModel` in `lib/model-info.ts`): Hermes's only route for it is the dashboard's `POST /api/model/set`, which the app can't reach, so the plugin's `POST model` `{ provider, model }` (`plugin/host_model.py`, `info` feature `host_model`) runs Hermes's own `switch_model` and `persist_model_selection`, as a messaging `/model --global` does: Hermes checks the pick (a refusal is a 400 with its reason, shown as a toast), only the `model.*` keys it changes are written, comments stay, and the API server reads `config.yaml` for every agent it builds, so every surface of the profile (Telegram, cron, new CLI sessions, the dashboard) runs it from the next turn. The bot then keeps no `modelChoice` of its own, so a change made in the dashboard shows here too. The field reads `provider/model`, and until the host answers it shows, greyed out, the model this device last read (`Profile.hostModel`, local only). Without the plugin feature (or reachable plugin) the pick stays the bot's own `modelChoice`, as before. Hermes locks `config.yaml` only within a process, so a dashboard save at the same moment can win over it. **The bot editor's Fallback models are the picks after that default**: up to two, read from and written to the bot's host (`GET`/`POST fallbacks`, `plugin/host_model.py`, `info` feature `fallbacks`, and `useFallbackModels` in `src/lib/fallbacks.ts`, over the read, write and grey-out both model fields share in `src/lib/host-record.ts`, which shows a write's own answer from the host as the rows), each new or edited pick checked by Hermes's `switch_model` as the main model is, so a refusal reaches the toast as the host worded it. **They are Hermes's own failover chain**: the plugin writes the profile's top-level `fallback_providers` — the key `hermes fallback` writes, which `hermes_cli/fallback_config.py::get_fallback_chain` reads into `agent._fallback_chain`, merging the legacy `fallback_model` after it, and the plugin drops that legacy key when it is there so the chain has one source of truth — so Hermes tries the rows, in order, after the main model on every surface of the profile (the gateway re-reads the chain per agent it builds, so a running chat, a routine and a new session all pick it up without a restart). The rows are the chain in the order Hermes would try it (`src/lib/fallback-list.ts` writes one slot and holds the cap of two for adding; a longer chain built with `hermes fallback` shows in full and can be shortened from Gots, never grown), cleared by removing the last one, and a row's entry keeps any endpoint or credential a hand-written entry carried. A bot whose plugin doesn't offer the route shows no field. **The bot editor's Subagent model is the host's delegation model** (`GET`/`POST delegation`, `plugin/host_model.py`, `info` feature `delegation_model`, and `useDelegationModel` in `src/lib/delegation.ts`): the model every `delegate_task` child of that bot runs on, read from and written to the profile's `delegation.provider` and `delegation.model` — Hermes's own keys, so a second opinion an AFK session asks for runs it — where the field's first row *Default model* clears both so a child inherits the bot's own model (a section that sets only `model`, or `provider: auto`, reads back under the main model's provider, since that is where its credentials point; one that sets only a provider reads back with the main model on it). A new pick is checked by Hermes's `switch_model` as the main model is, so a refusal reaches the toast in the host's words, a pick already held isn't checked again, and the section is written in one pass — so the new model never sits beside the old provider — keeping a budget, a concurrency or a hand-written endpoint, except that a pick naming another provider drops the endpoint written for the old one (Hermes reads a `base_url` as the provider being `custom`). A bot whose plugin doesn't offer the route shows no field.
- The context window is looked up in [models.dev](https://models.dev/api.json) (`limit.context`) by that `provider`/`model` (`src/lib/models.ts`). The bot remembers which model it was for and resets it when the model changes; if models.dev doesn't list the model, the window is unknown. Nothing sets a window by hand: the sheet reads the window the bot holds for the model, then Hermes's for the call that ran it, then models.dev's.
- Cron jobs are called **Routines** in the UI (`/routines`) and `cron` in code. `GET /api/jobs?include_disabled=true` (server root) returns `{ jobs }`. Each job carries `last_run_at`, `last_status` and `failure_streak`. Its `schedule` is Hermes's parsed `{ kind: interval | cron | once, minutes | expr | run_at, display }`; `src/lib/schedule.ts` puts it in words ("Weekdays at 9:30 AM", "Every 15 minutes") and falls back to `display` for shapes it doesn't know. Cron times are the host's clock, so when the next run's offset differs from the device's, the host's offset follows ("(UTC+5)"). `POST /api/jobs/{id}/pause | resume | run` control a job. A 501 means cron isn't available.
- The API server has **no run-history endpoint** (the dashboard's `/api/cron/jobs/{id}/runs` is localhost-only), so **run history needs the Gots plugin** (`plugin/`). `GET /api/plugins/memento/cron/runs?per_job=24` returns `{ jobs: { <jobId>: [run, ...] } }`, newest first, straight from Hermes's execution ledger (`status` `claimed | running | completed | failed | unknown`, plus `delivery_outcome`; a `completed` run whose delivery `failed` counts as failed). Without the plugin the route doesn't exist, and Hermes's 404 for an unknown route skips its CORS middleware, so the browser blocks it and `fetch` fails with no status. `syncCron` treats a failed plugin call as a missing plugin when `/api/jobs` on the same server succeeded, and the Routines screen shows the install commands instead. Runs aren't stored on the device.
- **Hermes Projects** (`hermes project create`, per profile in `$HERMES_HOME/projects.db`) have no API server route, so the Projects screen (`/projects`) reads them from the plugin's `GET /api/plugins/memento/projects`: `{ projects: [{ id, name, description, created_at, last_active, folders: [{ path, label, is_primary, git, repo, branch }] }] }`, where `branch` (0.17) is the one a session's worktree would start from: `origin/HEAD`'s branch, else what's checked out. The Projects screen's rows and a project name the repos, and a session not started yet shows them with that branch. Hermes stores no last-worked-on time, so `last_active` is the newest session whose `cwd` sits in one of the project's folders (the innermost folder wins, like the desktop app's grouping), and null when none has. The screen merges every bot's list, newest first; bots on the same server share one list.
- **New projects are created, and their GitHub repos cloned, on the Hermes host**, with the host's GitHub account: `GITHUB_TOKEN`, then `GH_TOKEN` (process env, then `$HERMES_HOME/.env`), then `gh auth token`, the order Hermes's own GitHub calls use. The token never reaches the app. `GET /api/plugins/memento/github` reports `{ connected, login? }`, `github/repos` lists the account's 100 most recently pushed repos, and `POST projects` takes `{ name, description?, repos: ["owner/name"] }`. It makes `$HERMES_HOME/projects/<slug>/` (the profile's home, so profiles stay apart; the slug is the one `projects.db` gets), clones each repo into it over HTTPS (the token goes in an `http.extraheader`, so it isn't saved in `.git/config`), and creates the project with that folder as its primary and each clone as a folder. A repo in two projects gets two clones. Without an account, public repos still clone by name.
- **Creating a project is asynchronous** (`plugin/clones.py`), so it carries on with the app closed. `POST projects` validates, makes the folder, records the project in `memento.db`'s `project_clones` table and answers **202** with it at once; a daemon thread then clones each repo. Until the last clone is in, the project is `pending-<slug>`, **not in `projects.db`**: a project there is always whole, so a session can never get worktrees in only some of its repos, and Hermes's own dashboard never sees a half-made one. `GET projects` lists it after the real ones with `status: "cloning" | "failed"` (real projects carry `ready`; the app reads an absent `status` as ready, for an older plugin), `error`, and each folder's `status` (`queued | cloning | done | failed`). The last clone creates the real project (new id) and drops the row. A failed clone removes the folder and keeps the row with its error until `POST projects/{id}/retry` (starts over) or `…/remove` (also cancels a running clone: `github.clone` takes a cancel event). A restart mid-clone clones again from scratch (`clones.resume`, at startup for the default profile and on the first `GET projects` for any other). A pending project can't be edited (409) or opened; the Projects screen shows it with Cloning n of m, or the error with Retry and Remove, and polls every 3s while one is cloning. `info` reports `projects_async`.
- **A ready project's repos are added and removed asynchronously too** (`plugin/repos.py`, `memento.db`'s `project_repos`). `POST projects/{id}/repos` `{ repo }` answers 202 and clones on a daemon thread into `$HERMES_HOME/projects/<slug>/`; the repo joins `projects.db` (`add_folder`) only once the clone is in. `POST …/repos/remove` `{ repo }` takes it out of `projects.db` at once (`remove_folder`) and deletes the clone on a thread, only when it's one the plugin made (a folder of a project folder under `$HERMES_HOME/projects/`) and no other project uses it; for a repo still being added it cancels the clone. `GET projects` lists such repos among the folders with `status: "cloning" | "failed" | "removing"` (and `error`), and a restart picks them up again (`repos.resume`). **While a repo is being added, no new session can start** in the project: the New session pop-up shows the project greyed out with the reason, and `POST sessions/{id}/workspace` answers 409 for a session with no record yet. **A session that works in a removed repo is read-only**: the workspace post answers 409 with the reason, and both workspace answers carry it as `blocked` (`Conversation.blocked`, local), which the chat shows in place of the composer (`BlockedCard`). An archived project blocks its sessions the same way.
- **Projects can be pinned, archived and measured.** `POST projects/{id}` also takes `archived` (Hermes's own `archive_project` / `restore_project`) and `pinned` (the plugin's `project_pins`, since Hermes has no pin). `GET projects` lists archived projects too, with `archived` and `pinned_at`; the Projects screen puts pinned ones first and archived ones in a folded group. `GET projects/{id}/usage` sums `input_tokens`, `output_tokens`, the cache counts and `actual_cost_usd` (else `estimated_cost_usd`) over the `state.db` sessions whose `cwd` (or their root's) sits in one of the project's folders (read-only), folding compression children into their root as one session, and lists each one as `threads: [{ id, title, started_at, last_active, models: [{ model, <the four counts>, cost_usd }] }]` (0.21). A session's `model` column is overwritten on a mid-session switch, so the split comes from `session_model_usage` (each call under the model that ran it, auxiliary calls included) and whatever those rows don't cover is counted under the session's own model; the totals stay the session rows', so the split can't disagree with them. An older Hermes without that table falls back to one model per session. The Usage view (`project-usage.tsx`) shows the totals, the split by kind and each session's share, and its **Est. cost** comes from `src/lib/pricing.ts`: Anthropic's first-party prices for a Claude model id (cache writes as Hermes's default 5-minute writes; Bedrock and Vertex sessions are priced the same), Hermes's own cost for any other model, and a `+` when some usage had neither. Update the price table when Anthropic's prices change.
- **Dictation is the host's own faster-whisper, through the plugin** (`plugin/dictation.py`, `src/lib/dictation.ts`; decided with Haseeb 2026-10-12, plan: https://claude.ai/code/artifact/059a9f63-6ba4-42c5-b145-f52b5fd684b2). Hermes's transcription routes (`POST /api/audio/transcribe`, `/api/audio/stt-lease`) live on the dashboard, whose CORS allows only `localhost`, and the API server reports `audio_api: false`, so the plugin serves `POST dictation` and `POST dictation/warm`, and `POST dictation/cleanup` tidies a finished dictation's whole text (see **Plugin**). The app records mono Opus at 24 kbps with `MediaRecorder` (`audio/webm` in Chrome and the Android WebView, `audio/mp4` in Safari; faster-whisper decodes either with its bundled PyAV), and warms the model when the mic opens. Hermes streams partial text only for its cloud providers (`tools/transcription_streaming.py`), never for the local model, so **the recording is cut at the user's pauses** and each piece is sent while they carry on: a level meter on the same stream (a `setInterval`, so it runs without animation too) cuts a piece of 6s or more at 700ms of quiet (one of 25s or more at 350ms), quiet being under a few times the room's own noise floor, by starting a new `MediaRecorder` on the stream before stopping the old one, so every piece is a whole file and nothing between them is lost. Pieces are transcribed one at a time in order, each with the text before it as `context` (plugin 0.35; Whisper's prompt is what was just said), so on Stop only the last piece is left to wait for; a piece that fails is tried again with the next one, and on Stop. **A recording is kept on the device until its text is in** (`db.dictations`, under the composer's draft key, its pieces and their text so far, the open piece saved every 2s), so a reload, leaving the chat mid-recording or a failed host keeps it: the composer shows it again with Retry and Discard. A kept take remembers the caret it began at, so its text lands there rather than at the end of the draft. **The mic works only when the bot's `info.dictation.ready` is true** (read on mount and every 5 minutes, again after a failed clip, and kept when a later read fails, so it doesn't flicker): it's greyed out and inert while the host is first asked, and greyed out with a pop-over saying why when the host says no (no plugin, an older one, faster-whisper missing or `stt.enabled: false`, with the plugin's reason) or couldn't be asked (a tap asks again). There is no Web Speech fallback. A tap toggles recording (the voice bar takes the mic's place under the finger, so its buttons only answer a press that began on the bar, or the keyboard); a press held 400ms or more is push-to-talk (letting go finishes, letting go 80px away cancels). The text goes in at the cursor, or Send sends it; a recording under 300ms is dropped. Clips stop at 10 minutes. In the Android app the WebView's `getUserMedia` needs `RECORD_AUDIO` and `MODIFY_AUDIO_SETTINGS` in the manifest (Capacitor's `BridgeWebChromeClient` asks for both). `MOCK_DICTATION=off|fail` in the mock hides the mic or fails every clip. **A dictation's words land when it ends, tidied once** (`POST dictation/cleanup`, ADR 0038): the joined text of its pieces and the bot's vocabulary go in one call on the bot's cleanup model, and the tidied text lands in one write at the caret the dictation began at. A cleanup that refuses, misses its budget, fails or answers junk lands the words as the host heard them and never fails the dictation, so the raw words are always what is left when the tidying isn't. **The bar keeps the composer's place and shows no words**: the level waveform, the elapsed time, the status line (`Transcribing…` while it ends) and Stop, Send and Cancel, so nothing can be read out of a take until the whole of it lands in one write. **A take ends inside one wait, so a slow host can't hold the composer** (`SEND_WAIT_MS` 4 s, `STOP_WAIT_MS` 8 s, ADR 0038; `finish(waitMs)`): a Stop waits longer because it is the user asking for the whole take — the pieces still with the host and the cleanup that tidies them both have to fit — and a Send waits shorter because it is in front of the user. The wait is one deadline for both: the pieces drain first, then the end cleanup spends whatever is left of it, and it is a race as well as an abort, so a host that never answers and a transport that never gives up both end it. Past the wait the take goes with what it has: the pieces whose text is in are the take, the piece still with the host is let go, and there is no room left to tidy it. A second Stop (or a Send behind one) while a take is ending does nothing more, and Cancel aborts the request in flight and the recorder at once: a cancelled take inserts nothing, keeps nothing and releases the mic, even when an answer already asked for arrives afterwards. One take at a time per profile is the app's rule (`src/lib/dictation-lock.ts`, held from the start of a take to its end, with a token a take that ends late can't take from a newer one): a second composer on the same bot is refused before its mic is asked for. **A take that fails says so** (`src/lib/dictation-failure.ts`): one line in the bar names what failed — the host's own words where it gave them — and the one thing to try, dismissible, with Retry wherever one might help (a microphone permission only the user can change is the one failure with none), and the take stops cleanly from it: the mic released, the words already in still inserted. **A bot's vocabulary biases the take** (`src/lib/vocabulary.ts`, `src/components/bot-dictation-tab.tsx`, on the Dictation tab of its editor, which exists only where the host advertises `dictation` and lands a bot on an older plugin on General): the names and words its dictation is written with ride on every piece's transcription as one repeated `vocabulary` query param each, and on the end cleanup's body, so each decode and the tidying are told them — after the host's own prompt, before the text already committed — and a name the host would otherwise hear as a common word comes back spelled as the user spells it. The list holds each word once however it is cased, is capped at fifty with the newest kept, and is read as it stands when a clip is sent and again for the end cleanup, so a removal lands on the next dictation; it lives in the bot's own record, so it syncs last-write-wins like its title. `scripts/test-vocabulary.mjs` pins those rules, and `scripts/test-bot-dictation-tab.tsx` the tab. **The model that hears a dictation is the host's, and the Dictation tab picks it** (`plugin/speech.py`, `src/lib/speech.ts`, `src/lib/host-speech.ts`, `GET` and `POST speech`, `info` feature `speech_model`; ADR 0036): the list is Hermes's local faster-whisper family, each row with its download and how many seconds of speech it hears in a second on a CPU, marked *Too slow on a CPU* where it can't keep up, *Not on this host* where it still has to download (the warm that opens the mic downloads it), and *In use* on the one in play. A pick is written to `stt.local.model` in one pass through Hermes's round-trip YAML writer — every other speech setting and comment survives — and lands on the next clip, never mid-clip. A pick the host can't load fails the clip with the host's reason, which the failure line shows, and changes nothing the settings hold, so the next clip tries the pick again. A write Hermes refuses writes nothing and its own sentence is what the tab shows beside the model still in place. **Cleanup's model is one line on the same tab** (ADR 0036): the pick is kept in the host's settings store per bot, read per request, so it survives a plugin restart and lands on the next dictation; where the host withholds `llm.model_override` and `llm.provider_override` the tab shows the host's explanation in place of the field and a stored pick is ignored anyway (the cleanup then runs on the bot's own model). `scripts/test-speech.mjs` pins the row rules, `scripts/test-host-speech.tsx` the two writes, `scripts/test-bot-dictation-tab.tsx` the picker, its refusal and the gate, and `plugin/tests/test_speech.py` the catalogue, the write, the load failure and the permission. `scripts/test-dictation-kept.mjs` pins what a kept take holds and how often it is written, `scripts/test-dictation-kept-offer.tsx` the offer, the insertion at the caret and what discarding and a deleted bot or chat remove, `scripts/test-dictation-lock.mjs` the profile's one take, `scripts/test-dictation-ending.tsx` how a take ends through the composer (no words on the bar while it runs, a Stop's tidied text at the caret in one write, a Send that waits for the cleanup, a cleanup that fails, answers junk or hangs landing the words as they were heard, a clip that never answers, a Cancel while the cleanup is in flight, and a second composer refused), `scripts/test-dictation-failure.mjs` the failure rules, and `scripts/test-dictation-failing.tsx` the line the bar says and its Retry. `pnpm e2e dictation` covers the pieces landing tidied at the end with the bot's words on the clip and the cleanup, a Cancel that inserts nothing, a recording kept across a reload, and a refused take and a host that goes away each saying so.
- `GET /api/sessions/{id}/messages?order=latest&limit&offset` (server root) pages a session's transcript back from the newest row, but returns each page oldest first. Rows carry `id` (increasing), `role`, `content`, `tool_calls`, `tool_call_id`, `tool_name`, `timestamp` (Unix seconds), `reasoning` and `display_kind` (`hidden` rows are compaction scaffolding; skip them). Gots uses it to fill in chats synced from another device, a whole turn at a time: a reply is named after its first row (`h-<session>-<row>`), so the first page and each "Load earlier" page back to a turn's start (`fetchTail`, `loadEarlierHistory`), and a part of a turn loaded on its own by an older version is replaced by the whole turn. Older pages sort before the chat's first message and a new turn after its last, whichever clock stamped them. A `role: user` row starting `[System:` is a note Hermes wrote to keep the turn going (a reply cut off by the network or the output limit, a fragment it asks the model to send again, a verification nudge); it's never shown and doesn't start a turn (`isNotice` in `history.ts`). The reply's text before it, back to the last tool call, is joined with what follows the way Hermes joins them for the run's `output` when the note asks to continue "where you left off" (unless the model started over), and replaced otherwise. Live, the stream never carries the note but streams every attempt, so a completed run's `output` replaces the text streamed since the last tool call when they differ (`settleFinalText` in `chat.ts`).
- **The agent's todo list is Hermes's `todo_list` tool** (`tools/todo_tool.py`), not Kanban: one list per session of `{ id, content, status: pending | in_progress | completed | cancelled, parent? }`, where each call returns the whole list with a `revision` and is stored as a `tool` row (written after every tool round, so mid-turn too). It's a deferred tool by default (`tool_search.defer`) and a saved `platform_toolsets.api_server` without `todo` leaves it out of reach, so the plugin adds its definition to every agent the API server builds (`todos.wire`, over `_create_agent` like `clarify`; `info` reports `todo_tool`), whatever the user's tool config says. `startRun` sends a fixed `instructions` line (Hermes appends it to the system prompt) asking the agent to plan with it on work of three or more steps. The plugin states the list's own progress (`{ done, total }`, a cancelled item counting for neither) and each item's depth under its parents with it, so the app draws and counts only what it is given and reads nothing out of the run's result preview, which is cut at 500 characters anyway. Once the turn is over, an item still `in_progress` shows as stopped (a pause icon, in the pill too) rather than spinning. Kanban cards are shared, dispatched work on a board every profile sees, so they aren't used for this.
- **Project sessions work in git worktrees, through the plugin.** `POST /v1/runs` takes no working directory, tool list or approval mode (its fields are `input`, `session_id`, `instructions`, `conversation_history`, `previous_response_id`, `model`, `provider`, `model_options`, `author`). What it does have is a tool `task_id` equal to the `session_id` we send, and `tools/terminal_tool.py`'s `register_task_env_overrides(task_id, {"cwd": path})`, which makes `path` the session's cwd for the terminal and file tools (in memory only, keyed under the routed profile scope). A session spans its whole project: `POST sessions/{id}/workspace`, which `sendMessage` posts before every turn (`workspace.ts`), makes a worktree in every git folder of the project on the first post, with Hermes's own `hermes_cli/worktree_ops._setup_worktree` (`<repo>/.worktrees/<slug>`, branch `hermes/<slug>`, locked), registers the primary repo's as the cwd, and answers with an `instructions` line naming every worktree and the session's library folder, which `startRun` adds to the run's `instructions` (fixed per session, so the prompt cache holds). Hermes's `-w` and `/worktree` are CLI-only; the gateway's own cwd is `terminal.cwd`. **Directories never reach the UI:** repos are named `user/repo` from each clone's GitHub `origin` (`folder.repo` on the projects route, `name` on a workspace's repos), and the app shows the branch, never a path.
- **Permission modes are Gots's, not Hermes's.** Hermes's `approvals.mode` is global config, and it only prompts for dangerous shell commands (and an SSH-config write), never for ordinary edits. So a project session's mode (`Conversation.mode`, held by the plugin) is: `accept_edits` (the default; Hermes's native behaviour), `auto` (the plugin's `pre_tool_call` hook turns on Hermes's own per-run approval bypass, `tools.approval.enable_session_yolo`, keyed by the run id, which is the approval key `get_current_session_key()` returns inside the hook (hooks run on a copy of the caller's context); the hook switches it off again when the mode isn't Auto, so a mid-run change applies to the next tool call. The bypass skips the prompt only: Hermes checks its hardline blocklist first, so that still blocks. Nothing needs the app open. Switching to Auto resolves, once, any approval a run of the session already waits on, except a guardian's DENY. The app doesn't answer approvals itself, so Auto needs the plugin and the Mode list disables it, with the reason, on a bot without one, where a session left in Auto shows as Accept edits), and `plan` (the plugin's `pre_tool_call` hook blocks `write_file`, `patch`, `execute_code`, `delegate_task`, `pull_request`, `library_add` (it moves a file out of the worktree) and any `terminal` command that isn't a plain read; the workspace's `instructions` carry the plugin's plan-mode line, which asks for the whole final reply to be the plan in a fixed shape: `# Plan: <title>`, overview, approach, changes, checkpoints that each name their commit message in Conventional Commits form, verification, risks and assumptions; before writing it the agent settles every open choice, asking the user with the `clarify` tool where it can and recording its own decision where it can't, so a plan never leaves a question for the user). An "ask before every edit" mode would equal Accept edits today; the hook's `{"action": "approve"}` return could add one later.
- **Plans are files on the Hermes host.** The plugin's `post_llm_call` hook saves a plan-mode reply that has the `# Plan:` heading as `plans/<branch slug>-<YYYYMMDD-HHMMSS>.md` under the project's primary folder (`$HERMES_HOME/projects/<slug>/plans/` for projects the plugin created), with a YAML front matter (`session`, `branch`, `project`, `created`); every iteration is its own file, and `plans/` goes into the folder's `.git/info/exclude` when the folder is itself a repo. The workspace reports the newest as `plan_file` (`Conversation.planFile`, local only), and approving the plan (in Auto, or in Accept edits, which the plan card offers side by side) sends the agent to that file's checkpoints, each committed on the session branch with the message it names. Hermes doesn't fire `post_llm_call` for an interrupted turn, so no half-written plan is saved.
- **Session states** (`sessionState` in `src/lib/session-work.ts`, re-exported by `workspace.ts`): `discarded` (`Conversation.discardedAt`, synced), `resolved` (`Conversation.resolvedAt`, set by the user or by the plugin when the session's pull request merges, synced), `waiting` (an unanswered approval or question here, `waiting_for_approval` from the plugin's `GET runs/live`, a pending plan, or an AFK session nothing is working any more — `{ kind: "stalled" }`, whose reason the host gives), `working` (a reply streaming here, `running` from `runs/live`, or — `subagents` — a chat whose turn ended but whose subagents the host still runs, `runs/live`'s `subagents` map read through `useLiveSubagents`), else `idle`, which is where a draft session sits too (`Conversation.draftAt`, set when the user leaves a session they typed in and saves the draft, synced; the text is the session's composer draft, below; a session nothing was sent or saved in is deleted when the user leaves it, and the Code screen hides any that remain). The Code screen's grouping (`sessionGroup` in `workspace.ts`) reads an idle session with an open pull request as `waiting` — to be reviewed and merged — except while that pull request's checks are still running, which is `working`. `runs/live` reads the API server adapter's in-memory `_run_statuses` (`queued | running | waiting_for_approval | stopping` and the terminal ones); Hermes has no run-list endpoint.
- **A session's pull requests** are found by the plugin on GitHub (`GET sessions/{id}/prs`, one per repo of the session): the branch as `head` on the repo's `origin`, with the host's token when it has one, plus `checks` (`success | failure | pending | null`) from the head commit's check runs and legacy statuses. Hermes tracks no PRs itself. The PR pill is coloured by state (green open, grey draft, purple merged with the `--merged` token, red closed) and orange when the checks fail, or while they run — with a spinning loader instead of the alert icon (`prLook` in `src/components/chat/pr-look.ts`, read by the pill, the PR row and the Code screen's second line). While any pull request of the open session has checks pending, the app reads them again every 10s (`PR_PENDING_MS` in `freshness.ts`, an interval on the session, Code and project screens; `refreshPrs` drops its 30s trust window to match), and the plugin's per-branch PR cache (`PR_PENDING_CACHE_S` in `plugin/github.py`) expires a pending-checks entry after 10s rather than 30, so a check that finishes shows up at once. On the Code screen a session whose pull request's checks are still running groups as `working` (a spinner), and as `waiting` once they settle either way. The plugin's own 5-minute news pass that pushes failing checks keeps its interval.
- **The agent ships a session's work itself, with the plugin's `pull_request` tool** (`plugin/ship.py`; `action` is `ship`, `push`, `update` or `status`, and `merge`/`close` are refused with a message to ask the user; pull requests are always drafts); the app never pushes or manages pull requests, it only shows their state. The plugin registers the tool (`ctx.register_tool`, toolset `memento`) and adds it to every agent the API server builds (`ship.wire`, like `todos.wire`), and the workspace's `instructions` tell the agent to call it once the work is done and checked, without asking, and name each repo's pull request template (`ship.template`: `.github/pull_request_template.md` and the other standard places), else Summary, Changes and How to test. The same instructions add two emphases for a finished task (`DONE_INSTRUCTIONS` in `prompt_builder.py`, echoed word for word in `scripts/mock-hermes.mjs`): don't share the pull request url or the commit message in the reply, since the `pull_request` result and the session's PR list already surface them where the user sees them; and update the todo list to its final state — every item completed, or cancelled where it was dropped. The handler finds the session by its `task_id`, commits what's uncommitted in each worktree with `commit_message` (`git add -A`; a host with no git identity commits as the GitHub account's no-reply address), pushes `HEAD` to the branch on `origin` with the host's token as an `http.extraheader` (like the clone), and opens a pull request into the branch the session started from with the GitHub API, or just pushes when one is open; the body ends with the Gots Code footer (`PR_FOOTER` in `sessions.py`). Each repo goes on its own: one failing returns its `error` and the others still ship. Plan mode blocks the tool. Approving a plan asks the agent to open the pull request once its checkpoints are committed.
- **The agent files its generated files with the plugin's `library_add` tool** (`plugin/library.py`, registered and wired exactly like `pull_request`). The screenshots, images, charts, reports and markdown a session makes for the user belong under the session's library folder — `<project's primary folder>/files/<worktree slug>/`, computed when the worktree is made and kept on the session row as `files_dir` (schema v15) — not in the worktree, so they stay out of the branch's diff and the app's Library tab can link them later. The workspace's `instructions` tell the agent to file each generated file with the tool (`prompt_builder._LIBRARY_RULES`, in the section every session shares, naming no path) and name the folder once under `## Current Session` (`_library_folder_line`); the handler finds the session by its `task_id` like `ship.handle` does, resolves a relative path against the session's cwd, and files the file at `files_dir/<folder>/<name>` — the `folder` argument is required, one level. **Folders and file names are kebab-case slugs** (`^[a-z0-9]+(-[a-z0-9]+)*$`; a file name is a slug plus one extension, `dashboard-light.png`), and folders are named after the flow or change the files belong to — `library-tab` for work on the library tab, `library-tab-tree-view` for a follow-up change to it — never the file type, so one project's library reads as a tree of what was done; the tool's description and the `instructions` teach this. A name that isn't a slug is an error, never rewritten, carrying the rule and the nearest correction (`'Library Tab' is not a slug (kebab-case: …); name the folder after the flow … Call again with folder 'library-tab'.`); a file name that isn't one tells the agent to rename it on disk first. The folder is created if it needs to (a row from before the column resolves it from the project, the way `save_plan` resolves `plans/`) and `files/` goes into the project clone's `.git/info/exclude` like `plans/`; the answer is `{ name, path }` with the new absolute path, which the agent can then reference with a `MEDIA:<path>` tag for an image. A file of that name already in the folder is an error naming the file and the folder — the agent renames it and calls again, and nothing is renamed for it.
- **AFK's frontier is read from GitHub and listed.** The project screen's options menu carries an AFK row where the Bot's plugin advertises `afk`, opening a sheet that lists the project's tasks as AFK reads them: `GET projects/{id}/tasks` (`plugin/tasks.py`) answers `{ repos, ready, claimed, blocked }` — ready oldest first, claimed carrying the assignees that took them, blocked naming the open blockers (`{ repo, number, title, url }` each) — or the Host's own reason as an error, a Host with no GitHub account included. The rule is one pure function, `groups()`, over the rows the read already fetched — the ready group is the frontier, and the claimed and blocked ones are what is out of it (`GLOSSARY.md`) — so it's tested with fabricated rows (`plugin/tests/test_tasks.py`): a task is AFK's at all only when it's open and marked `ready-for-agent`; it's claimed, and out of the frontier, when it carries an assignee or the `gots-got-it` mark; blocked while any blocker is open; ready otherwise. Each repository is asked for its open ready-marked issues (`state=open&labels=ready-for-agent`, oldest first), following GitHub's `Link` header from one page to the next so a repository with more ready tasks than a page holds still has all of them read, and pull requests are dropped from the answer. A blocker is GitHub's own issue dependency — `issue_dependencies_summary.total_blocked_by` says whether an issue has any edges at all, and `dependencies/blocked_by` names them — with a `Blocked by: #n` line at the top of the body read *only* for an issue with no native edges: each number is looked up so a closed blocker is known to be closed, one that doesn't exist blocks nothing, and one that can't be read counts as open, since working a task ahead of its blockers is the worse mistake. `src/components/afk.tsx` reads the route each time the sheet opens and keeps nothing on the device; `src/lib/features.ts` is the shared answer about what a Bot's plugin advertises, which the row and the MCP screen both gate on.
- **A bot's workflows are its library, and a task keeps the one it started under** (`plugin/workflows.py`, `workflows` in `memento.db`, schema v29). A workflow is `{ name, stages }` and a stage `{ name, steps, ships, check?, loop? }` — the skills it follows in order, whether it is the stage that ships, the check the host answers itself (the gate, and nothing else), and the stage a loop restarts from with its cap. Three presets — One run, Build · Test · Review · Summary, Build ⇄ Test · Review · Summary — are seeded on first read under fixed ids (`preset:one-run`, `preset:staged`, `preset:loop`) and refreshed in place when the plugin's version moves (`_version`, off the package metadata), so a body a later build ships reaches a store that already seeded the earlier one without a project losing its pick; a preset the user deleted is not seeded again (the row stays with `deleted = 1`). A preset body is never written: `update` on one forks it into a row of its own with a new id and the name the write gives it, else the preset's own name with ` (copy)` after it. `normalise` is the one rule over a whole workflow, used by the host's write and by the app's editor: a name is required, stage names are trimmed, non-empty and unique within their workflow, at most twelve stages, a loop's cap is 1–10 and starts at a stage before the one it ends on, and exactly one stage ships — which can't be a gate stage, since a gate stage posts no run and a workflow shipping from one would never open a pull request (One run ships from a stage that names no check at all), while a stage naming both steps and the check is refused, since a stage either runs its skills or is answered by the host. `delete` is refused (`Refused` → 409) while a project names the workflow, and the message names those projects (`_projects_naming`, off `projects.db`); a project whose pick is gone reads as One run and works one prompt run. The library is routes — `GET workflows`, `GET workflows/{id}`, `POST workflows`, `POST workflows/{id}`, `DELETE workflows/{id}` — advertised as the feature `afk_workflows`, which the app's picker and editor are gated on (#338). Tested over a temp store in `tests/test_workflows.py`: the presets and their refresh, forking, the rule, the delete refusal, the migration and the snapshot.
- **AFK's switch is the project's own setting on the host** (`plugin/afk.py`, `project_afk` in `memento.db`, schema v26). `GET projects/{id}/afk` answers `{ on, reason, task, refusal, workflow, prompt, stage, stage_name }` — the switch, why it can't be on, the task AFK holds, the last reason GitHub refused its sweep, the workflow the project's work runs under (`workflow`: the whole library entry, `{ id, name, preset, at, stages }`, where the project names one — `project_afk.workflow_id`, schema v29, see **A bot's workflows are its library** — and One run where it names none, since a project that picked nothing works one prompt run (ADR 0027); a project whose old `build_skill`/`critique_skills` columns hold something is read as the workflow they described, written once into the library, so it keeps exactly the shape it had) and the stage the task it holds is in (`stage`: `build` | `gate` | `critique` | `done`, or null when it holds none and when its task isn't staged, read off the session working it — `project_sessions.pipeline`, schema v29, see **AFK stages a task**) and the Prompt its work is told (`prompt`: the project's own words for how the work is carried out, `project_afk.prompt`, schema v30, or the bot's default method `prompt_builder.DEFAULT_PROMPT` where it has written none, so neither the app nor the device holds a copy of it) — and `POST` with `{ "on": true | false }` writes the switch, with `{ "workflow_id": "wf-…" }` the workflow it runs, or with `{ "prompt": "…" }` the Prompt it is told (one shape per write, never three; an id the library doesn't hold is a 400 that writes nothing, and a Prompt write clears any workflow pick in the same statement — a project is never both — with a blank one clearing the field back to the default), answering the same shape; the app shows a switch in the AFK sheet — always in place, its label reading `Turned off` or `Turned on` — left live where the project can be worked and turned off and disabled with the reason under it where it can't — no GitHub repository in any of its checkouts, no GitHub account on the host, or the project archived — because the sweep that would do the work runs there, with the app closed. A project already left on keeps its switch when its reason comes back (the account it read tasks with is gone, say), the reason shown under it: turning it off is still the user's to do. With the workflow library off, the sheet draws a Prompt row under the switch instead, reading the Prompt the read answers — the project's own words or the default — and writing it back as one `{ "prompt": "…" }` write through its editor (`afk-prompt.tsx`) — Done on words nobody changed closes without writing them, so the bot's default never becomes a project's own. Turning a project on is refused with that reason and writes nothing, so the host never holds an on it refused; turning one off is always allowed. Archiving a project turns its switch off (`projects.update`) and deleting one forgets it (`projects.remove`). `info` advertises the route as `afk_switch`, apart from `afk`: a plugin that lists a project's tasks but was never able to switch AFK on shows the switch off and disabled, with nothing under it, rather than a control that could only fail. It advertises `afk_prompt` for the Prompt, which an app that predates it answers without and so keeps the sheet it has, and `afk_workflows` for the picker.
- **AFK claims the oldest ready task, one per project** (`plugin/afk.py`, `github.claim_issue`). With the switch on, a sweep on the host reads the project's frontier (`tasks.read`) and takes the oldest ready task: the `gots-got-it` label applied and the issue assigned to the host's GitHub user (`github.login`), in that order, and a refused assignment takes the label back off (`github._unlabel`, best-effort) so a task a failed claim half-touched returns to the frontier instead of being left marked as claimed with no sweep holding it. The label is created on the repository the first time it's used (`_ensure_label`; a 404 on the label read is GitHub's "Not Found"), because a label that doesn't exist can't be applied (ADR 0012). `afk.sweep` does one project, `afk.sweep_all` every project the store says is on (`enabled_projects`) and every one still holding a task, and `afk.run` is the loop started beside the other background loops: it sweeps at once on start, then every `SWEEP_SECONDS` (three minutes), and immediately when `afk.wake` is called — from a write that turns the switch on, from `afk.after_run` (the `on_session_end` hook) when a project session ends, not a chat's turn, and from the close route once it has given a closed session's task back. It sweeps every home the process serves (`link.served_homes(adapter)`, as the check-in loop does), so a bot at `/p/<profile>` is worked from its own store too. One task per project at a time: a project holding one (the row's own `task`) is left alone, and the hold is the host's record (`project_afk.task`/`claimed_at`/`session_id`, schema v26), not the app's. The hold lasts as long as the run working the task (ADR 0015): a run that finishes lets go of the hold but leaves the claim on GitHub, since the work is in review; a run that fails or was interrupted keeps both the session and the claim and records why (`project_afk.stalled`/`stalled_at`), so the session is reported as waiting rather than working; the user closing the session — discarded, resolved or deleted, read off the chat list so a close made on any device counts, and by `afk.release_session` from the close route — gives the claim back (`afk.release` → `github.release_claim`: the label and Gots's own assignment, since a task carrying either is out of the frontier), and so does a start that never got its run away, so the task returns to the frontier where the next sweep may take it. A hold is settled whatever the switch says — `sweep_all` sweeps the projects left on *and* every one still holding a task, for its hold alone — so a project switched off mid-run still gives its task back when the session is closed, and the switch only decides whether a new task is taken. Releasing is best-effort on GitHub: a refusal is recorded for the sheet and the hold goes anyway, because nothing on the host is working the task either way. A reason the project can't be worked — no repository, no account, archived — is the switch's own (`afk.reason`), so the sweep returns without recording it; a GitHub refusal — no permission to write issues, a rate limit, no connection — leaves the switch on, records its reason (`project_afk.refusal`/`refused_at`) and stops that sweep, so the sheet says why instead of the app retrying; the next sweep is the next attempt, and a sweep GitHub answers clears the reason. The claim is tested through the plugin's HTTP stub (`tests/test_afk.py`, `ClaimStubTests`); `sweep` answers the task it just claimed, so the loop starts its session without a second read. A project whose chosen build or critique skill its bot's profile no longer has claims nothing and records `afk.MISSING_SKILL` as that refusal, with the switch left on so the sheet says what to fix; the names are judged against the home's own `skill_catalog.read`, once a sweep (`afk._profile_skills`), and a host that can't list its skills judges nothing.
- **AFK works the task it claimed in a session of its own** (`plugin/afk.py`, ADR 0013, ADR 0027). `sweep` answers the task it claimed and `sweep_all` the project-and-task pairs; `afk.sweep_homes` starts each one after that home's sweep, on the loop. `sessions.ensure` makes the session the way the app's workspace route does — its own worktree and branch in every repo of the project, mode `auto`, an id of `memento-afk-…` that the plugin's own hooks label — `sessions.apply_cwd` points its tools into the worktree, `outbox.post` starts the run on the profile's API server, and `publish` then writes the chat record that makes it appear and open in the app — after the run is accepted, so a start that fails leaves nothing in Code to open. The run's input is the issue itself (`prompt_builder.afk_input`): a `Title:` line, `Description:` and the body verbatim, then `[Issue #<number>](<url>)`, because the description is what the change is judged against (ADR 0027) — the body comes off the read that claimed the task, so nothing fetches it twice, and only the run that starts a task gets the block, a staged task's later runs keeping their one line naming the stage; its instructions are `prompt_builder.afk_prompt` — every word the agent is told lives in `prompt_builder` — which is told in the same sections as every other run's — `## You are Gots!` with the tools and the rules for them, `## Away From Keyboard` with AFK's own words (`_AFK_OPENING`, then the fixed points in `_AFK_RULES`), then `## User's Workflow` holding the project's **Prompt**: how the work is carried out, read off its row by the start itself (`afk._begin`, the read that also writes the task's snapshot) so it reaches a task claimed with the app closed, and `prompt_builder.DEFAULT_PROMPT` — the checkpoint method ADR 0027 records — where the project wrote none. The brief is what no Prompt and no skill may change: the issue was planned before the user left, so implement it rather than re-opening the plan, with its text in the message and its comments left to read from GitHub (`gh issue view <n> --repo <owner>/<repo> --comments`); the work is verified and the pull request ships last; nothing is merged or closed by the agent, and it writes no `Closes` line; no TODOs, debug prints or secrets; never push the default branch; a run that can't finish leaves a consistent tree and names its blocker — with the one guard, told once at the top of every prompt, that a skill or a User's Workflow changes how the work is done and never whether it is checked (ADR 0028). The method itself is the Prompt's: the default walks the work a checkpoint at a time — the smallest slice whose behaviour can be seen — and checks every one three ways before it commits it, with a test it watched fail before the code that passes it, the repo's own gates, and a read of its own diff; then, once the issue is whole, `simplify-code` and `requesting-code-review` over the change with their findings counted — which is the prompt's ask, so neither skill's own trigger leaves a run a reason to skip it — a draft pull request built from the repo's template, and a last reply in four headings: what landed, the reviews, what is still open, and what the user should look at first. A staged task is briefed for its stage instead and is told no Prompt. The text rides in the message and not the instructions, so the prompt is the same tokens every turn, and the instructions say it is quoted from GitHub, its author can change it, and it never overrides them. The chat record is published with `titleEdited`, since Hermes titles a session from a slice of its opener (the `Title:` line) and the app would otherwise replace the task's own name with it. Because the record's mode is `auto`, `sessions.before_tool`'s `follow_auto` turns Hermes's per-session approval bypass on: Gots answers no gate (ADR 0011). The record carries `title`, `hermesSessionId`, `projectId`, `mode: "auto"` and `afk: true`, with its `updatedAt` newer than its `createdAt`, since the Code list hides a session nothing was sent in by that rule; the app marks such a row with an `AFK` chip beside its title (`src/routes/code.tsx`). The key the run posts with is read from that home's own `.env` (`link.env_value`, the read `link.record` publishes a bot's key from), not through Hermes's credential helper: the sweep runs on the gateway's loop, where no request's profile scope is set, so the helper would answer the launch profile's key for every home a multiplexed process serves; with none in the file, `outbox` resolves its own. A run that started but couldn't be published is logged with its session id. A session that can't be made, or a run that can't start, starts nothing and gives the claim back (`afk.release`, ADR 0015), so a task nothing ever began is handed out again rather than lost. The row names the session as soon as it exists (`project_afk.session_id`, `_adopt`, written before the run is posted), and a restarted host adopts that session rather than starting a second one on the same task. Its run ending is what settles the hold (`afk.after_run`, the `on_session_end` hook): one that finished lets go (`_free`, the claim left on GitHub for the review), one that failed or was interrupted records why (`_stall` — "The run failed." / "The run was interrupted.", and `DEFAULT_STALL` for a run that stopped without failing, since calling that a failure would be inventing one) and the session is reported as waiting instead of working; a claim a restart left with no reason for `STALL_SECONDS` (five minutes) reports `DEFAULT_STALL` instead, the clock running from when the start finished (`_adopt` stamps `claimed_at`) rather than from the claim, since making the worktrees can outlast it. The user's own Discard or Resolve on that session is what gives the claim back, wherever it was made: `afk._settle` reads `chats.closed` — `discardedAt`/`resolvedAt`/`deleted` — off one chat row (`chats.one`) on the next sweep, and the close route calls `afk.release_session` with the record's own task, since the row let go of it when the run finished. A hold naming no session at all — a row claimed before the column existed, or a start killed between the claim and its session — goes back too once it is older than `STALL_SECONDS`, because nothing on the host can be working it; and the sweep that gives a task back claims nothing more in that pass, so the task the user walked away from waits for the next one. The record's fields, its clock and the run's request are tested with `sessions.ensure` and `outbox.post` patched (`tests/test_afk.py`, `AfkSessionTests`), because that record is what makes the session visible at all, and what the run is told is `tests/test_afk_prompt.py`'s; the hold's whole life — given back when a start fails, freed when a run finishes, stalled when one doesn't, adopted after a restart, released when the user closes the session, and reported by `runs/live` — is tested against a real store and the same HTTP stub. The session names the task it works too (`project_sessions.task`, written as the run is published), so the work comes back as a pull request that closes what it worked (ADR 0012): `ship` reads the task off the session's own record and appends `Closes #<n>` to the body — in the task's own repository only, since GitHub closes an issue through a pull request in the same repository and a project's other repos open theirs without it — and leaves a body that already says it alone; `update` puts it back on a body that replaces one. Opening that pull request is AFK's own news: `push.notify("afk_pr", …)` under the category `code_afk_pr`, so a tap lands on the session whose pill leads to the pull request. The reference is tested through the plugin's HTTP stub, with the task on the session's record (`tests/test_pull_request_tool.py`, `AfkTaskTests`).
- **AFK stages a task through the workflow it started under — build, gate, critique — with the host running the gate** (`plugin/pipeline.py`, `plugin/gate.py`, ADR 0020, ADR 0021). A claimed task's session starts under a snapshot of the workflow its project picked, written before the run is posted (`project_sessions.pipeline`, schema v29): `{ workflow: { id, name }, stage, round, stages: [{ name, steps, ships, check?, loop?, state, rounds }] }`, where `state` is `current`, `done`, `failed` or `todo` and a round is `{ run_id, commands, gate, findings, stop, retry }` — `retry` being the command a loop's next round is told the round before it failed on. The snapshot is the task's own, so editing or deleting the library entry afterwards cannot rewrite what a finished task ran (ADR 0018's reason the record outlives the hold). `pipeline.read` upgrades a record an earlier build wrote — `{ stage, build_skill, critique_skills, gate, reason }`, its stage a name rather than a position — into the three-stage workflow it meant, and `kind` answers the step any record's current stage is judged as: `build` before the stage that ships, `gate` for a gate stage, `critique` for the stage that ships, `done` past it. That step is what the tools and the prompts read, so a record can change shape without a tool changing what it says. A stage's run is told what it follows — the skills that stage names, in order, each loaded with `skill_view` and none of them delegated, applied to the diff where the stage is the one that ships — a skill that wants reviewers asks for them itself — and the points no skill may change are stated once, in the section every prompt shares, rather than in each stage's brief (ADR 0028); a stage that names none has one built-in brief (`prompt_builder.stage_prompt`, one brief per kind: `_BUILD_STAGE` implements and ends at the gate, `_REVIEW_STAGE` reviews the diff and opens the draft, `_SUMMARY_STAGE` writes the wrap-up, `_ONE_RUN_STAGE` does all three in one run; fixed text with the stage's name and steps named into it, so the prompt cache holds across every task's turns). A stage posts a run of its own when its work is needed — every stage up to and including the shipping one, and a stage after it that names a skill — while a checkpoint posts none (the host answers it from the run before) and an empty stage after the shipping one posts none either (`pipeline.posts`). `pull_request`'s `ship` is refused from every stage but the workflow's shipping one, naming the stage the task is in and the one that ships in both directions, and allowed only at the shipping one (`tests/test_pull_request_tool.py`, `StageTests`); `afk_gate` is refused from a stage that can't be gated, naming it. `afk_gate` (`plugin/gate.py`, toolset `memento`, registered and wired like `pull_request`) runs each command the run names — in the session's own worktree, or in that of the repo it names beside the command — each under `GATE_TIMEOUT_S` (ten minutes; a timeout is exit code 124, never a wait, and the command's whole process group is ended with it), stopping at the first that exits non-zero, writes `{ commands: [{ command, code, repo? }] }` onto the round of the stage in hand and answers the exit codes; it refuses a session that isn't staged, one past the gate answerable in its stage, one naming no command, and one naming a repo this session hasn't got, while a build may call it again after fixing what the gate named, the last answer being the one the host judges the run by (`tests/test_gate.py`, against a real throwaway worktree and the plugin's store). What the run executed itself and what its review found are kept beside that answer: a `pre_tool_call` hook (`plugin/commands.py`) records the line of every `terminal` call on the stage in hand's round — the line only, cut at `COMMAND_CHARS`, the most recent `COMMAND_CAP` (fifty) of a stage's across its rounds, and nothing at all for a session with no pipeline to record against, so a chat or a plain code session keeps nothing — and the `afk_findings` tool (`plugin/findings.py`, registered and wired like `afk_gate`) keeps what each review skill reported on that round, the skill's name and its findings of a title and an optional detail, capped, refusing a call naming no skill or no findings list, since an empty list is a skill that found nothing and a missing one is a typo. The shipping stage's brief tells its run to report each skill with `afk_findings` before it ships. `pipeline.stage_commands` reads a stage's commands in order with the gate's exit codes merged onto the ones the host checked (and the gate's own for any the run never executed), and `pipeline.stage_findings` answers each skill's findings including the ones that found none, so one read draws what the sheet lists — both tested with no host in `tests/test_pipeline.py`, and over a temp store in `tests/test_commands.py` and `tests/test_findings.py`. The run-end hook then reads the worktree (`ship.status`) and `pipeline.advance` — one pure function over the record, why the run stopped, the gate's answer and the worktree's state, tested with no host in `tests/test_pipeline.py` — decides: a stopped run keeps its stage and starts nothing; a stage that finished and passed moves the task on and the next stage that posts a run is posted on the loop that owns the runs, with the same home's key (`afk.work_stage` for whatever stage it is: its input names the stage and the issue, and its instructions are `prompt_builder.stage_prompt`, told the base branch read from the worktree's origin only where it is the stage that ships); a checkpoint that failed inside a loop sends the task back to the stage the loop starts at, as another round carrying the failure, up to the loop's own cap (`pipeline._round_again`, `_loop_for`), and past it the task waits for the user naming the command; a stage whose gate failed, never ran, or left the tree uncommitted or commitless stalls the task with that named in `project_afk.stalled` ("The gate failed: pnpm test exited 1.", "The build ended without running the gate.", "The build left uncommitted changes in the worktree.", "The build left no commits in the worktree."), and so does a stage that ships and ended without a pull request in any of its repos ("The stage that opens the pull request ended without one."), since the pull request is what it was for (`afk._unshipped`, one cached `github.pull_request` per repo, and a GitHub that can't be asked says nothing rather than stalling); a task past its last stage is `done` and the record stays. A skill the workflow names that the profile no longer has claims nothing and records `afk.MISSING_SKILL` as its refusal with the switch left on, judged against the home's own `skill_catalog.read` once a sweep and over every step of every stage, not just the stage in hand. Only a project on a workflow is staged: one that picked nothing works one prompt run and snapshots nothing, so its session holds no pipeline and the app draws no pill and no sheet for it (ADR 0027), while a workflow whose stages name no skill still runs as one run did. The stages' runs and stalls are tested with `outbox.post` and the hook's own paths patched (`tests/test_afk.py`: `StagedStartTests`, `StagedRunTests`, `StagedFlowTests`, `StagedSweepTests`, `StageRunTests`), what each run is told in `tests/test_afk_prompt.py`, and the sheet's reading of the stage in `pnpm e2e afk-stage`. The app draws that record too, since the workspace route answers it as the pill has always read it (`pipeline.for_app`: the step, the skills the runs were told, the gate's commands and why it stopped): a session that ran a pipeline carries a pill first in the row above its composer (`src/components/chat/pipeline.tsx` over `src/lib/pipeline.ts`) — one bar per stage of the workflow the task ran, green done, blue in hand, red failed and grey to come, with the stage in words — which opens a sheet titled by the stage it has reached out of the workflow's stages, each stage a row listing what it ran (its commands with the codes the gate read, each skill's findings counted and opening to the list, and why the host stopped it), drawn only where `info` advertises `afk_pipeline` and the device's AFK Workflows switch is on (Developer on too; `useStagedPipeline` in `src/lib/afk-workflows.ts` returns the pipeline to draw or nothing, for the pill and the sheet alike, and the sheet stays closed when it returns; the library gate reads the same `useAfkWorkflowsOn`), still there after the task is finished and covered by `pnpm e2e pipeline-pill`; the picker's own screens are #338's, in the AFK pop-up behind `afk_workflows`.
- **The project's Library tab shows those files, and a session with any shows an outputs pill.** `GET projects/{id}/library` walks the project's `files/` folder and answers `{ folders: [{ name, files: [{ name, path, size, at, worktree, folder }] }] }` (folders alphabetical, files newest first, capped at 500, a file with no folder grouped under its worktree's name); `GET sessions/{id}/library` answers one worktree's files (an empty tree, never a 404, for an unknown session) and `GET library/file?path=` serves a file under a project's `files/` folder for opening it, capped at `MAX_BYTES`, with its extension's content type (an image, markdown and friends as text, anything else an octet-stream). `workspace.ts`'s `refreshLibrary` counts a session's files into `Conversation.library` (`{ count, at }`, local only, trusted for `LIBRARY_MS`), read when the chat opens and again after a turn, and the chat's pill row shows `library-pill.tsx`'s "N outputs" when the count is above zero. - **A merged pull request resolves its session, with the app closed too** (`plugin/merges.py`). Every 5 minutes, and whenever `GET sessions/{id}/prs` finds a merged one, the plugin looks up the pull requests of the open project sessions in its chat list (active in the last 30 days); when none is open and one merged, it sets the chat's `resolvedAt` with a newer change clock, so every device gets it on its next sync (the app syncs at once when it sees a merge). `memento.db`'s `merged_prs` remembers which pull requests did it, so a session the user reopens stays open until another merges.
- **Delete and Discard both close a session's work on GitHub** (`POST sessions/{id}/close`, `closeSessionWork` in `workspace.ts`): the plugin removes the worktrees first (keeping those with uncommitted or unpushed work, like `workspace/remove`), then closes each repo's open pull request from the branch and deletes the branch on GitHub when it was pushed. Delete then deletes the chat (`deleteConversation`, a tombstone); Discard sets `Conversation.discardedAt` (synced), which puts the session in the Code screen's folded Closed group with the composer replaced by `DiscardedCard`, and it's never waiting or resolved again. ## Plugin

- `plugin/` installs with `hermes plugins install thehaseebahmed/memento/plugin --enable` (Hermes clones the subdirectory into `~/.hermes/plugins/memento`). `plugin.yaml` holds the version; `dashboard/manifest.json` repeats it, so bump both.
- **Hermes's own install scanner has to come back `safe`.** `.github/workflows/plugin-scan.yml` runs `tools/plugin_guard.py` from the latest Hermes release and from `main` over `plugin/` on every pull request that touches it (and weekly), and fails on anything but `safe`. MEDIUM and LOW findings are listed but don't change the verdict; a HIGH or CRITICAL one does. Its `inline_shell_exec` rule matches an exclamation mark immediately followed by a backticked span, so a heading that ends in one — wrapped in backticks and followed by anything but a space — reads as an inline-shell snippet: write `the Gots section` or move the code span away from the mark, never a bare heading with an exclamation mark just before a comma. Run it before pushing a change to prose or prompts: `python3 .github/scripts/scan-plugin.py <hermes checkout> plugin`.
- **The app names the oldest plugin it works with** (`MIN_PLUGIN_VERSION` in `src/lib/version.ts`). Raise it, after bumping the plugin, when an app change relies on a route, field or behaviour only the newer plugin has. A bot whose plugin is older (`Profile.pluginVersion`, local: what its host last reported to the registry, or what Test connection read) is flagged on its card and on Settings' Bots row, and its editor says which version it needs. An unknown version is never flagged.
- **The composer's `/` menu lists the profile's skills from the plugin** (`GET /api/plugins/memento/skills`, `plugin/skill_catalog.py`, `info` feature `skills`). It is Hermes's own listing under the request's profile scope, so a `/p/<profile>` bot sees its own skills. The app asks the route and asks nothing else: a plugin that lacks it (`lacksRoute`, an older plugin) has no skills to show — the commands alone, no error line, and no `MIN_PLUGIN_VERSION` bump — and is left alone for `MISSING_ROUTE_MS` like every other route-missing read, while a host that is merely away leaves the last-known list standing. It doesn't call Hermes's `/v1/skills` for this (see § Hermes API). **A `/` that begins any word opens it, wherever the caret is** (`slashToken` in `src/lib/slash.ts`): the query is that token up to the caret, a pick rewrites the token from its `/` up to the caret — the rest of the message, a word the token was typed into included, stays where it was — and a slash inside a word — `and/or`, a URL, a path, or a second slash in the token — never opens it. It is the caret that decides, so the menu follows a click or an arrow key (`onSelect`), it follows the field after any write the user didn't type (a restored draft, dictation), and Escape closes it until the text changes. **A picked skill lands where the caret is** (`pickItem`): `/name` replaces what was typed of the token up to the caret, with a single space after it unless one already sits there, and the message keeps the order it was written in — the host needs no front position, since `POST /v1/runs` passes the message through as text (ADR 0037) — while `/steer` and `/queue` replace the whole token (`pickSendMode`), being commands the app itself reads only at the front of the message, and `new` and `settings` run at once and match only when their token is the whole message (`alone`), the shape the composer's own actions take, so running one never drops text. Matching is tiered (`rankSlashItems`): an exact name, a name the query starts, a name that contains it, a fuzzy subsequence name (tightest first, `nameSpread`), a category, then a description, ties keeping the plugin's order, with the commands pinned above the skills. **The list is kept on the device** (`db.skills`, one row per connection, `src/lib/skills.ts`, dropped with the bot when it's deleted or the data is cleared): the cached list answers the instant the menu opens, a read runs in the background on each open (one per server at a time) and the list it brings replaces the held one, a failure leaves the cached list standing, and a bot that can't list skills writes nothing. **The list is only as tall as the room above the composer** and no more of the screen than 45%, up to the 288px it has always been — and never taller than the room there is, so a phone with the keyboard up scrolls four rows instead of pushing its own top rows off the screen (`SlashMenu` measures at open, and again on the frame while the composer grows or that viewport moves — the visual viewport's height is what the keyboard leaves). `scripts/test-slash.mjs` pins the token rules, the ranking and the pick; `pnpm e2e slash-skills` the menu itself.
- **A bot's MCP servers are read from Hermes's own in-process machinery** (`GET mcp`, `plugin/mcp.py`, `info` feature `mcps`). The read names each of that profile's servers with one of Gots' own state words — `on`, `off`, `connecting`, `failed`, `needs_access`, `plugin` — mapped from Hermes's finer ones (`configured` and `lazy` collapse to on, an absent `enabled` key reads as on because Hermes's own reader is what computes it, and a server a Hermes plugin provides is `plugin`, since Hermes refuses to modify those and the app shows it read-only). Every row carries that flag as its own `enabled` boolean, which is what the app's switch follows: the state word is cached runtime and can still read `connecting` for a server the config has just switched off. The profile's own servers come from `server_configs_with_sources` and their cached runtime state from `get_mcp_status`, whose docstring is the authority for the read never connecting a server, so opening the screen cannot spawn one; the whole read runs in the profile's home-and-secrets scope (`_config_profile_scope`, never `_profile_scope`, which holds the skills lock) off the event loop. A failed server carries Hermes's own reason. The feature is advertised only where those built-ins import, so a bot on an older Hermes has no row and no screen rather than an error, and no `MIN_PLUGIN_VERSION` bump is needed. A plugin without the route is left alone like every other route-missing read. - **Name a new agent tool the way Hermes names its own: `<subject>_<action>`**, lower snake case, the thing it works on first and the verb last, like `web_search`, `web_extract`, `browser_navigate`, `image_generate`, `session_search` and `skill_manage` (checked in hermes-agent's `tools/`, 2026-10-14). Tools on one subject share its prefix, so they sort together and the model reads them as a family (`claim_add`, then `claim_list` or `claim_remove`). Use a plain verb (`add`, `list`, `get`, `remove`, `search`, `run`, `review`) and no `memento_` prefix: the toolset (`memento`) already groups them. Hermes still has older verb-first names (`read_file`, `delegate_task`, `execute_code`); don't copy them. The words a model is told and the components the app can draw are one fact on either side of a process boundary, so the artifact is generated from `library.tsx` (`pnpm build:openui-prompt`, `app/scripts/build-openui-prompt.mjs`) and checked in, and `app/scripts/test-openui-prompt.tsx` fails the app's gates when the two disagree, when the text names a fence other than `openui-lang`, or when it passes Hermes's 4,000-character section limit — a section that size is dropped **whole** rather than truncated, so the generator refuses to write one and never truncates. ## Triage

- **A message sent from a bot's Main thread is triaged by the host** (`plugin/triage.py`, `info` feature `triage`, only where the host offers `ctx.llm`; ADR 0029). `POST sessions/{main session}/triage` `{ text, body }` (`body` being the run request the app built for Main) asks the profile's own model, through `ctx.llm.complete_structured`, whether the message `stay`s, `continue`s one of the bot's threads or is a discussion of its own that opens a `new` one. The candidates are the bot's plain threads only — never a project session, a deleted, discarded or resolved chat, another bot's chat or Main — the 15 most recently active, each as id, title, last line (from `state.db`) and last-active, and Main's last four turns come with the message. **Unsure is Main**: an unparseable answer, an unknown thread id, a missing model facility, any error, a call past `DEADLINE_S` (3s) and a session that isn't a Main thread all answer `{ decision: "main" }`, and nothing in `triage.py` raises. A `new` answers `{ decision: "new", thread, session_id, item }` after the route made the thread (`triage.open_thread`: a UUID chat id, `memento-<id>` as its session, the bot's `profileId`, the title `New chat` for Hermes's auto-title to replace, created and changed on one clock and updated just after it, so the daily cleanup doesn't take a thread whose first message still waits in the queue for an empty one, written to the chat list as a new chat on any device would be) and queued the message as its first turn through the outbox with only the message in the run (the body's `session_id` swapped for the thread's, and the attachments it names, which the app saved on the host first); it is made after the decision, only if the answer is still wanted, and a failure queueing it takes the record back with a tombstone and answers Main, as every failure does (`triage.start_thread`). The thread keeps the model the run's body names, and its record says so (`modelChoice`) so the pill shows what ran. Asks sharing an id are serialised (`triage.lock`), so a retry that races the first waits for it and reads its answer, and a message is queued once. A `continue` answers `{ decision: "thread", thread, session_id, item }` after the route queued the message on that thread's session through the outbox (the body's `session_id` swapped for the thread's), so it reaches the thread with the app closed and never enters Main's Hermes session. The thread runs on its own model (the chat record's `modelChoice`, else the host's), not Main's; a thread whose queue is paused stays in Main; the request carries the message's `id` and the host answers a repeat of it as it did before, so a dropped response can't send one message twice. The request also carries `steer` (the user's steer-or-queue choice for this message): a thread whose reply is running takes a message whose files are only files as a steer (`triage.deliver`, over `outbox.steer`, the helper the queue's own steer route uses — the item's own body holds the marker lines that steer), while a thread waiting on the user, a message whose body carries a photo or a refused steer leaves it queued, which the dispatcher starts with the app closed. Tested over a temp store with the model facility patched (`plugin/tests/test_triage.py`).
- **A message triage sent out of Main leaves a Moved marker** (`plugin/moves.py`, `memento.db`'s `main_moves`, schema v33, `info` feature `moves`). The triage route records the move — the message's text, the thread, the host's clock and `undone` — when it has queued the message on a thread or opened a new one for it, keyed by the id the app sent so a repeated ask is one row; a message that stayed in Main records nothing. `GET sessions/{id}/moves` answers `{ moves }` oldest first, each saying whether the host opened the thread for it (`new`) — which is what makes that message a thread's card rather than a marker. The app reads it for a Main thread with the other follow-up reads (`refreshMoves` in `src/lib/moves.ts`, local `Conversation.moves`), and `moveMarks` (`src/lib/move-marks.ts`) puts each marker above the first message written after it (`src/components/chat/moved-marker.tsx`: the message as the user's own bubble, with a "Moved to <thread>" link under it, and Undo beside that while the move is undoable). **A move that opened its thread draws no marker**: that thread is a card in Main's flow where the message left, its opener bubble showing it, and the card carries the same Undo (`ThreadCard`, `scripts/test-card-undo.tsx`) — the same message is never drawn twice. A message moved into a thread the bot already had keeps its marker, and that thread's card stays where it began (`scripts/test-move-marks.mjs`). **Undo is open until the thread's reply to the message finishes** (schema v35): a move also keeps its thread's session, the queued item, whether it opened the thread and the message as Main would have run it (`main_body`, `files`). `GET moves` marks each move `undoable` (`moves.phase` over the item's outbox row and the run's status: `queued`, `running`, `stopped` — a reply that never finished — or `replied`; a row or run that can't be found counts as replied), and `POST sessions/{id}/moves/{move}/undo` removes a queued item, or stops a running reply and takes the item and the message out of the thread's `state.db` transcript (best effort, `moves.take_from_transcript`), discards a thread the move opened, queues the message on Main untriaged and marks the move `undone`; after the reply it answers 409. A move older than the outbox's hour is a finished reply and drops its stored body; Undo is serialised per move, puts the message on Main before it tidies the thread (a queued item is taken back and restored if Main can't take it), and removes the transcript rows only when the moved message is the thread's newest user row, whole and written after it was sent. The marker — and a card drawn for a move that opened its thread — shows Undo while `undoable` (`undoMove` in `src/lib/moves.ts`); an undone move draws no marker on any device, since the message is an ordinary Main message again, and the card of a thread that existed only for it goes with the host's discard. `plugin/tests/test_moves.py` and `scripts/test-main-triage.tsx` drive it.
- **Triage decides with the bot's triage model** (`GET`/`POST triage-model`, `triage.read_model` / `triage.set_model`, `info` feature `triage_model`, `useTriageModel` in `src/lib/triage-model.ts`, `TriageModelSetting` on the Models tab beside the Subagent model; `GLOSSARY.md` has the term). The pick is the bot's own setting on its host (`memento.db`'s `host_settings`, schema v34, not Hermes's `config.yaml`), `{ provider, model }` or none, and none means the bot's own model decides: `triage.decide` passes the pick as the call's `provider` and `model` and nothing otherwise. A pick overrides the model of a call, so the write needs the host's override permission (`plugins.entries.memento.llm.allow_model_override` and `allow_provider_override`, `research.llm_gate`, reported as `info.research.writers`, read by `getResearchWriters`) and is a 403 in the host's words where it is withheld, while the field shows the same warning as Research's rewrite picker; clearing needs no permission. Hermes checks a pick with `switch_model` as it checks the main model (a refusal is a 400 with its reason, shown as a toast, and writes nothing), and a pick already held (as asked or as Hermes resolved it) is a no-op that needs neither the permission nor another check. A saved pick that later fails (the model retired, credentials gone, the permission taken back) falls back to the bot's own model for that call rather than to Main. A bot whose plugin lacks the route shows no field. `plugin/tests/test_triage.py` (`TriageModelTests`), `scripts/test-triage-model.tsx` and the mock (`MOCK_RESEARCH_WRITERS=off` withholds the override) cover it.
- **The app asks before it sends** (`sendFromMain` in `src/lib/chat.ts`, `triageMessage` in `src/lib/hermes.ts`): only a Main thread's message with text, from the chat's composer, while Main's own reply runs too (it then goes to another thread at once or, staying, steers or queues behind the reply as the user's setting says), on a bot whose plugin advertises `queue` and `triage`. The message shows as `Message.status: "triaging"` — as any message the user sent, with no cue of its own (ADR 0036) — for up to `TRIAGE_MS` (`freshness.ts`, 5s, a little over the plugin's own deadline); then a `thread` or `new` answer drops the held message, toasts where it went ("Started a new thread" for a new one, whose chat the app learns of with a sync of the chat list) , and anything else — a stay, a timeout, a failure, a bot without the feature — sends it to Main as any message is, keeping the bubble's id. A message sent while another is being triaged waits in the queue behind it, and a `triaging` row left by a closed page becomes a failed message to send again (`settleTriaging`). Messages typed inside an open thread, a new chat (the New thread button) are never triaged. A message with files saves them on the host (Main's session) before the ask and the ask names their paths, so whichever thread gets the message reads them; a stay sends it to Main with those paths and uploads nothing twice. `scripts/test-main-triage.tsx` drives it; the mock serves the route (`MOCK_TRIAGE=off|stay|thread|slow|fail`).

## Research missions

- **A mission runs on the plugin** (`plugin/research.py`, `memento.db`'s `research_missions`, `research_sources`, `research_claims` and `research_outputs`), so it carries on with the app closed. Its `stage` is `brief → scope → reading → drafting → reviewing → delivered`; `busy` is a model call under way (`brief`, `outline`) and `error` a step that failed, which `…/retry` runs again. `info` lists the `research` feature and `research: { ready, reason }` (not ready without `ctx.llm`). Missions belong to the profile that started them; the app lists every bot's (`useMissions`) and starts one on the active bot.
- **Brief and outline are `ctx.llm.complete_structured` calls** on the profile's own model (no override, so no extra trust): the question read back as title, goal, format, audience and depth, which the user edits and confirms (`…/brief`), then an outline of 3 to 6 points. The Scope Gate (`…/start` `{ outline, source_kinds }`) is the mission's one designed pause: nothing is read before it.
- **The researcher is an ordinary Hermes run**, session `research-<mission id>`, started over loopback with the key the app's `…/start` came with (`outbox.post`), with fixed `instructions` and the brief as its message. It searches and reads with Hermes's web tools (`web_search`, `web_extract`, in the API server's toolset; a host with no web backend records nothing and the reading fails with a hint). `research.wire` adds the plugin's `claim_add` tool to that session's agents only, and its `pre_tool_call` hook blocks the terminal, file writes, delegation, `clarify` and the other tools that could stall or change things. `claim_add` `{ claim, url, title, kind, snippet, confidence? }` fetches the page (`urllib`, 20s, 6 MB; scripts and tags stripped, compared as lower-case words, an ellipsis splitting the passage) and refuses a passage the page doesn't hold; a page it can't read (a PDF, a blocked site) records the claim as `uncertain`. Sources (`s1…`) and claims (`c1…`) are numbered per mission. A background loop (`research.run`) watches the run in `_run_statuses` and, once it stops, moves on to drafting with 3 claims or more, else fails the reading; a restart resumes each mission's step (`research.resume`, also on the first list of a `/p/<profile>` bot).
- **Writing is `ctx.llm` from the ledger alone**: one call per outline point for a guide, saved section by section (`written`), where every sentence must end with the ids of its claims (`[c3]`); one call for a quiz or a glossary, whose items must cite a claim in the ledger or are dropped. **The review is plain code** (`research.spans`): a sentence without a marker, or whose markers name no claim, is `flagged` ("No source" in the app). `…/formats` `{ format }` writes another format from the same ledger, without new reading. Every change notes a `research` event (the mission's id), which `live.ts` turns into a refresh; without the stream the screens poll every 3s while a mission works.
- **Questions a delivered mission missed are read for and added** (plugin 0.38, `info` feature `research_followup`). Once delivered, `research._suggest` asks the profile's model (`ctx.llm`, best effort) for up to 3 questions the outline and the ledger leave open (`suggestions`, dropped when a follow-up is asked meanwhile). `…/followup` `{ questions }` (1 to 3, none already an outline point, the outline at most `MAX_OUTLINE` = 12) records the round in `followups` (`{ questions, from, claims, at }`) and as the mission's `pending` rewrite, and starts the researcher again in the same `research-<id>` session with a prompt naming what's covered and what was missed, adding to the same ledger (schema v17); the write-up stays on show meanwhile. The round needs at least one new claim, else it fails with Try again. **Drafting then writes the whole mission again** (plugin 0.39, decided with Haseeb 2026-10-14: no section tacked on at the end): one `ctx.llm` call plans the outline again with each question worked in where it belongs (`research._replan`, falling back to adding them as points), every section of the guide is written afresh, every other format made before is written again, and `research_done` is pushed again. An older guide's follow-up sections may still carry `question`, which the app labels. The app offers **Missed something?** in a delivered mission's options menu, a pop-up with the suggestions as chips to pick and a question of the user's own, only when the plugin sends `followups`.
- **Every delivery is kept as a revision** (plugin 0.39, schema v18, `research_revisions`): its number, `reason` (`first`, `followup` with its `questions`, `rewrite` with its `model`), the claim count, when, and a snapshot of the outline and every format as delivered, so the app's Revisions list says why each was written and opens an earlier one read-only. A mission delivered before revisions were kept gets its first one just before it's written again. `GET research/{id}` carries `revisions`, `pending` (the rewrite under way) and `writer`.
- **A Learn & understand mission can be rewritten with another model** (`…/rewrite` `{ provider, model }`, `info` feature `research_rewrite`; an empty body is the profile's own model). It writes the whole mission again from the same ledger, without new reading, and the pick stays the mission's `writer` for later writing (a follow-up, another format). It's a `ctx.llm` override, so it needs `plugins.entries.memento.llm.allow_model_override` (and `allow_provider_override` with a provider), which `info.research.writers` reports and the route checks first (403); the app's picker (the host's models, `ModelPicker`) shows a warning when the host doesn't allow it. A rewrite that failed can be taken over by another model from the same menu item.
- **A mission names its main agent** (plugin 0.40, schema v19): the bot is the profile that owns it, and the model is the one the researcher ran on, which `finished_reading` reads from the `research-<id>` session's row in Hermes's `state.db` (read-only, best effort; `researcher: { provider, model }` on the mission, absent until reading has finished or when the plugin is older). The app shows the bot's picture on each row of the Research list and "<type> · <bot name> · <model>" under the mission's title.
- **Compare & decide is the second mission type** (plugin 0.63, schema v31, `info` feature `research_compare`; the app refuses to start one without it). Decided with Haseeb 2026-10-21 on the planning doc's recommendations, after two tests on the doc's cases: one Opus judge matched a three-model panel on 5 of 5 comparisons, and advocates beat a single writer 4 to 1 with ties (n=5, one grader, same model family, more compute spent), so Phase 1 uses one judge and advocates. The brief (`compare_brief`) reads the question back as the decision, 2 to 5 options (`o1…`) and 2 to 6 criteria (`k1…`) with weights 1 to 5, all editable (`confirm_brief` → `_confirm_compare_brief`); there is no outline call, so the criteria are the Scope Gate's outline and the push `research_scope` goes at once. The Scope Gate takes the kinds of source and an optional judge model (`mission.judge`, a `ctx.llm` override that needs `info.research.writers`, so the app hides the picker when the host doesn't allow it). **The researcher tags every claim** with `option` (required) and `criterion` through `claim_add` (`research_claims.option_id`/`criterion_id`; an id the mission doesn't have is refused), and reading ends with at least `max(3, 2 × options)` claims. **Drafting is `write_memo`**: one advocate call per option sees only that option's claims, then one rebuttal call each sees the others' cases, then one judge call (`judge`) scores every option on every criterion from 0 to 10 with the claims behind it, names any option a claim rules out on a criterion, and writes the verdict and what would flip it. Every cited sentence goes through `spans`, so an uncited one is flagged; a score whose claims are all unknown, or with no reason, is `flagged` (thin); a ruling whose claim isn't in the ledger is dropped. The memo is `research_outputs` format `memo`, saved after each of its `2n + 1` steps so the app shows it building (`written` counts them). **The ranking is code, never the judge's** (`decide`): weighted scores as a share of the best total (0 to 100), an option that is ruled out can't lead, and totals within `CLOSE_POINTS` (5) are a close call; `GET research/{id}` carries it as `decision` (absent for Learn missions). A comparison has one format: `formats`, `followup` and `rewrite` refuse it, and no follow-up suggestions are made. The app's `MemoCanvas` (`components/compare.tsx`) shows the verdict, the scores table (each cell opens its reason, a thin one says so) and each option's case folded under it. Phase 2 (changing a weight or adding an option or criterion and judging again, a second judge, Missed something?, rewrite with another model) isn't built.
- **A mission tells the user when it needs them, is ready or failed** (plugin 0.37): `research_brief` when the brief is read back, `research_scope` when the outline is ready for the Scope Gate, `research_done` when the first format is delivered and `research_failed` when a step fails (`research._tell`, through `push.notify` with the mission's id and title; another format asked for later isn't news). They are the Research feature's categories `research_input`, `research_done` and `research_failed`, all on by default, and a tap opens `/research/<id>`. A muted bot mutes them; there is no per-mission mute.

## Meetings on the host

- **Phase 1 (plugin 0.73, `plugin/meetings.py`, `memento.db`'s `meetings` and `meeting_parts`, schema v37; the app reads it, see the Layout row).** `info` lists the `meetings` feature. **Upload and transcribe (step 1):** a recording goes up as byte chunks of the one file, in order (`POST meetings/{id}/parts?n=`, each at most 9 MB since the API server refuses bodies over 10 MB, at most 64), kept under `$HERMES_HOME/memento/meetings/<id>/`. A chunk is not audio on its own (a slice of an m4a, wav or ogg has no header), which the first version, uploading 5 minute parts cut by the app, got wrong; so `finish` starts the job on a thread, which joins the chunks (`_assemble`), decodes the file once with faster-whisper's own decoder (`_decode`, 16 kHz mono; three hours of it is about 700 MB of samples) and cuts it into windows of at most 5 minutes, which replace the chunks as the meeting's parts (`parts` and `parts_done` then count windows; a part's `content_type` is `window`). One window at a time in order across all meetings, on the host's faster-whisper like dictation, each prompted with the end of the text before it. Segments come from the loaded model (`_get_or_load_local_model(...).transcribe`, given the window's samples, so a segment's own second is added to its window's start); when that can't be reached a window is one segment at its start. The joined file goes with the transcript. A transcript the app parsed (`transcript: [{ at, text }]`) skips audio and starts at `writing`. Limits: 3 hours (judged once the file is decoded), 64 chunks, audio refused (501) on a host without faster-whisper, and any meeting refused (501) on a Hermes without `ctx.llm`. **Questions (plugin 0.75, schema v38, `info` feature `meetings_ask`):** `POST meetings/{id}/ask` `{ question }` records the question in `meeting_chat` (`n`, `role`, `text`, `cites`) and answers 202 with the meeting, whose `chat` carries every line; a thread (`spawn_answer`) then asks the profile's own model (`ctx.llm`, no override) with the notes, the earlier lines (last six) and the transcript — all of it when it fits `ASK_CHARS`, else the lines sharing the most words with the question with their neighbours (`pick_lines`) — and writes the answer as the bot's line with its cited stamps held to the transcript like the notes' are; a failure is the bot's line, `I couldn't answer that: …`, so the app never waits on an answer that isn't coming. Refused (409) before the meeting is ready, while the last question is unanswered and past `MAX_CHAT` lines; a restart answers a question left open (`resume`). The app polls for the answer through the same read as a meeting at work. **Notes (step 2):** stages are `uploading → transcribing → writing → ready`, with `error` set on a failure, which `…/retry` runs again from the first part not done (or from the transcript, for `writing`); a restart resumes both. The notes are one fixed template — `summary`, `key_points`, `decisions`, `action_items` (each with an `owner`), `open_questions` — written by the profile's own model (`ctx.llm.complete_structured`, no override) from the transcript alone, as `[mm:ss]` lines (`1:02:04` from the first hour). A transcript over `NOTES_CHARS` is written in sections and merged by a second call. **The check is code, not trust** (`meetings.check`): each item's `cites` keep only stamps the transcript has, an item left with none is kept with `unsourced: true`, and an action item's `owner` is kept only if the transcript says that name, else `Owner not stated`; the summary is the model's words. **Topics (plugin 0.74):** after the notes, `write_topics` asks the same model for the meeting's topics (3 to 8, or 2 to 4 per section of a long transcript): a title, the first and last stamp, a sentence or two and one quote with its stamp. `check_topics` holds them to the transcript like the citations: a topic whose first stamp the transcript lacks is dropped, an end that isn't a stamp of it falls to the line before the next topic, they run in order without overlap, and a quote stays only when the line it names says it. They are best effort: a failed call leaves `notes.topics` empty and the notes written, and the app shows the sections. Stored as `{ title, start, end, summary, quote? }` in seconds. `GET meetings/{id}` carries `transcript` and `notes` (null until ready). Pushes `meeting_done` and `meeting_failed` (categories of the same names, feature Meetings, which Notification types lists only while the Meetings switch is on; a tap opens `/meetings/<id>`). `MIN_PLUGIN_VERSION` is not raised for it: a bot whose plugin lacks the `meetings` feature is told so on the Meetings screen (as Research is), and Meetings is behind a Developer switch.

## Sync

- Sign-in is Netlify Identity with the GitHub provider (`@netlify/identity`). It only identifies the owner. **Never send plaintext, a key or anything that derives one to the server.** Every document the function stores is sealed with `vault.ts` first, and the associated data names its owner and slot (`memento:<userId>:<doc>`).
- **In the Android app** the page is `https://localhost`, and `@netlify/identity` only talks to its own origin. So `account.ts` hands off to `native-account.ts`, which calls `${VITE_SITE_URL}/.netlify/identity` and the sync function through `CapacitorHttp.request` with a Bearer token. Don't turn on `CapacitorHttp`'s fetch patching: it would buffer Hermes's SSE streams. Identity ignores `redirect_to` and returns to the page that started sign-in (its `Referer`, when on the site's host), so sign-in starts from `/auth/native.html`. The function skips its origin check for Bearer requests. Passkeys are off in the app, so it unlocks with the recovery code.
- **Sign-in is compulsory where Identity is available.** `SetupGate` (`src/routes/setup.tsx`) keeps the app behind GitHub sign-in and unlocked sync unless the account is `unavailable` (plain `pnpm dev`, no Identity, no `VITE_SITE_URL`, or offline), and behind the first-run wizard until `Settings.onboarded`: Sign in, Turn on sync, Join the leaderboard (on by default, with what it shares shown; Continue), Link your bots (Start chatting once a linked bot answers from this device). The wizard's link step comes back whenever the untouched seed is the only bot (`needsBotSetup`), say after the last bot is removed. An upgrade with configured bots is marked onboarded without it. Where Identity is `unavailable` nothing can link, so the seed bot is set up by hand in Settings.
- **Chat lists live on the Gots plugin** (`plugin/chats.py`, `$HERMES_HOME/memento/memento.db`, under the profile home the API server scopes the request to). `POST /api/plugins/memento/chats` takes this device's `{ id: { at, deleted?, value? } }` record set, keeps the newer record per id in one SQLite transaction, and returns the whole list; `mergeDocs` then picks what to pull. It's plaintext, like the transcripts Hermes already holds. **The plugin is mandatory**: there's no other place for a chat list, and a server that doesn't answer shows as `unreachable` (a flag on the bot's card) until it does.
  - Older versions kept a bot's list in a Netlify `chats/<botId>` document when its server had no plugin. Each bot's first sync with an unlocked vault pulls that document onto the device, and once the plugin has merged it the document is deleted and the bot recorded in `Settings.movedChats`, so it's read once.
  - Plugin chat sync needs no account, so it also runs where Identity is `unavailable`. Two bots on one server share its list; a chat stays with the bot that already has it. Deleting a bot leaves its chats on the plugin.
- Documents are `vault` (the wrapped data keys and the inbox), `bots` (what the user changed about each bot: name, character, default model) and `settings` (the Appearance section's switches (`steerByDefault`, `breakReminders`), one record merged on `Settings.appearanceAt`; the colour mode is this device's own, in next-themes' storage). Writes carry the etag they read; a 412 means re-pull, merge and retry.
- Records merge last-write-wins on a change clock: `Profile.updatedAt` and `Conversation.changedAt`. Change synced fields through `updateProfile` / `updateConversation` so the clock moves, and delete through `deleteProfile` / `deleteConversation` so a tombstone is left for sync.
- Message bodies don't sync. They come from Hermes (`history.ts`): with `X-Hermes-Session-Id`, Hermes builds the turn's history from its own session store and ignores the body's, so its transcript holds every device's turns. An open chat catches up (`reconcileHistory`) on open, when its `updatedAt` changes, on focus, when the plugin's stream says its session moved, every 30s while visible (every 5 minutes while its bot's stream is open), and before a send. `Conversation.hermesTip` (local only) lets that start with a one-row probe. Turns streamed on this device are kept (they carry stats and approvals) and matched to their rows by `hermesRowId` — or, after a compaction re-emits a turn under a fresh row id with its time untouched, by its text and the row's own time (`Message.hermesAt`), so a carried turn is adopted where it stands instead of added again.
- **Changes are pushed, not polled, where the plugin is** (`plugin/events.py`, `plugin/stream.py`, `src/lib/live.ts`). Hooks (`pre_llm_call`, `post_api_request`, `pre_tool_call` / `post_tool_call`, `pre_approval_request`, `post_approval_response`, `on_session_end`, API server sessions only) and the plugin's own writes (a chat-list merge that changed something, a session's mode or pending plan, a clarify status, a project clone or repo change) note a content-free row in an `events` table in `memento.db` (`session`, `runs`, `chats`, `projects`; an hour, 2,000 rows, a quarter second per kind and session). `GET events[?since=N]` is SSE per profile: `hello` with the cursor, those rows (a session id walked back through compression parents for `session`), `title` (watched for 90s after a session moves, since Hermes titles in a background thread whose hooks carry no session), `cron` (a fingerprint of the jobs and the ledger's newest runs, every 4s, shared by a profile's streams) and `reset` when the cursor fell out of the table. A stream wakes on an in-process signal and also reads the table every 2s, for hooks run in other processes. It sets its own CORS headers before `prepare()` and pings every 20s for proxies and tunnels (Cloudflare cuts a quiet one at 100s). Events never carry content: the app fetches as it always has.
- **A session that needs the user is pushed to a closed PWA** (`plugin/push.py`, `src/lib/push.ts`, `public/push-sw.js`; the Android app has no Push API in its WebView and gets Firebase messaging through the registry, below). A browser subscription is tied to one VAPID key, so the key is the *device's* (made in the app, kept in `Settings.push`, local only) and goes to each bot's plugin with the subscription: `POST push` `{ device, subscription, vapid_key, subject }` (a public https endpoint only, the plugin posts to it; at most 20 per profile) and `POST push/remove` `{ endpoint }`, kept in `memento.db`'s `push_subscriptions`. The plugin encrypts a `{ kind: approval | question | plan, session_id }` message to the device (RFC 8291 `aes128gcm`, with `cryptography`, which Hermes already depends on) and signs it with the device's key (RFC 8292), sent from `pre_approval_request`, the clarify callback and a pending plan; never what was asked. A 404 or 410 from the push service drops the subscription. A device that holds an `events` stream with its `device` id is skipped, since the app is on screen (a stream whose client vanished without a FIN can keep a device skipped until the server notices). The service worker (imported by the generated one) shows the notification (see **What a push says**) tagged by session, silent and closed as soon as it is shown when a window is visible (the app clears the tray with `clearNotifications` when it comes to the front or launches) (Safari revokes subscriptions that get pushes without a notification), and a tap opens `/s/<session id>`, which finds the chat by `hermesSessionId`, syncing the chat list (with a spinner) until a chat started on another device arrives (a session that compression moved on isn't matched). **The Android app is pushed through Firebase, by the registry** (`netlify/lib/fcm.ts`, `src/lib/push.ts`): the service account key can't live on every user's Hermes host, so it is the Netlify environment variable `FIREBASE_SERVICE_ACCOUNT` (JSON or base64; the same key as the CI secret of that name, which uploads to App Distribution; the registry answers 503 to a push without it), and the plugin asks for the send with `POST registry?route=push` `{ kind, session_id, skip }` (the host token authenticates; `skip` is the devices with the app open; one a second per host; `push.py`'s `_relay`). The app gives the registry its Firebase token with `POST devices&id=<device>` `{ token }` (Identity; at most 10 per account) and `DELETE devices&id=`, through `@capacitor/push-notifications`; the message is a notification message (`notification` + `data`), so Android shows it with the app closed and a tap opens `/s/<session id>` (`PushLinks`). A token Firebase reports unregistered is dropped. `Settings.fcm` is the device's id and switch, which `followEvents` sends like the PWA's. CI writes `android/app/google-services.json` from the secret `FIREBASE_GOOGLE_SERVICES` (the file's JSON, raw or base64); without it the APK builds with push off. That step runs before the web build, which sets `VITE_FIREBASE=1` only when the file is there: `pushAvailable()` is false in an APK without it (the plugin's `register()` throws natively without Firebase, which ends the app), and `Settings.fcm.trying` is set across each native `register()`, so a launch that finds it left behind (the app died there) turns push off instead of crashing again. Developer settings has a Send test notification row in the Android app (`sendTestPush`: `POST registry?route=push-test&id=<device>` with Identity, answering Google's own reason as a 502 on a refusal, which the row shows as a toast): it pushes to that one device whether or not the app is open, and `presentationOptions: ["alert"]` in `capacitor.config.ts` makes the push plugin show the tray notification while the app is in the foreground (a real push also shows then, only if the plugin didn't skip the device). iOS only delivers to a PWA added to the Home Screen, and asks for permission only from a tap; the Notifications row is hidden where the browser has no Push API.
- **A push has a kind, and a device picks which it wants** (`plugin/push.py` `KINDS`, `netlify/lib/fcm.ts` `PUSH_KINDS`, `src/lib/push-kinds.ts`, which keep the same list). `approval`, `question` and `plan` wait on the user, as before; `run_failed` (a turn of a Gots chat ended with `failed`, a stop doesn't count) and `run_done` (a turn that completed after 60s or more, not a plan-mode one) come from the `pre_tool_call`, `pre_llm_call` and `on_session_end` hooks (`plugin/alerts.py`, so only for chats whose id starts `memento-` or that have a project workspace, never a delegated child), `pr_merged` from `merges.py` (the same moment it resolves the session), `clone_failed` from `clones.py` and `repos.py` (the project's id or slug), the `research_*` kinds from `research.py` (the mission's id; see **Research missions**), the `meeting_*` kinds from `meetings.py` (the meeting's id; see **Meetings on the host**), `afk_pr` from `ship._open_pr` (an AFK session's task pull request, the session's id, see **AFK works the task**), and `pr_checks` and `routine_failed` from `alerts.run`, which looks every 5 minutes, only when a device could be told: an open session's PR whose checks went to `failure` (pushed once, and again after they stop failing) and a routine run that failed (or whose delivery did) in the last 30 minutes, which `push_seen` in `memento.db` (`push.once` / `clear`) remembers so a pass never repeats one. The plugin's `session_id` is the session the news is about, or the routine's job id or the project's id, and the kind picks where a tap goes (`pushPath`: `/routines`, `/code`, `/research/<id>`, else `/s/<id>`). Kinds fall into categories (`category_of(kind, project)` in `push.py`, `PUSH_CATEGORIES` in `fcm.ts` and `push-kinds.ts`: `chat_input`, `chat_run_failed`, `chat_run_done`, `code_input`, `code_run_failed`, `code_run_done`, `code_pr_checks`, `code_pr_merged`, `code_setup_failed`, `routine_failed`, `research_input`, `research_done`, `research_failed`, `code_afk_pr`), grouped by feature (Chats, Code, Routines, Research). Every category is a switch under Settings, Notification types (`usePushCategories`, `Settings.pushCategories`, local to the device; a feature's master switch sets all its categories; a run finished and a pull request merged start off) and an Android channel of its own (`createChannel` per category, so Android's own settings can turn each off). The device says which categories it wants: the PWA with its subscription (`categories` on `POST push`, kept in `push_subscriptions.categories`, null for an older app, which gets `chat_input` and `code_input`) and the Android app with its token (`categories` on `POST devices`, `PATCH devices` when only they change; the registry keeps them on the device and counts the others as `muted`); the plugin relays `{ kind, category, session_id, skip }` and the registry derives the category for an older plugin. **Muting is held by the plugin**, so it works with the app closed and covers every device: a bot is muted with `POST push/mute` `{ muted }` (`push_prefs`; `Profile.muted` syncs through `bots` and `syncMutes` tells each bot's plugin), which silences all its pushes, and a thread through the chat list's `muted` field (`Conversation.muted`, `CHAT_FIELDS`), which silences only the pushes about its session (compression lineage followed). Muted bots show a bell-off in the sidebar, muted threads in the chat header and on the bot's thread card. The registry takes one push a second from a host, so the plugin's relay tries again after a 429. A new kind goes in all three lists, `WORDS` in `fcm.ts` and `push-sw.js`, and a category if the user should pick it; `test_push_kinds.py` fails when the lists drift apart.
- **What a push says** (plugin 0.33): its title is what it is about and its body what happened there. The plugin adds `title` to the message (a session's: its chat's title from the chat list, renames included, else Hermes's `state.db` title, compression lineage followed; a routine's name; a project's name; cut at 80 characters), and `bot`, the bot character the app told it with `POST push/mute` `{ muted, bot }` (`push_prefs`, sent by `syncMutes` whenever the character changes). The body is one sentence per kind (`WORDS` in `public/push-sw.js` and `netlify/lib/fcm.ts`, which keep the same text); a push without a title reads "Gots" ("A routine", "A project"). The PWA's icon is the bot's picture (`/bots/<bot>.png`); Android's is the app's, since Haseeb didn't like Firebase's notification image, and the plugin keeps `bot` from the registry. The title, unlike what was asked, reaches the registry and Firebase in the clear on Android; Web Push carries it encrypted to the device.
- **Live bots** (`live.ts`): the app keeps one `fetch` stream (EventSource can't send the key) per distinct server and key while the page is visible and online, closes it when hidden, resumes from its cursor and treats 50s without a byte as dead. `session` catches up the open chat, `title` re-reads Hermes's title, `chats` runs `syncNow`, `runs` (settled for 300ms, since the status follows the approval hook) refreshes Waiting for input and the Code screen's sessions, `projects` the Projects, project and Code screens, `cron` Routines, and a first `hello` or a `reset` does all of it. A live screen keeps its timer at `SAFETY_MS` (5 minutes) as a safety net; a bot whose stream isn't open (an older plugin without the `events` feature, which is asked again after 5 minutes, a proxy that buffers it, a page in the background) polls as it always did.
- **A chat's context use needs the Gots plugin** (`Conversation.liveContext`, local only, read on every catch-up and after each turn): the latest model call's prompt and Hermes's own window, the same on every device. Hermes's API has nothing exact to work it out from (a turn's `prompt_tokens` and the session's `input_tokens` are summed over every call, and message rows' `token_count` is unset), so bots without the plugin aren't tracked: the usage sheet keeps an empty bar under a `Banner` saying the plugin is needed. The window the bot holds for the model shows first, then Hermes's for the call that ran it, then models.dev's. The usage sheet opens from Context in the chat header's options menu, which shows the percentage; a wide screen shows the ring in the header instead.
- **A project session's `projectId`, `resolvedAt`, `discardedAt` and `afk` sync** through the chat list (`CHAT_FIELDS` in `sync.ts`, applied field by field so a field a newer record dropped, like a reopened session's `resolvedAt`, clears here too; add any new synced chat field there). `afk` is written by the plugin for the session it started for a claimed task, never by the app, and the Code list reads it as a chip beside the row's title. Its `mode`, `worktree` (branch, repos and the instructions line), `planPending`, `prs` and `pipeline` are local copies of what the plugin holds, read on open, on every catch-up and a moment after each turn (`refreshWorkspace`, `refreshPrs`), written with `db.conversations.update` so the clock doesn't move. Before the first turn the mode is only local, and the first workspace post carries it.
- **A chat's todo list needs the Gots plugin too** (`Conversation.todos`, local only, read on every catch-up, at turn end and just after a `todo_list` call, which is what picks up the list the live stream only previews). Keyless bots and bots without the plugin show no list, so a chat shows the same on every device. The progress and each item's depth arrive with the list; a plugin older than 0.48 has neither, and the app shows the list without a count rather than working one out.

## Linking bots

Bots register themselves instead of being typed in (design: https://claude.ai/code/artifact/2ecc0ba3-e01e-4604-a8d5-bdacd8285650). The app shows a link code; on the host, `hermes memento link <code> --site <app>` (or the Hermes dashboard's Gots tab) claims it and publishes the profile's sealed record; every device turns the record into a bot.

- **The inbox.** The vault carries `inbox: { keyId, publicKey, privateKey }` (`vault.ts`): a P-256 key whose private half is sealed with the data key for `memento:<userId>:inbox`. `setUpSync` makes it, and `ensureInbox` (every sync) adds one to an older vault and keeps this device's non-extractable copy in `db.vault` (`id: "inbox"`). `keyId` is the hex of the first 8 bytes of the public key's SHA-256. **The plugin never gets the recovery code or the data key.**
- **Link codes** are minted by the app: `mk_<codeId>-<secret>-<fingerprint>`, Crockford base32 of 5, 10 and 8 random/derived bytes (8, 16 and 13 characters); the fingerprint is the same 8 bytes as `keyId`. The app posts only `codeId` and the secret's SHA-256 hex (`POST ?route=codes`), so the registry can't forge a code or swap the key: the plugin checks the public key it's handed against the fingerprint. A code lasts 30 minutes and 20 claims; 10 wrong secrets burn it.
- **The registry** (`/.netlify/functions/registry?route=…`, Blobs store `memento-registry`) reads the inbox from the account's `vault` document in `memento-sync`. Hosts send `Authorization: Bearer mh_…` (stored only as a SHA-256 under `tokens/`): `POST claim` (no auth; `{ codeId, secret }` → `{ userId, hostId, token, inbox, origins }`), `GET inbox`, `PUT bots&id=` (`{ keyId, sealed }`), `DELETE bots&id=`, `POST seen` (`{ bots, pluginVersion }` → each bot's `enabled`, or null to publish again, and the current `keyId`) and `DELETE host`. The app (Identity): `POST codes`, `GET bots` (records with `seen`), `PATCH bots&id=` (`{ enabled?, adopts? }`) and `DELETE hosts&id=`. `enabled` and `adopts` belong to the app; a host's publish keeps them.
- **A bot record** is `{ name, profile, baseUrl, apiKey, pluginVersion }`, sealed to the inbox (`openFromInbox`): an ephemeral P-256 key, ECDH, HKDF-SHA256 with the ephemeral point as salt and `memento-inbox-v1` as info, AES-256-GCM, associated data `memento:<userId>:bot:<botId>`. `botId` is the first 16 hex of SHA-256 of `<hostId>:<profile>`.
- **Records become bots** (`syncRegistry` in `registry.ts`, on every sync with an unlocked vault and every 3s while a link screen is open). A bot's id is its `botId`, or the `adopts` id when it took over a bot added by hand with the same server and key (the app sets `adopts` the first time it sees the record, so its chats stay with it on every device). `baseUrl` (plus `/v1`), `apiKey` and `hostId` come from the record; name, character and default model stay the user's and sync through `bots`. `disabled` and `seenAt` are local copies of the registry's. A failed read changes nothing; a bot whose record is gone is deleted (the last one is replaced by a fresh seed). Records sealed to another inbox key are skipped until the host re-seals.
- **Online** is a check-in within 25 minutes (the plugin checks in at gateway start, every 10 minutes and right after linking). **Reachable** is `/health` answering from this device (`useReachable`).
- **Disable** only hides a bot in the app and stops every live check for it (decided): it leaves the bot picker, Recents, Code, Routines, Waiting for input and chat sync, and context, todos and PRs aren't read. The host, its routines and its heartbeat carry on.
- **Remove** revokes the bot's host (`DELETE hosts`), which takes every bot that host linked; the host sees a 401 on its next check-in and stops. Its chats stay on the plugin.
- **Bots added by hand** before linking keep working and stay editable (address and key); new ones can't be added. A bot without an API key can't send.

## Community

- **On by default from setup, off by choice, and the GitHub username is the only identity.** The setup wizard's Join the leaderboard step (`app/src/routes/setup.tsx`, `CommunityStep`) turns it on unless the user switches it off before Continue; Settings > Community (signed in only) joins or leaves the leaderboard with `POST/GET community?route=join|leave|me` (Identity). The function takes the GitHub account id from the sign-in's avatar URL (`avatars.githubusercontent.com/u/<id>`, what Netlify Identity's GitHub provider gives) and asks GitHub's public `GET /user/<id>` for the login (`GITHUB_TOKEN` on the site only lifts the rate limit). **Under no circumstances store any other personal data on Netlify** (Haseeb's rule): no email, name, avatar URL or id, no hosts, sessions, prompts or paths in the public store `gots-community`; the only thing that names a person there is `users/<login>`, with day, model and mode counts. What links a login to an account (`users/<userId>/community`, `community/owners/<login>`, each host's last report) lives in the private `memento-registry` store, and Leave deletes all of it plus the public record and the cached board.
- **What is tracked:** per UTC day, model (lower case, provider prefix dropped) and mode (`plan`, `auto`, `accept_edits`, `chat`; a report's `theseus` or `goal` counts as `auto`), the input, output, cache-write and cache-read tokens and the call count, and separately each day's tokens by provider and model (Hermes's provider slug from the hook, a custom endpoint's own name dropped: `custom:acme` is `custom`; `community_providers`, sent as the report's `providers`, which an older plugin leaves out). The plugin counts them (`plugin/community.py`, `post_api_request`, API server sessions only, the project session's record else `chat`; `memento.db`'s `community_usage`, 35 days) whether or not the account joined; they leave the host only once it has (`GET community` on each check-in says `enabled`, then `POST report` when the counts changed, with the host's token). Counts are host-reported, so the function validates and caps them (`cleanDays`) but can't prove them.
- **Boards:** Top tokens spent (each person's tokens split by the period's five most used models, `topModels`, and Others) Top model (its tokens split by mode) and Top providers (each provider's tokens split by its own five most used models and Others, named under its bar), each for today, 7 and 30 days (`GET community?route=board`, public, cached 5 minutes, CORS `*`; a cached board whose `version` isn't `BOARD_VERSION` is built again, so bump it when the shape changes). The website remembers the period last picked on the device (`localStorage`), after a `#today`/`#week`/`#month` link. A new board goes in `buildBoard` and the website's `render.ts`.

## Sharing into Gots

- **Links, text and any file shared from another app open `/share`**: the shared content, a note, the bot (every one turned on) and a new chat or one of that bot's 30 newest, where tapping one sends at once (project sessions left out; called threads when bot threads are on). Sending is the chat's own send: a new chat is created, an existing one catches up first (as its composer does) and gets the message queued while a reply streams. The message is the note, then the title (with a link), the text and the links; files become its attachments through `prepareAttachment`, under the caps a pick is held to, and one that doesn't fit is a toast naming the limit (`src/lib/attachment-caps.ts`).
- **Android app**: `ShareTargetPlugin` (registered in `MainActivity`) takes `ACTION_SEND` text and `ACTION_SEND`/`SEND_MULTIPLE` files of any type (the intent filters in `AndroidManifest.xml`), copies up to 10 files (20 MB each) into the cache, since the sender's grant ends with the intent, and sends a retained `share` event, so the share that launched the app reaches the page too (`skipLaunchRestore` then keeps the launch from reopening the last chat). A file the copy can't take — more than 10, over 20 MB, unreadable — comes back in the event's `refused`, so the screen says which limit refused it rather than losing it; the app's own caps (9 MB a file, 10 a message, 6.5 MB of inline photos) are what the screen holds every file to. The page reads the copies through `Capacitor.convertFileSrc`.
- **Installed PWA**: the manifest's `share_target` posts to `/share-target`, which `public/share-sw.js` (imported by the generated service worker before Workbox's routes) keeps in the `memento-share` cache and redirects to `/share?id=`. Chromium only (Chrome and Samsung Internet on Android, desktop Chrome and Edge); Safari has no share target (MDN's compat data, checked 2026-10-09), and a browser tab that isn't installed is never offered.
- **iOS has nothing yet**: there is no iOS app, and receiving shares there needs one with a Share Extension and an App Group, so a paid Apple Developer Program account.
- `window.mementoShare({ title, text, url, files })` opens the screen in development.

## Conventions

- **The UI renders from Dexie live queries.** Streaming writes into IndexedDB (throttled), and components never hold stream state.
- **Every write re-runs every live query over its range**, and a streaming reply writes every `FLUSH_INTERVAL_MS` (`chat.ts`). So keep the work each write causes small:
  - Read only what a screen shows, through an index: a list row reads its chat's tail or opener (or a count over `[conversationId+role]`), never every message, and never `anyOf(...)` filtered in JS. Add the index (bumping the Dexie version) rather than scan.
  - Don't write what didn't change: compare before a `put` or `update`, since a fresh object wakes every query that covers it (`saveSettings` skips equal writes).
  - A live query hands back new objects on every run, so memoize rows that render them on their value (`MessageItem`), and depend on ids, not live-query objects, in effects and memos.
  - Work that grows with streamed text keeps its finished part: markdown renders as memoized blocks (`markdown-blocks.ts`), so only the open block is parsed again.
- **Requests are bounded and independent.** Every read to a host carries a timeout (`READ_TIMEOUT_MS`), and per-bot work runs side by side, so one hung host never stalls another bot, sync or onboarding. Follow-up reads (title, context, provider limits, todos, workspace, PRs) run when the transcript moved, else at most every `FOLLOW_UP_MS` (`freshness.ts`), and never on the send path. The one read fired there is a chat's model record, as a turn is sent and never awaited (`model-changes.ts`, and ADR 0010 for why that exception is narrow). A cooldown starts only when the route is missing (`lacksRoute`), never on any failure.
- **Release what you take.** A guard, lock or `streaming` status set at the start of an async flow is released in `finally`, so a throw or a dropped stream can't leave a chat stuck. Deleting a record deletes its device-only rows too (drafts, saved dictations).
- **Startup stays small.** Only the chat route loads up front: every other route, heavy library (the markdown renderer, highlight.js) and anything behind a feature switch (Research) is a lazy import. A returning device renders from what it has on the device; network checks (Identity, the vault) run behind it, never in front of it.
- **Measure performance changes.** Profile before and after (CDP `ScriptDuration` while a reply streams, or the build's chunk sizes) and give the numbers in the PR. `pnpm e2e stream-writes` and `pnpm e2e idle-requests` guard the write and request budgets; keep them passing, and add a flow when you fix a regression.
- **History mirrors the sidebar.** Top-level screens (chats, Code, Routines, Settings) open with `root` as the only history entry, so back leaves the app; a deeper screen (a project, a session, a Settings section) is pushed on its parent, goes back with `up`, and sets `setBackGuard` so Android's back does the same. From a top-level screen Android's back shows a "Press back again to exit" toast at the bottom (above anything marked `data-toast-above`, like the composer), and a second press within 2s minimizes the app.
- **Screens and tabs animate in.** `AppShell` slides the main pane in from the right on a push, from the left on back, and fades it on a replace; a `replace` navigation that keeps the same screen passes `state: { quiet: true }`. Tab panels slide in from the side of the tab they were opened from. Everything respects `prefers-reduced-motion`.
- **If you change the schema, bump the Dexie version** in `src/lib/db.ts` and keep existing data loading.
- **Every screen must work at phone (390px) and tablet (≥768px) widths, in light and dark mode.**
- **Pop-ups are bottom sheets on phones and tablets and side drawers from 1024px.** Build them with `Popup` / `PopupContent` (`src/components/popup.tsx`), which picks with `usePopupDrawer`, rather than a bare `Sheet` or dialog. A one-tap pick opened from a button passes it as `anchor`, to be a menu beside it on large screens. A yes-or-no confirmation stays an `AlertDialog`; a recording or a photo is a `FullscreenPopup`. A form inside an `AlertDialog` is an exception only where one step's answer is what the next step shows, as replacing a sync recovery code is (`docs/adr/0005-a-recovery-code-is-compulsory-a-passkey-is-optional.md`). The sidebar's drawer is not a pop-up.
  - A pop-up's width is its `size` (`lg` by default, or `md`, `xl`, `2xl`), never a max-width class: a tablet sheet narrower than 640px only for `md`, and a menu's width. A side drawer takes its own width and the full height, so a size or a max-height can't set it.
  - Every pop-up renders a `PopupHeader` with a title — it's pinned, reserves room for the close button, and keeps content from ever sitting against it. The heading is centred in every form, like a Material bottom sheet's, and cuts with an ellipsis rather than running under the close button; a heading beside a control of the header's own row passes `text-left`. A phone sheet centres its whole header, as a bottom sheet does. The close button lives in a side drawer's header; sheets have none (swipe, the scrim or the handle dismisses) and nor do menus (a press outside dismisses). `PopupContent` reports to the dev console when a pop-up renders with no `PopupHeader`.
  - Use the theme tokens. Don't hard-code colours, except for the fixed character palettes in the bots.
  - Respect safe-area insets.
  - Keep touch targets at 44px or larger.
- **Bots:** they are still by default. Only the header (and the empty-state hero) passes `animate`. Animations must respect `prefers-reduced-motion`.
- **Assets must be original or properly licensed.** Never copy third-party characters, mascots or brand assets, even as "inspiration" copies.
- **Never commit secrets.** API keys live only in the user's browser.
- **No explanatory copy.** Don't add UI text that explains how the app works or where its data comes from (footnotes, "from X" captions) unless asked. If it seems needed, ask first.
- Match the surrounding code: Prettier style (no semicolons, 100 columns) and few comments. Comments explain *why*.
